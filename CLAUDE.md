## Ключевые архитектурные решения
**Состояние КП.** Плоский `st.session_state` с префиксными ключами
(`opt_{key}_enabled`, `opt_{key}_price`). Вложенных dict нет, кроме `options`.

**Состояние договора.** Вложенный `st.session_state["contract"]`:
`specification.items` (массив SpecItem), `flags` (winter_concrete и т.п.),
`scope_overrides`, `card`, `extracted`.

**Цены — 3 класса** (поле `price_class` в prices.json):
- `A_retail_and_dealer` — slider [dealer_ru ↔ retail×1.4], default retail
- `B_retail_only` — slider [retail×0.6 ↔ retail×1.4], default retail
- `C_manual_range` — number_input [range_min ↔ range_max], default price_retail

**Инварианты поведения:**
- При смене модели — сбросить все options, model_price = retail новой модели.
- Derived (model_id, spec_items, суммы) — считаем на рендере, не храним в state.
- Валидация возвращает `(errors, warnings)`. errors блокируют кнопку.
- Дефолт пресета оплаты — `split_by_items`.

## Правила работы
- JSON-СПРАВОЧНИКИ ДАННЫХ в `data/` (prices.json, модели, оборудование)
  правит Антон вручную. Не переписывай их.
  Шаблоны текста (payment_terms.json — body_template) — часть рендер-пайплайна,
  правятся кодом при необходимости, но дифф показывать Антону до коммита.
- Type hints везде. Комментарии на русском, имена на английском.
- Файлы ≤200 строк, при разрастании — разбивай.
- Новые зависимости в requirements.txt — только с одобрения Антона.
- Git: Conventional Commits на русском (`feat:` `fix:` `refactor:` `chore:`
  `docs:` `test:`). Один коммит = один шаг из STATUS.md.
- Code делает `git add` + `git commit` после каждого блока. **НЕ пушит**
  (push — только по явному запросу). **НЕ создаёт ветки** — работа в `main`.
- Перед коммитом `pytest tests/` должен пройти. Красное — не коммитить.
- Нетривиальная задача (3+ шага, новый файл, рефакторинг) → сначала plan mode.
  План поплыл в процессе → STOP, переплан, потом продолжаем.

## Принципы разработки (Karpathy)
1. **Think Before Coding** — не угадывай. Неясно — спроси. Несколько трактовок
   — покажи их, не выбирай молча. Есть путь проще — скажи.
2. **Simplicity First** — минимум кода. Никаких фич «на будущее», абстракций
   для одного использования, обработки невозможных ошибок. 200 строк можно за
   50 — перепиши.
3. **Surgical Changes** — трогай только относящееся к задаче. Не «улучшай»
   соседний код, не удаляй чужой dead code. Стиль — как в файле.
4. **Goal-Driven Execution** — критерии успеха до начала. «Добавить валидацию»
   → «написать тесты на невалидные входы, потом пройти их».
5. **Verification First** — до начала сформулируй чек-лист проверки: какая
   команда покажет, что работает, какой ручной smoke. Без чек-листа задача не
   закрывается. Не «должно работать» — «вот команда, вот её вывод».
6. **Бриф — гипотеза, а не спецификация.** Разведка обязана проверять саму
постановку задачи, а не только исполнять её. Если бриф называет файл/функцию —
проверить, что дефект действительно там. Прецеденты 2026-07-13:
- A6: бриф указал код, «рублей» жила статикой в трёх DOCX-шаблонах →
  фикс по брифу оставил бы цитату гейта несогласованной.
- A8: бриф предложил развилку «код vs Word»; оба варианта неверны, фикс
  только в шаблоне. Вариант из брифа уронил бы соседний страж A5.
- days: бриф указал payment_section.py (превью в сайдбаре); настоящий провод
  генерации КП — generators/payment_renderer.py → печатный документ остался бы
  сломанным.
Во всех трёх случаях исполнение «по брифу» дало бы корректно реализованный баг.

## Работа по активной задаче (docs/STATUS.md)
Секция «Активная задача» в STATUS.md — единственный источник правды о шаге.
- **Начало сессии:** назови текущий незакрытый шаг (маркер `← ТЕКУЩИЙ`) одной строкой.
- **Завершение шага:** `[x]` + хэш коммита в строке шага, сдвинь маркер на
  следующий. Галочка — отдельным коммитом `docs: шаг N выполнен`.
- **Секцию «Сейчас»** (фаза/прод) НЕ трогай — только по команде «обнови статус».
- **Новая задача:** разбей набросок на 5–12 атомарных шагов, покажи план,
  жди подтверждения.
- **Закрытие:** все шаги `[x]` → удали блок (история остаётся в git log),
  верни «(нет активной задачи — следующий фронт: …)».

**Что НЕ писать в STATUS.md** (анти-протухание):
- ничего выводимого из git log: закрытые задачи, «сделано в сессии», теги;
- номера/счётчики строк кода — только имя символа/файла (+ grep-команда);
- статусы и описания техдолга — только ID-ссылки на `docs/TECH_DEBT.md`,
  статус пункта живёт ровно в одном месте.

## Финализация сессии (обязательно, перед последним коммитом)
Сессия не считается завершённой, пока не выполнено:
1. **STATUS.md актуален:** шаг закрыт → `[x]` + хэш коммита, маркер `← ТЕКУЩИЙ`
   сдвинут; задача закрыта целиком → блок удалён, возвращена строка
   «(нет активной задачи — следующий фронт: …)». Прогнать
   `pytest tests/test_docs_sanity.py`.
2. **Находки — в TECH_DEBT.md, в ЭТОЙ ЖЕ сессии.** Любой обнаруженный по ходу
   дефект, риск или мина, который НЕ чинился (чинить попутно запрещено — один
   фронт за раз): запись в раздел A/B/C со статусом 🔲, с данными для фикса
   (имя символа/файла + grep-команда, НЕ номера строк — плывут). Обновить
   таблицу «Прогресс». **Находка, не записанная до конца сессии, потеряна:**
   следующая сессия о ней не узнает.
   Принцип: факт не должен существовать в нуле копий ни одного коммита.
   Нашёл → записал → закоммитил в той же сессии. Не «запомню и заведу потом».
3. **Доккоммит отдельный:** правки STATUS/TECH_DEBT — коммитом `docs:`,
   не смешивать с кодом.
Если обновлять нечего — сказать это явно в финальном отчёте:
«STATUS/TECH_DEBT: без изменений». Это осознанная проверка, а не умолчание.
