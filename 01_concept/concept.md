## 1. Зачем (бизнес-цели)

В порядке приоритета:

1. **Устранить типовые ошибки** в КП и договорах (рассинхрон модели и ТХ, ошибки в условиях оплаты, арифметика, опечатки).
2. **Автоматизировать генерацию договоров** из утверждённого КП — сейчас это 1–2 часа ручной работы, самая болезненная часть процесса.
3. **Сэкономить время на подготовку КП** — текущая оценка ~5–6 часов в месяц (см. метрики).
4. **Создать задокументированный кейс AI-внедрения в B2B-продажи** — основа для будущей консалтинговой практики.

## 2. Базовые метрики (точка отсчёта)

> Цифры — экспертная оценка менеджера, **не замерены секундомером**. До запуска MVP запланировать замер 5–10 реальных КП для честного baseline.

- Простое КП по автовесам: ~15 мин
- Типовое КП: ~30 мин
- Сложное КП: 1 час+
- Объём: ~15 КП/мес по автовесам
- Конверсия в сделку: 1–2 из 15 (7–13%)
- Средние трудозатраты: ~5,6 ч/мес на КП
- Договор: 1–2 часа на каждый, ~1–2 договора/мес

## 3. Что строим (scope MVP)

**MVP = конфигуратор КП по автовесам ВЕСТА.**

### Продуктовый scope (справочник):

- **Линейки:** С, СЛ, Ф, ФЛ, П
- **Длины платформы:** 18, 20, 22, 24 м
- **Тоннажи:** 40/60/80/100 (для С, Ф); 40/60/80 (для СЛ, ФЛ); П — по факту продаж
- **Датчик:** один пресет — Zemic DHM9B-30t (покрывает 85% продаж)
- **Вне scope:** М1, М2, К, Б, СБ, ФБ, ПВП, ПВС; длины короче 18 м; альтернативные датчики

### Функциональный scope:

1. Выбор модели из справочника → автоподтяг ТХ (без рассинхрона)
2. Конфигурация комплектации (фундамент, монтаж, доставка, поверка, ПАК ОРИОН — опционально)
3. Цена в коридоре «дилерская–розничная»
4. Условия оплаты — пресеты + ручная подстройка процентов
5. Обязательные поля: «Кому», номер лида из Битрикса (вводится вручную)
6. Редактируемые поля с дефолтами из справочника: гарантия, толщина настила и т.п. — менеджер может переопределить
7. Автоматический расчёт сумм (никакого ручного сложения)
8. Генерация DOCX по единому шаблону (как в текущих КП — 12–14 страниц со всеми маркетинговыми блоками)

### Архитектурный принцип:

**«Умный шаблон с пресетами и страховкой», а не «робот-генератор».**
Большинство технических полей = дефолт из справочника + возможность ручного переопределения. Менеджер остаётся принимающим решения, но не вспоминающим цифры.

## 4. Какие ошибки MVP механически предотвращает

1. **Рассинхрон названия модели и её ТХ** в шаблоне (модель из справочника → ТХ автоматом)
2. **Пропуск/некорректное заполнение условий оплаты** (обязательное поле с пресетами)
3. **Арифметические ошибки** в суммировании позиций (считает конфигуратор)
4. **Рассинхрон температурного диапазона и базового датчика** (для дефолтного Zemic — автоматом)
5. **Дубли номеров КП** (обязательное поле «номер лида», полная автоматизация — после интеграции с Битриксом, фаза 3+)
6. **Гарантия не той линейки** (дефолты по линейкам: С/Ф = 36 мес., СЛ/ФЛ = 24 мес., с возможностью ручного снижения для Сибири/тяжёлых условий)

## 5. Технологический стек

- **Streamlit** — UI и хостинг (Streamlit Community Cloud)
- **JSON/CSV** — справочники (модели, ТХ, опции, пресеты оплаты)
- **python-docx** — генерация DOCX по шаблону
- **Basic-auth** — простая защита от случайного доступа (цены чувствительны)
- **Никакого Битрикса в MVP** — интеграция отложена на фазу 3+

## 8. Критерии успеха

MVP считается успешным, когда выполнены **все четыре** условия:

1. Время на подготовку КП через конфигуратор < времени на подготовку через текущий Word-шаблон
2. В сгенерированных КП отсутствуют типовые ошибки из раздела 4
3. Договоры собираются автоматически из утверждённого КП по шаблонам Тензосилы (фаза 2)
4. Старые Word-шаблоны не открываются для подготовки КП и договоров в принципе

## 9. Принципы работы над проектом

- MVP сначала, красота потом
- Каждая итерация — рабочая и улучшает текущий процесс минимум на 30%
- Технически максимально просто
- Overengineering — враг
- Никакой интеграции с внешними системами раньше фазы 3
