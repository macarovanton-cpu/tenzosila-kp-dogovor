### A9. `delivery.prepay` — фантомное поле роняет сумму оплаты Доставки — ✅ ЗАКРЫТО (2026-07-13)

**Корень.** `delivery.prepay` — фантомное поле: живёт в `payment_split_state`,
редактируется в UI, участвует в валидации суммы (`validation.py:66-78`), но
`build_lines_from_snapshot` его НИКОГДА не читает — у доставки потребляется
только `postpay` (`payment_line.py`, L3). В отличие от `foundation`/`iv`, чьи
`prepay` реально уходят в L1/L4. Любой путь, делающий `delivery.prepay`
ненулевым при компенсирующем понижении `postpay` (чтобы пройти сумму=100),
молча занижает график: L3 билит `delivery_total·postpay%` вместо `·100%`,
недостающая доля нигде больше не выставляется. `validation.py` это пропускает
(`50+50=100`), кнопка «Сгенерировать» не блокируется. Эталон: `915000 =
50%·весы + 100%·доставка`.

**Правка разведки (что запись утверждала неверно).** Первичная запись говорила,
что кнопка «Применить ко всем группам» ПЕРЕТИРАЕТ доставку на 50/50. По факту
на проде она до этого не доходила — она ПАДАЛА (`StreamlitAPIException`):
писала в `st.session_state[f"split_{gid}_{k}"]` ПОСЛЕ инстанцирования виджета
с тем же `key`. Перетирания не было; был краш. Фантом-класс воспроизводится и
без кнопки — ручным вводом Доставка prepay=30/postpay=70 (тот же недобор).

**Фикс (трёхслойный, по образцу A5):**
- **Слой 0.** Крашащая кнопка «Применить ко всем группам» удалена целиком
  вместе с мёртвым обвесом (`active_group_ids`, `has_other_active`). Решение
  Антона: экономила два поля, требовала спецкейса на Доставку — не окупается.
- **Слой 1.** `delivery.prepay` — read-only 0 (disabled) в UI
  (`payment_section.py`, флаг `frozen`), в `split` пишется 0 напрямую (залипшее
  значение виджета из прошлой сессии не утечёт). `foundation`/`iv` prepay не
  тронуты. Валидацию суммы=100 не ломает (дефолт `0+100`).
- **Слой 2 (главное).** Страж `_assert_payment_covers` в
  `build_lines_from_snapshot` (`src/contracts/payment_line.py`) — сверяет
  Σ`amount` с суммой-эталоном ветки: split — Σ 4 бакетов (позиция без бакета —
  забота UI, `st.error`, не движка), non-split — `_spec_total×qty`. Недобор >
  допуска `max(len,1)` ₽ → падает `PaymentCoverageError`. Суммирует реальные
  `amount` (не `%×база`) — о мину составной строки W1 не спотыкается.
  ⚠️ Границы страж не покрывает (агрегатный, не build-time-путь — не финальная
  генерация): см. **B10**.

**Тесты (B9, пятое пятно).** `test_bridge_delivery_prepay_undershoots_raises`
(бывший `..._keeps_percent`, что ЗАКРЕПЛЯЛ баг) +
`test_bridge_delivery_default_covers_total` (компаньон против ложного
срабатывания), `tests/contracts/test_payment_line.py`. Полная сеть + golden
зелены — страж не сработал ни на одной легальной фикстуре (инвариант держится).

### B1. Два семейства id в матчинге оплаты — 🔲 ОТКРЫТО (не фиксить превентивно)

**Проблема:** путь Спецификации использует канонические id из `spec_items`
(`rama`, `pandus`, `orion_poles`), путь КП — ключи опций конфигуратора.

формулировки оплаты (W6, W9 и т.п.) перестанут матчить эту позицию молча.

**Данные для фикса (держать в уме при следующей новой позиции, не чинить превентивно):**
- Искать: `grep -rn "wording_flags" src/`
- При добавлении новой позиции — чек-лист: id заведён и в `spec_items`
  (канонический), и в ключах опций КП; `wording_flags` матчит оба.
- Кандидат на устранение позже: единый реестр id вместо двух параллельных
  семейств — отдельный рефакторинг, не делать между делом.

### B2. Р/с-checksum в валидаторе реквизитов — неполный — 🔲 ОТКРЫТО

**Проблема:** валидация расчётного счёта сейчас проверяет только длину (20
цифр) и согласованность с БИК через к/с. Полная 23-значная контрольная сумма
р/с (алгоритм ЦБ РФ 7-1-3) не считается — невалидный по контрольной сумме
счёт может пройти валидацию и попасть в договор.

**Данные для фикса:**
- Искать: `grep -rn "_valid_inn\|requisites_validation" src/` — валидатор
  реквизитов, туда же добавляется чек-функция.
- Алгоритм ЦБ РФ для проверки р/с: контрольная сумма считается по 23-значному
  ключу (БИК-код банка, дополненный нулём слева при необходимости, + номер
  счёта), с весовыми коэффициентами 7-1-3-7-1-3-7-1-3-7-1-3-7-1-3-7-1-3-7-1-3-7-1
  (повторяющийся паттерн), сумма произведений по модулю 10 должна быть равна 0.

### Реестр типов работ для ручных позиций (custom_work_types) — 🔲 ОТКРЫТО

- [ ] **Расширить `CUSTOM_WORK_TYPES` на Фундамент / Поверку / ОРИОН.**

     разные клаузы/разные бакеты оплаты при одинаковом смысле. Это главный риск.
  3. Для фундамента дополнительно решить: какой `foundation_scope` считать дефолтом
     (`contractor_full` / `customer_builds` / иное) — от него зависит, кто по договору
     строит фундамент. Неверный дефолт = договор с чужими обязательствами.
  4. Поверка: проверить `customer_side`-клаузы (испытательный автомобиль, организация

## Как использовать этот файл

1. **Обновлять статус пункта СРАЗУ после фикса или проверки** — не копить
   расхождение между файлом и реальным состоянием кода. Три пункта в этой
   версии (A1, B3) оказались ложными тревогами именно из-за такого разрыва —
   описание жило дольше, чем сам дефект.
2. Свериться, что номера строк/файлов актуальны (код мог измениться) —
   перепроверить через `grep`/`view`, не доверять слепо.
3. Написать/найти воспроизводящий тест ДО фикса, где это уместно
   (диагноз фактами до фиксов — принцип проекта).
4. Прогнать `python -m pytest tests/ --ignore=tests/contracts/synthetic`
   до и после — синтетика (`tests/contracts/synthetic/`) исключена из
   прогона намеренно, не трогать, не анализировать её падения.
5. Один пункт — один атомарный коммит (Conventional Commits, русский).
6. Для изменений бизнес-логики (платежи, клаузы, spec-рендереры) или
   многофайловых правок — ревью более сильной моделью до `git push`
   (см. правила ревью в `CLAUDE.md`).
7. Обновить таблицу «Прогресс» в начале файла при закрытии/открытии пунктов.
   **Закрытый пункт (✅/🕵️) сжимать до 3–5 строк** — диагноз + хэш коммита;
   полная история — в `git show` коммита закрытия, не здесь.
8. `grep "🔲" docs/TECH_DEBT.md` — остаток реального долга, цель фазы — ноль.
   🔒 ОТЛОЖЕНО (осознанное решение не делать) в счёт не идёт.
