## A — в первую очередь

### A1. Привязка «ТПК»→«Компания» к подстроке номера Госреестра (C4)

**Проблема:** в клаузах есть замена наименования «ТПК» на «Компания», которая
привязана к подстроке конкретного номера Госреестра СИ РФ. T3 (контентный фикс
КП) сменил печатаемый номер на `78871-20` (был `62329-15`). Если привязка C4
матчится по старому номеру-подстроке — она молча перестала срабатывать, и
каждый генерируемый договор сейчас содержит неверную подстановку наименования
Подрядчика. Молчаливый и клиентский — высший приоритет.

**Данные для фикса:**
- Искать: `grep -rn "78871-20\|62329-15" src/` и `grep -rn "ТПК.*Компания\|Компания.*ТПК" src/`
- Вероятная локация — рендерер клауз (`clauses_renderer.py` или аналог) и/или
  `clauses.yaml` (см. `data/clauses.yaml` в проекте).
- Проверка: сгенерировать любой свежий договор → найти в тексте, где должно
  быть «Компания» вместо «ТПК» → сверить, что подстановка сработала.
- Если привязка отвалилась: заменить матчинг по подстроке номера на явный
  плейсхолдер/флаг, не зависящий от конкретного значения номера Госреестра
  (номер может смениться снова).
- Тест: юнит-тест на рендер клаузы с текущим номером `78871-20`, ассертящий
  корректную замену «ТПК»→«Компания».

- Механическая замена по всем файлам `src/ui/`, `src/pages/` — низкий риск,

## B — следующим эшелоном

### B1. Два семейства id в матчинге оплаты

**Проблема:** путь Спецификации использует канонические id из `spec_items`
(`rama`, `pandus`, `orion_poles`), путь КП — ключи опций конфигуратора.
`wording_flags` матчит оба семейства параллельно. Не баг сейчас, но при
добавлении НОВОЙ позиции легко забыть завести id в одном из двух семейств —
формулировки оплаты (W6, W9 и т.п.) перестанут матчить эту позицию молча.

**Данные для фикса (не фиксить превентивно — держать в уме при следующей
новой позиции):**
- Искать: `grep -rn "wording_flags" src/`
- При добавлении новой позиции — чек-лист: id заведён и в `spec_items`
  (канонический), и в ключах опций КП; `wording_flags` матчит оба.
- Кандидат на устранение позже: единый реестр id вместо двух параллельных
  семейств — отдельный рефакторинг, не делать между делом.

### B2. Р/с-checksum в валидаторе реквизитов — неполный

**Проблема:** валидация расчётного счёта сейчас проверяет только длину (20
цифр) и согласованность с БИК через к/с. Полная 23-значная контрольная сумма
р/с (алгоритм ЦБ РФ 7-1-3) не считается — невалидный по контрольной сумме
счёт может пройти валидацию и попасть в договор.

**Данные для фикса:**
- Искать: `grep -rn "_valid_inn\|requisites_validation" src/` — валидатор
  реквизитов, туда же добавляется чек-функция.
- Алгоритм ЦБ РФ для проверки р/с: контрольная сумма считается по 23-значному
  ключу (БИК-код банка, дополненный нулём слева при необходимости, + номер
  счёта), с весовыми коэффициентами 7-1-3-7-1-3-7-1-3-7-1-3-7-1-3-7-1-3-7-1-3-7-1
  (повторяющийся паттерн), сумма произведений по модулю 10 должна быть равна 0.
  Реализовать как отдельную чистую функцию, покрыть юнит-тестами на известных
  валидных/невалидных пар БИК+счёт.
- ⚠️ ВАЖНО: `_valid_inn` импортируется из парсера в `requisites_validation.py` —
  НЕ переименовывать при рефакторинге этого модуля, иначе молча сломается
  импорт в валидслое.
- Тест: несколько известных валидных пар БИК/р-счёт (банковские примеры из
  открытых источников) + заведомо невалидная контрольная сумма → функция
  должна корректно отличать.

### B4. `merge_runs` guard не защищает `w:pict`/`w:object`/field-runs

**Проблема:** функция слияния текстовых runs в DOCX (используется, вероятно,
для нормализации форматирования после подстановки плейсхолдеров) имеет guard

Word, например номера страниц). Риск — повреждение этих элементов при
слиянии runs.

**Данные для фикса:**
- Искать: `grep -rn "merge_runs" src/`
- Расширить существующий guard (уже есть для `w:drawing`) — добавить
  аналогичные проверки на присутствие `w:pict`, `w:object`, `w:fldSimple`/
  `w:fldChar` в run перед слиянием; если элемент присутствует — run не трогать.
- Тест: собрать DOCX с полем/legacy-картинкой (или мокнуть XML-структуру),
  прогнать через `merge_runs`, убедиться, что элемент не повреждён/не потерян.

## Как использовать этот файл

Для каждого пункта A/B перед фиксом:
1. Свериться, что номера строк/файлов актуальны (код мог измениться) —
   перепроверить через `grep`/`view`, не доверять слепо.
2. Написать/найти воспроизводящий тест ДО фикса, где это уместно
   (диагноз фактами до фиксов — принцип проекта).
3. Прогнать `python -m pytest tests/ --ignore=tests/contracts/synthetic`
   до и после — синтетика (`tests/contracts/synthetic/`) исключена из
   прогона намеренно, не трогать, не анализировать её падения.
4. Один пункт — один атомарный коммит (Conventional Commits, русский).
5. Для изменений бизнес-логики (платежи, клаузы, spec-рендереры) или
   многофайловых правок — ревью более сильной моделью до `git push`
   (см. правила ревью в `CLAUDE.md`).
