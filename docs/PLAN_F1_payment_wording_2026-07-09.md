# F1 — единый источник формулировок блока оплаты (2026-07-09)

## Контекст

Текст оплаты генерируют два независимых пути с ручной синхронизацией → дрейф:
- **КП** — `src/generators/payment_renderer.py` (`render_split_by_items`), короткие строки без денег;
- **Договор/Спецификация** — `src/contracts/payment_line.py` (`build_lines_from_snapshot` → `format_payment_line`), полная юридическая форма.

Плюс 4 копии дефолтов процентов (JSON + 3 хардкода) и 11 расхождений с эталонами (W1–W11
в `docs/FIX_SPEC_payment_wording_2026-07-09.md` — единственный источник требований, решения приняты).

**Цель:** общий словарь формулировок (триггеры, объекты, предлог, слово-тип, срок) в одном модуле;
оба генератора рендерят из него в своём регистре (КП — lite без денег, Спец — full). Дефолты — только
из `data/payment_terms.json`. Итог совпадает с целевыми формулировками из FIX_SPEC.

**Решения Антона при планировании (2026-07-09):**
- Рама/пандусы — называть в объекте оплаты («Весов, комплекта пандусов и рамы»), тем же механизмом, что W9. В Стадию 2.
- Flat-формат для одной группы — НЕ автогенерировать; остаётся ручной опцией редактора (`share_pct=None`), зафиксировать тестом.
- W8: supply `WORK_ACT` («поставки Весов Покупателю») НЕ трогать. W8 закрывается самим механизмом контекстных
  override'ов в общем словаре (SPEC_SIGNED в supply уже даёт «настоящего Договора»). Тест supply остаётся.
- W3 («единичный платёж → Оплата») — только внутри `split_by_items`, по каждой группе. Не-split пресеты
  (prepay_100 «Предоплата», v3 «оплата») не трогаем — совпадают с эталонами.

**Проверка стоп-условия из задания:** свод НЕ задевает сериализацию снапшотов (ключи
`prepay`/`postpay`/`preship`/`split_state` не переименовываются, формат снапшота не меняется; старые КП
с явными процентами восстановятся дословно — меняются только fallback-дефолты и текстовый рендер).
`split_by_items` не ломается каскадно — правки точечные. СТОП/переключение на opus не требуется.

## Архитектура: общий словарь

**Новый модуль `src/payment_wording.py`** (уровень src-корня, как `spec_builder.py`/`term_days.py` —
без streamlit, чтобы его могли импортировать и `contracts/`, и `generators/`; `data_loader.py` не подходит,
он тянет streamlit). Содержимое:

1. **Дефолты из JSON** (единственный источник):
   - `_load_payment_terms()` — plain `json.loads(PAYMENT_TERMS_JSON.read_text())` из `src.config`, `@lru_cache`.
   - `default_split_percents() -> dict[str, dict[str, int]]` — из `presets[split_by_items].groups[*].default_percents`.
   - `default_days() -> int` — из `default_days` пресета.
2. **Триггеры** — один словарь, два регистра + контекстные override'ы:
   ```python
   TRIGGER_WORDING = {
       "SPEC_SIGNED":    {"full": "подписания настоящей Спецификации",
                          "lite": "с момента подписания Договора"},
       "FOUNDATION_ACT": {"full": "подписания Акта выполненных работ по строительству фундамента",
                          "lite": "после подписания Акта выполненных работ по строительству фундамента"},
       "SHIPMENT_READY": {"full": "получения уведомления о готовности Весов к отгрузке",
                          "lite": "после уведомления о готовности Весов к отгрузке"},
       "BRIGADE_READY":  {"full": "уведомления о готовности принять монтажную бригаду на месте монтажа",
                          "lite": "после уведомления о готовности к монтажу"},
       "WORK_ACT":       {"full": "подписания Акта выполненных работ по настоящей Спецификации",
                          "lite": "после подписания Акта выполненных работ"},
       "DELIVERED":      {"full": "поставки Весов Заказчику", "lite": "после поставки Весов"},
   }
   SUPPLY_TRIGGER_OVERRIDES = {"SPEC_SIGNED": "подписания настоящего Договора",
                               "WORK_ACT": "поставки Весов Покупателю",
                               "DELIVERED": "поставки Весов Покупателю"}
   ```
   + W9-расширение триггера: `foundation_act_text(has_orion_poles, register)` →
   «…по строительству фундамента **и установке опор и кабель-трасс**».
3. **Объекты** — функции с регистрами:
   - весы: `Весов` / `весов` (+ `(включая ПАК ОРИОН)`), + рама/пандусы: «Весов, комплекта пандусов и рамы»
     (детект по `item_key.startswith(("frame_", "ramp_set_"))` в spec_items);
   - фундамент: «фундамента Весов» + W9: «фундамента Весов и установку опор и кабель-трасс для ПАК ОРИОН»
     (детект `item_key == "orion_cable_poles"`);
   - монтаж: «монтажных работ и поверки» / W6: «шеф-монтажных работ и поверки» (по `installation_scope`);
   - доставка: «доставки».
4. **Слово-тип** (W3, только split): `kind_word(prepay_pct, postpay_pct, phase)` — обе фазы > 0 →
   «предоплата»/«доплата»; ровно одна > 0 → «оплата».
5. **Константы:** `PREP = "от стоимости"` (W10), `INVOICE_BASIS = "на основании выставленного Поставщиком счёта"` (W7).

`payment_line.py` строит `TRIGGER_TEXTS` из `TRIGGER_WORDING[..]["full"]` (имя и API сохраняются —
их импортируют `supply_filler`, `payment_lines_editor`); `supply_filler.SUPPLY_TRIGGER_TEXTS` — из
`TRIGGER_WORDING` + `SUPPLY_TRIGGER_OVERRIDES`. `payment_renderer.py` берёт `lite`-тексты и те же объекты.

**Критерий спеки:** формулировка правится в одном месте → одинаково меняется в КП и договоре.

## Границы (из спеки, соблюдаются)

`resolve_payment_group` для orion_lite/standard/auto — не трогаем (опоры W9 — только текст, сумма уже
в бакете foundation). Внутренние ключи prepay/postpay/preship — не переименовываем (W11 — только видимый
текст). `foundation_supervision`, пресеты v1/v2/v3/custom (кроме сведения их дефолтов к JSON) — не трогаем.
Инвариант «сумма КП = сумма договора» не затрагивается: суммы строк меняются только у монтажа
(50/50 вместо 0/100 — Σ по бакету по-прежнему 100%).

## Доп. замечания по плану (сверка Антона + Sonnet, 2026-07-09)

Подтверждено при ревью плана — держать в голове при исполнении:

1. **Доставка (W1).** НЕ становится 50/50. Остаётся 0/100; L3 печатает `scales.postpay`%
   («Весов и доставки»), доставка едет целиком при отгрузке. Это и есть эталонная арифметика
   (915 000 = 50%·весы + 100%·доставка). Подтверждено правильным.
2. **Асимметрия защёлки L1 vs L3 — осознанная.** L3 больше не схлопывается (W1), L1 (весы+фундамент)
   защёлку сохраняет как есть (не в W-списке). На дефолте обе строки рендерятся нормально; разъедется
   только если менеджер вручную задаст разные % предоплаты весов/фундамента. Не баг, задокументировано.
3. **W7 (счёт) — только в full (Спец/Договор поставки), НЕ в lite (КП).** `SPEC_SIGNED_INVOICE` не должен
   протекать в lite-рендер КП — там фразы про счёт быть не должно (эталон КП её не содержит).
4. **W6 (шеф-монтаж) — один источник scope в обоих путях.** `installation_scope` (Спец) и
   `state["is_shefmontazh"]` (КП) должны быть согласованы (одно выводимо из другого), иначе КП и
   договор разойдутся словом «монтаж»/«шеф-монтаж» на одном и том же сценарии.
5. **W10 (предлог) — расхождение с эталонами рама/шеф-монтаж намеренное.** Те эталоны пишут «за…»,
   наш дефолт — «от стоимости» (решение Антона). При финальной сверке с эталонами это НЕ регресс,
   не откатывать обратно на «за».
6. **Доставка и ручной ввод (edge, не блокер Стадии 1).** Если менеджер вручную поменяет postpay
   доставки, печатаемый % весов в L3 не будет отражать её долю. На дефолте — не проблема. Зафиксировать
   допущение («доставка = 100% при отгрузке») или закрыть её % от ручного ввода — можно позже.
