# Архитектура v2.1 — генерация Спецификаций к Договору подряда

Статус: утверждено. Дата: 2026-05-29.
Заменяет путь v1.0 «универсальный шаблон + clauses.yaml».

---

## 1. Решение и границы

v1.0 даёт структурно неверную спецификацию: подзаголовки секций вместо
сквозной нумерации, оплата без сумм и триггеров, сроки без отсылок на
конкретные пункты, обязательства не зависят от scope. Причина — попытка
обслужить все сценарии одним шаблоном.

v2.1 — **гибрид (A3)**: тело из общих jinja-includes + scope-зависимых
блоков внутри них. Платежи — список строк переменной длины со scope-default
скелетом и детерминированным форматтером. Строительные задания и контрольные
листы — внешняя библиотека `.docx`, склейка через `docxcompose`.

### В scope v2.1

- Спецификация к Договору подряда (сквозная нумерация п.1…N).
- Платёжный редактор переменной длины (scope-default + ручная правка).
- Бакеты позиций (3 шт), назначаются на странице Договора.
- Зимний период как вариант секции сроков (отдельные пункты, не аддон).
- Библиотека строительных заданий (фундаменты + основания под раму) и
  контрольных листов (2), склейка в приложения через docxcompose.
- ОРИОН: позиции, обязательства, приложения.
- Реквизиты сторон: два режима — AI-экстракт (A) и ручной ввод (B).

### Вне scope v2.1 — режем явно

- «Только поставка» = полный Договор поставки (10 разделов). Другой класс
  документа, отдельный трек.
- Модели П — фундаменты не продуманы.
- Изменение платёжной **модели** КП (UI-доработки КП — отдельный чат;
  сюда входит только то, что КП отдаёт на вход через snapshot).
- Косметика ТТХ — параллельный трек.

## 2. Структура документа (сквозная нумерация)

Без подзаголовков «Обязательства Подрядчика / Заказчика / Заключительные».
Секции в `clauses.yaml` — только ключ сортировки, в выводе не рисуются.

```
Шапка:  «Спецификация №{n} к Договору №{...} от {...}»
        «на поставку весов автомобильных и выполнение сопутствующих работ»
        г. Воронеж + дата, преамбула сторон.

1.   Таблица позиций + «Итого: {сумма} ({прописью}), в т.ч. НДС 22%.»
2.   Порядок оплаты: 2.1 … 2.N  (из платёжного редактора — §3)
3.   Срок поставки Весов и выполнения Работ (подпункты по scope; winter-вариант)
4.   [фундамент строит/курирует Подрядчик] Направление строительной бригады.
5.   Сдвиг сроков при неготовности Заказчика принять бригаду.
6…   [winter_concrete=true] Доплата 200к + фиксация в Акте + обогрев бетона.
…    Подрядчик готовит комплект документации (паспорт/РЭ).
…    Обязательства Заказчика (плоско по scope — §5).
…    Особые условия (доп. работы при строительстве, ОРИОН-оговорки).
M.   «…нарушающие условия п.п.{range}… применяются п.п.3.2-3.4 Договора.»
M+1. Адрес поставки.
M+2. Таблица ТТХ.
M+3. Комплект поставки (+  ОРИОН-комплект, если есть).

Подписи.
Приложения: №1 строит.задание [, №2 контрольный лист] [, ОРИОН №3/4].
```

Нумерация п.1…N вычисляется автонумерацией на сборке (как `obligations_range`).
Никаких section_number-констант в выводе.

## 3. Платежи — модель, scope-default, форматтер

**Почему E2 (редактор на стороне Договора):** КП не несёт бакеты/триггеры —
только проценты, и это решение не меняется. Предзаполнение — не сырыми
процентами КП (разные ментальные модели: КП мыслит «расщеплением по
позициям», Договор — «этапами по событиям»), а scope-default скелетом.
Проценты КП показываются как подсказка («В КП было: 30/40/30»).

### 3.1 Модель строки

```python
@dataclass
class PaymentLine:
    kind:     Literal["предоплата", "доплата"]
    basis:    Literal["percent", "fixed"]   # fixed — для рамы с круглыми суммами
    value:    float                          # 50.0 (%) или 1_000_000 (руб.)
    bucket:   Literal["equipment", "foundation", "install_verification"]
    trigger:  PaymentTrigger
    due:      int
    due_unit: Literal["банковских", "календарных"] = "календарных"
```

### 3.2 Триггеры (закрытый Enum, 6 значений)

| Ключ | Текст |
|---|---|
| `SPEC_SIGNED`     | подписания настоящей Спецификации |
| `FOUNDATION_ACT`  | подписания Акта выполненных работ по строительству фундамента |
| `SHIPMENT_READY`  | получения уведомления о готовности Весов к отгрузке |
| `BRIGADE_READY`   | уведомления о готовности принять монтажную бригаду на месте монтажа |
| `WORK_ACT`        | подписания Акта выполненных работ по настоящей Спецификации |
| `DELIVERED`       | поставки Весов Заказчику *(обычно календарные дни)* |

### 3.3 Scope-default скелет

Пресет — отклонён: фиксировал % и количество строк. **Скелет** фиксирует
только набор этапов (детерминирован scope; доказано по 8 заводским шаблонам).
Проценты и суммы — полностью редактируемы, строки добавляются/удаляются.

Правила построения дефолта по наличию бакетов в позициях:

```
equipment (всегда):
  + предоплата  bucket=equipment              trigger=SPEC_SIGNED
  + доплата     bucket=equipment              trigger=SHIPMENT_READY

foundation (contractor_full / contractor_with_materials / contractor_supervised):
  + доплата     bucket=foundation             trigger=FOUNDATION_ACT
  (аванс за фундамент часто слит в строку equipment/SPEC_SIGNED — менеджер правит)

install_verification (installation_scope != none):
  + предоплата  bucket=install_verification   trigger=BRIGADE_READY
  + доплата     bucket=install_verification   trigger=WORK_ACT
```

Дефолтные % — мягкие (50/50 на бакет). Кнопка «Заполнить по умолчанию»
строит скелет, менеджер сразу правит числа.

### 3.4 Расчёт суммы строки

- `basis=percent`: `round(value / 100 × bucket_total)`, где
  `bucket_total = Σ цен позиций с этим бакетом`.
- `basis=fixed`: `value` напрямую (бакет используется только для текстовой
  формулировки «за что»).

Контроль целостности: `Σ всех строк == Итого по спецификации`. UI показывает
дельту красным, если не сходится.

### 3.5 Текстовая формулировка бакета

```
equipment:
  подбирается по составу позиций:
  «Весов» | «Весов и фундамента» | «Весов, комплекта пандусов и рамы»
  | «Весов и Программно-аппаратного комплекса «ОРИОН»»

foundation:
  «фундамента Весов» | «работ по строительству фундамента»
  | «фундамента Весов и установки опор и кабель-трасс ПАК «ОРИОН»»

install_verification:
  «монтажных работ и поверки»
```

Шаблон строки (jinja):

```
2.{{i}}. {{kind|cap}} {{share_text}} {{bucket_text}} в размере
{{amount}} ({{amount_words}}) рублей, в т.ч. НДС 22%, в течение
{{due}} ({{due_words}}) {{due_unit}} дней с момента {{trigger_text}}.
```

- `share_text`: `«50% от стоимости»` если percent, пусто если fixed.
- `amount_words`: `num2words(lang="ru")` + пост-обработка склонений.
  Юнит-тест на 20+ контрольных сумм из заводских шаблонов.

### 3.6 UI — блок «Оплата» на странице Договора

`st.data_editor`, колонки:

| Тип | Основа | Значение | Бакет | Событие | Дней | Ед. |

Под таблицей: `«Σ строк: X / Итого: Y» + δ`.
Кнопки: «+ строка», «Заполнить по умолчанию».
Подсказка: «В КП было: …» (из snapshot, не загружается в строки автоматически).

## 4. Бакеты позиций

Три бакета. Доставка — внутри `equipment` (по всем шаблонам «Весы и
доставка» платятся вместе). Бакет — свойство позиции, назначается на странице
Договора в колонке таблицы позиций. КП не трогаем.

| Бакет | Позиции |
|---|---|
| `equipment` | весы, рама, пандусы, оборудование ОРИОН, доставка, бытовка, кастомные товарные позиции |
| `foundation` | фундамент, строительные работы, основание под раму (с моделью весов), опоры + кабель-трассы ОРИОН |
| `install_verification` | монтаж, монтаж ОРИОН, поверка, шеф-монтаж |

**Авто-маппинг по имени позиции** (дефолты, все редактируемы):

```
«Весы автомобильные*», «Рама*», «*пандус*», «Доставка*»,
«*ОРИОН*» (кроме монтажа/опор)      → equipment
«Фундамент*», «Строительство фундамента*», «Бетонное основание*»,
«Укладка*плит*», «*опор и кабель-трасс*»  → foundation
«Монтаж*», «Поверка*», «Шеф-монтаж*»     → install_verification
нераспознанное                             → equipment (дефолт)
```

**Попутный фикс «id вместо name»:** имя позиции берётся из поля `name`
при сборке таблицы Договора, не из `id`.

## 5. Обязательства Заказчика — оси scope

```
foundation_scope:   none | customer_builds | contractor_full
                  | contractor_with_materials | contractor_supervised | rama
base_type:          (только при rama) concrete | road_slabs | pag_slabs
installation_scope: none | full | shefmontazh
verification_scope: none | supplier | customer   ← независимая ось
has_orion:          bool
orion_poles_scope:  none | by_customer | by_contractor
winter_concrete:    bool
```

### 5.1 contractor_supervised — «курирование строительства»

Заказчик строит фундамент полностью своими силами и материалами. Подрядчик
выезжает курировать процесс. Использует **те же** строительные задания (§6),
что и `contractor_full`.

Отличия от `customer_builds`: Подрядчик присутствует на объекте → пункт
«направления специалиста для контроля» вместо «направления строительной
бригады»; платёж по бакету `foundation` может отсутствовать (Заказчик строит
сам — платёж только за курирование, если оно выделено отдельной позицией).

Клауза (черновик, на юр-ревью `clauses.yaml`):
> «Заказчик выполняет работы по строительству фундамента Весов самостоятельно
> по строительному заданию Подрядчика (Приложение №1). Подрядчик осуществляет
> контроль (курирование) процесса строительства.»

### 5.2 base_type под рамой — 3 разных текста обязательств

Базовая рамная клауза (общий каркас, всегда при `foundation_scope=rama`):
> «Заказчик для установки рамы и Весов предоставляет твёрдую (асфальт, бетон
> или дорожные плиты) горизонтальную площадку размером не менее 30×4 м.
> Допустимые перепады по высоте — не более 50 мм по всей длине площадки.
> Допустимый уклон не более 1:500.»

Клауза по `base_type` уточняет основание:

| base_type | Уточняющая клауза |
|---|---|
| `concrete` | Бетонное основание под раму (заливка). Обяз.: ровная площадка под бетонирование; доп. работы при скрытых конструкциях. |
| `road_slabs` | Укладка дорожных плит. Обяз.: основание под плиты, отвод воды. |
| `pag_slabs` | Укладка плит ПАГ. Обяз.: подготовка основания под ПАГ. |

Каждый — отдельная клауза в `clauses.yaml`, `applies_when` по `base_type`.

## 6. Тип фундамента, секции, строительные задания

### 6.0 Поток данных: КП → Договор

Тип фундамента влияет на **цену** → определяется на этапе КП. Может
**переопределяться** на этапе Договора (реальный кейс: в КП приямок, при
согласовании решили пандусный). Паттерн — как платежи и реквизиты:
КП-источник → Договор показывает унаследованное → менеджер правит.

**Поля в snapshot КП** (структурированные, не парсинг текста позиции):

```
foundation_execution:  "пандусный" | "приямок"
                     | "rama_concrete" | "rama_road_slabs" | "rama_pag_slabs" | null
foundation_sections:   2 | 3 | 4 | null   # авто из длины, переопределяемо
model_code:            "ВЕСТА-С-60-18"     # для текста позиции и шапки задания
```

**КП также формулирует наименование позиции с типом:**
«Фундамент железобетонный пандусный под весы ВЕСТА-С-60-18, 18м» /
«…в приямок…».

> ⚠️ **Связь с чатом доработок КП:** поля `foundation_execution`,
> `foundation_sections`, `model_code` должны добавиться в КП-конфигуратор
> и его snapshot. Без них страница Договора не прочитает тип фундамента,
> шаг 8 реализации встанет.

**Что показывается в UI Договора:** унаследованные значения из КП
отображаются как «В КП было: …» — менеджер видит исходное и может изменить
и тип, и секции перед генерацией. Расхождение не логируется, просто
генерируем по актуальному значению.

### 6.1 Библиотека (внешние .docx, вне кода)

Файлы — JPG-страницы, вставленные в Word. Без плейсхолдеров.
Шапка приложения (№, дата, «Утверждаю ___», строка с моделью весов)
**генерируется в коде** перед вставкой.

```
data/fundament/
  build_task/
    # Фундаменты (6): тип × секции
    пандусный_2скц.docx       пандусный_3скц.docx       пандусный_4скц.docx
    приямок_2скц.docx         приямок_3скц.docx         приямок_4скц.docx
    # Основания под раму
    rama_concrete_2скц.docx   rama_concrete_3скц.docx   rama_concrete_4скц.docx
    rama_road_slabs.docx      rama_pag_slabs.docx
  control_sheet/
    пандусный.docx            приямок.docx
```

Итого: 11 файлов заданий + 2 контрольных листа = **13 файлов библиотеки**.

Примечания:
- Пандусный / приямок — общие для С, Ф, СЛ, ФЛ (один чертёж на тип).
  Приямок — общий для всех семейств без исключений.
- `rama_concrete` — секционный (основание повторяет длину весов);
  `rama_road_slabs`, `rama_pag_slabs` — одиночные (секции не применимы).
- Наименование позиции основания под раму включает модель весов:
  «Бетонное основание под раму для весов ВЕСТА-С-60-18».

### 6.2 Выбор файла задания

```python
# filename logic
if base_type in ("road_slabs", "pag_slabs"):
    filename = f"rama_{base_type}.docx"
else:
    filename = f"{execution}_{sections}скц.docx"
    # execution: "пандусный" | "приямок" | "rama_concrete"
```

**Lookup длина → секции** (захардкожен, канон фундамента, не платформы):

```python
LENGTH_TO_SECTIONS = {
    7: 2,  9: 2, 12: 2,
    14: 3, 15: 3, 16: 3, 18: 3,
    20: 4, 22: 4, 24: 4,
}
```

Длина парсится из `model_code`: «ВЕСТА-С-60-**18**» → 18 → 3 секции.
Менеджер видит вычисленное значение в UI и может переопределить.

### 6.3 Контрольный лист

2 варианта: `пандусный` / `приямок` (от секций не зависит).

- `customer_builds`: контрольный лист **включается** (Заказчик строит сам,
  нужны замеры перед выездом бригады).
- `contractor_supervised`: контрольный лист **включается** (Заказчик строит
  по нашему СЗ, замеры нужны).
- Прочие scope: не включается.

### 6.4 Склейка (docxcompose)

```
тело_спецификации.docx
  + Прил.№1: build_task/{filename}        ← шапка с моделью весов — от кода
  [+ Прил.№2: control_sheet/{тип}.docx]  ← customer_builds или supervised
  [+ Прил.№3: схема размещения ОРИОН]    ← has_orion
  [+ Прил.№4: конфигурация ПК для ОРИОН] ← has_orion
```

Нумерация приложений вычисляется по факту наличия блоков.
Зависимость: `docxcompose` (`pip install docxcompose`). `python-docx` сам по
себе не склеивает документы без потери стилей/разрывов.

## 7. Общие блоки → jinja-includes

```
src/contracts/includes/
  _header.j2            шапка + преамбула сторон (читает реквизиты §8)
  _table_positions.j2   таблица позиций + итого прописью
  _payment.j2           цикл по PaymentLine (§3.5)
  _terms.j2             сроки (поставка / фундамент / монтаж) + winter-вариант
  _obligations.j2       цикл по clauses (плоская нумерация)
  _ttx.j2               ТТХ-таблица (из renderer, как в v1.0)
  _kit.j2               комплект поставки (+ ОРИОН-комплект)
  _signatures.j2        подписи сторон
```

Базовый `spec_body.j2` инклудит блоки по порядку §2. Scope-ветвление —
внутри `_terms.j2` и `_obligations.j2`. Отдельных файлов тела на каждый
scope не создаём.

## 8. Реквизиты сторон — два режима

AI-экстрактор в проде = единая точка отказа. Менеджер обязан мочь
сгенерить договор, когда AI недоступен или файл не загружен.

```
Mode A (дефолт): AI-экстракт из файла контрагента (DeepSeek Flash).
Mode B (fallback): ручная форма.
```

**Структура реквизитов** (общая для обоих режимов):

```python
@dataclass
class Counterparty:
    name_full:        str   # ООО «Агрофирма «Промышленная»
    name_short:       str   # ООО «Агрофирма «Промышленная»
    role:             str   # «Заказчик»
    signatory_fio:    str   # Голодников Виктор Петрович
    signatory_post:   str   # Директор
    signatory_basis:  str   # Устав
    inn:              str
    kpp:              str
    ogrn:             str
    legal_address:    str
    postal_address:   str
    bank_name:        str
    rs:               str
    ks:               str
    bik:              str
    phone:            str
    email:            str
```

Реквизиты Подрядчика (ООО «ТПК «Тензосила») — константа в коде.

**UI:** переключатель «AI / Вручную». В Mode B — форма с мягкой валидацией
(длина ИНН, КПП, ОГРН; контрольная цифра — предупреждение, не блокировка).
Mode B сохраняет введённое в snapshot Договора — при повторной генерации
заполнять не нужно.

## 9. Зимний период

При `winter_concrete=true`:

- Из секции «Сроки» **убирается** оговорка «работы при ср.сут. темп. >+5°С».
- **Добавляются** отдельные пункты (после п.5, до обязательств Заказчика):
  1. Доплата 200 000 ₽ в т.ч. НДС 22% за зимние работы; подтверждение
     метеоданными (gismeteo.ru и т.д.).
  2. Увеличенная стоимость оплачивается на условиях п.2.2; факт выполнения
     зимних работ фиксируется в Акте по фундаменту.
  3. Срок набора прочности бетона увеличивается; обогрев бетона — за
     отдельную плату по соглашению.

Это **вариант секции**, не аддон-клауза. НДС всегда 22% (заводской косяк
с «20%» в одном из шаблонов — игнорируем).
