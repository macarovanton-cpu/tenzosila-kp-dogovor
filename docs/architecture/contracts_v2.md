## Зачем v2

Текущая (v1) реализация модуля договоров стоит на двух гипотезах, которые не выдерживают столкновения с реальным разнообразием конфигураций:

1. **Спецификация = фиксированный набор позиций.** Шаблон `spec_foundation_install.docx` содержит жёсткую структуру под одну конфигурацию (фундамент + монтаж + поверка). Любое отклонение требует нового шаблона.
2. **Текст договора = константа.** Формулировки разделов «Обязательства поставщика», «Обязательства заказчика», «Порядок сдачи-приёмки» зашиты в .docx-шаблон. Любая вариация (есть поверка / нет, есть фундамент / нет, делаем монтаж / поставка только) требует или нового шаблона, или ручной правки после генерации.

При текущем темпе появления новых сочетаний (5–6 уже сейчас, дальше больше — бытовки, ИРИОН, видеонаблюдение, ограждения, кастомные опции) число шаблонов растёт комбинаторно. Это тупик.

v2 переносит вариативность из шаблонов в данные.

---

## Принципы

**Принцип 1. Структура договора стабильна, вариативность — в позициях и пунктах.**  
Разделы договора (преамбула, предмет, цена, оплата, поставка, монтаж, гарантии, ответственность, реквизиты) одинаковы во всех конфигурациях. Различаются:
- список позиций в спецификации,
- набор и формулировки пунктов внутри разделов «Обязательства сторон» и «Порядок сдачи-приёмки».

**Принцип 2. Один шаблон договора, один шаблон спецификации.**  
Никакой логики «если такая конфигурация — взять такой шаблон». Шаблоны — это скелет с jinja-циклами. Всё содержательное приходит из данных.

**Принцип 3. Данные — единый источник правды.**  
Позиции спецификации и применимые пункты договора рассчитываются из объекта сделки (snapshot КП в Supabase + ручные поля договора). При генерации эти данные разворачиваются в DOCX. Тот же объект сделки — единственный источник для будущего тендерного модуля и интеграции с Битриксом.

## Модель данных: позиции спецификации

Позиция — это элемент массива `specification.items`. Структура одной позиции:

```python
{
    "id": "weights" | "delivery" | "installation" | "verification" | 
          "foundation" | "fence" | "bytovka" | "orion" | "custom_<uuid>",
    "name": str,           # отображаемое название
    "unit": str,           # ед. изм. ("шт", "компл", "м", "усл.ед" и т.д.)
    "quantity": float,
    "price_per_unit": float,  # без НДС
    "total": float,        # quantity * price_per_unit
    "payment_group": int | None,  # для split_by_items оплаты
    "is_custom": bool,     # True для произвольных позиций
    "source": "preset" | "custom",  # происхождение
    "metadata": dict       # доп. поля для clauses (см. ниже)
}
```

Поле `metadata` — это то, по чему правила применения clauses определяют, что именно поставщик берёт на себя. Например:

```python
{
    "id": "installation",
    "metadata": {
        "scope": "rama" | "fundament" | "shefmontazh"
    }
}
```

Это позволяет различать «монтаж рамы» и «монтаж на фундаменте», и применять под них разные текстовые пункты в договоре.

**Кастомные позиции** добавляются менеджером через UI кнопкой «+ Добавить позицию». Менеджер вводит `name`, `unit`, `quantity`, `price_per_unit`. У такой позиции `id = "custom_<uuid>"`, `is_custom = True`, `metadata = {}`. На clauses кастомные позиции не влияют — они только увеличивают сумму договора и появляются строкой в спецификации.

**Источник позиций:**  
- Преднастроенные позиции собираются из snapshot КП через расширенный `from_kp.build_specification_from_kp_snapshot()`.
- Менеджер может на странице Договор добавлять, удалять, редактировать любые позиции (включая преднастроенные).
- Список преднастроенных позиций и их metadata — в `data/spec_presets.yaml`.

## Модель данных: clauses library

Библиотека текстовых пунктов договора живёт в `data/clauses.yaml`. Один пункт — одна запись.

```yaml
- id: poverka_supplier
  section: obyazatelstva_postavshchika
  order: 30                           # порядок внутри секции
  applies_when: "has_item('verification')"
  text: |
    Поставщик осуществляет первичную поверку Товара силами 
    аккредитованной организации с оформлением Свидетельства о поверке.
  related_to: ["poverka"]             # для будущих перекрёстных ссылок

- id: poverka_customer
  section: obyazatelstva_zakazchika
  order: 40
  applies_when: "not has_item('verification')"
  text: |
    Заказчик в течение 10 (десяти) рабочих дней с момента подписания 
    Акта приёма-передачи обязуется самостоятельно организовать 
    первичную поверку Товара силами аккредитованной организации.
  related_to: ["poverka"]

- id: fundament_supplier
  section: obyazatelstva_postavshchika
  order: 20
  applies_when: "has_item('foundation')"
  text: |
    Поставщик выполняет работы по устройству фундамента под Товар 
    в соответствии с проектной документацией Поставщика.

- id: fundament_customer
  section: obyazatelstva_zakazchika
  order: 20
  applies_when: "not has_item('foundation')"
  text: |
    Заказчик до прибытия Товара на объект обеспечивает готовый 
    фундамент в соответствии с проектной документацией Поставщика, 
    переданной Заказчику в составе технической документации.
```

**Поля записи:**
- `id` — уникальный, snake_case. Используется в тестах и при ссылках.
- `section` — раздел договора, в который пункт попадает. Перечень секций фиксирован (см. ниже).
- `order` — целое число, определяет позицию пункта внутри секции (сортировка по возрастанию).
- `applies_when` — условие применения, выражение на ограниченном DSL (см. ниже).
- `text` — текст пункта. Поддерживает плейсхолдеры `{{ ... }}` (например, реквизиты, суммы).
- `related_to` — теги для группировки и перекрёстных ссылок (опционально, для будущего использования).

**Фиксированный перечень секций:**
- `predmet` — предмет договора
- `tsena_i_poryadok_oplaty` — цена и порядок оплаты
- `poryadok_postavki` — порядок поставки
- `obyazatelstva_postavshchika` — обязательства поставщика
- `obyazatelstva_zakazchika` — обязательства заказчика
- `sdacha_priemka` — порядок сдачи-приёмки
- `garantii` — гарантии
- `otvetstvennost` — ответственность сторон
- `forsmazhor` — форс-мажор
- `zaklyuchitelnye` — заключительные положения

Добавление новой секции — изменение архитектуры, делается осознанно. Большая часть будущих добавлений — это новые clauses в существующих секциях.

## DSL условий применения

Условие в `applies_when` — это Python-выражение, выполняемое в ограниченном контексте через `eval` с whitelisted globals. Доступные функции:

| Функция | Семантика |
|---|---|
| `has_item(id)` | True, если в `specification.items` есть позиция с этим `id` |
| `has_metadata(id, key, value)` | True, если у позиции `id` поле `metadata[key] == value` |
| `has_any(*ids)` | True, если есть хотя бы одна позиция из перечисленных |
| `count_items(id)` | Количество позиций с этим `id` |
| `total_amount()` | Общая сумма спецификации (без НДС) |
| `flag(name)` | True, если установлен ручной флаг договора (UI-чекбокс) |

**Правила:**
- Условие должно быть **атомарным**: проверять одну вещь. Сложные комбинации — это сигнал, что нужно разнести на два clause или ввести новый флаг.
- Запрещены: операции с файлами, импорты, обращения к session_state напрямую.
- Если `applies_when` пустое или `"true"` — пункт применяется всегда.

**Пример сложного, но допустимого условия:**
```yaml
applies_when: "has_item('installation') and has_metadata('installation', 'scope', 'fundament')"
```

**Пример недопустимого условия (рефакторить):**
```yaml
applies_when: "(has_item('foundation') or has_item('installation')) and not flag('skip_poverka') and total_amount() > 1000000"
```
→ разделить на несколько clauses, либо ввести отдельный вычисляемый флаг.

## Сборка договора

Функция `build_contract_clauses(deal: dict) -> dict[str, list[Clause]]` принимает объект сделки и возвращает применимые пункты, сгруппированные по секциям:

```python
{
    "predmet": [Clause(id="predmet_main", text="..."), ...],
    "obyazatelstva_postavshchika": [
        Clause(id="postavka", text="...", auto_number="4.1"),
        Clause(id="fundament_supplier", text="...", auto_number="4.2"),
        Clause(id="poverka_supplier", text="...", auto_number="4.3"),
    ],
    ...
}
```

Нумерация (`auto_number`) считается на лету в момент сборки. В шаблоне `contract.docx` секции рендерятся jinja-циклом:

```jinja
{% for section_id, clauses in sections.items() %}
  {{ section_titles[section_id] }}
  {% for c in clauses %}
    {{ c.auto_number }}. {{ c.text }}
  {% endfor %}
{% endfor %}
```

Шаблон спецификации `specification.docx` рендерится одной таблицей с jinja-циклом по `specification.items`.

## Перекрёстные ссылки

В v2 (MVP) перекрёстные ссылки **не реализуются**. Если в тексте clause нужна ссылка на другой пункт, она временно пишется как «согласно соответствующего пункта раздела N» (без явного номера) или вшивается жёстко (с пониманием, что при выпадении ссылочного clause формулировка станет некорректной).

Перекрёстные ссылки через символические идентификаторы (`{{ ref('poverka_supplier') }}` → авторезолв в номер пункта) — это **отложенная фича**. Внедряется только после стабильной работы базовой механики.

Тег `related_to` уже сейчас есть в схеме clause — это задел на будущее.

## Юридическая корректность

Динамическая сборка договора создаёт риск собрать невалидную комбинацию пунктов (например, обязательство одной стороны без встречной нормы у другой). Контроль реализуется через **юридические инварианты** — pytest-тесты вида:

```python
def test_poverka_invariant():
    """Если упомянут поверка_supplier, должен быть упомянут срок_поверки."""
    deal = build_deal_with(items=["weights", "verification"])
    clauses = build_contract_clauses(deal)
    ids = collect_ids(clauses)
    
    if "poverka_supplier" in ids:
        assert "poverka_term" in ids, "поверка без срока недопустима"
```

Перечень инвариантов формируется по результатам анализа исходных 5–6 шаблонов на Шаге 4 (см. план миграции).

**Дополнительный контроль:** перед production-использованием каждой новой clause-комбинации — однократный ручной юридический ревью сгенерированного договора. Это не масштабируется на тысячи комбинаций, но Тензосиле столько и не нужно — реальный рабочий перечень это 10–20 типовых сочетаний.

## Границы применимости

v2 хорошо работает в случаях:
- стандартный договор Тензосилы со стандартным набором обязательств;
- любые сочетания типовых опций (поверка, фундамент, монтаж, ограждение, бытовка, ИРИОН и т.д.);
- произвольные кастомные позиции в спецификации с собственным наименованием.

v2 **не покрывает**:
- договоры по шаблону заказчика (LUKOIL-форма, РЖД-форма и т.п.) — это отдельный задача, решается в тендерном модуле через мапинг данных сделки в чужой шаблон;
- одиночные нетиповые условия, не вписывающиеся ни в одну существующую clause-категорию (например, специфические требования по приёмочным испытаниям для конкретного заказчика) — менеджер дорабатывает руками после генерации, либо такой clause добавляется в библиотеку, если случаи повторяются.

## Хранение

`data/clauses.yaml` и `data/spec_presets.yaml` — в репозитории, версионируются через git. Изменения проходят обычное code review (а также юридический ревью при изменении формулировок).

Объект сделки (с применёнными позициями и применёнными clauses) сохраняется в Supabase в таблицу `contracts` JSONB-полем `данные`, включая список id применённых clauses — для аудита и для возможности воспроизвести договор позже.

Сами тексты clauses в Supabase не дублируются. Для аудита «какой именно текст был сгенерирован для договора X в дату Y» используется git-история `clauses.yaml` (или фиксируется git-commit-hash в записи договора).

Полный пошаговый план — в архитектурном чате и в `docs/STATUS.md`. Краткие вехи:

## Открытые вопросы

- **Реквизиты в текстах clauses.** Шаблоны v1 содержат много инлайн-формулировок типа «в течение 10 рабочих дней». Часть таких сроков завязана на конфигурацию (срок поверки зависит от того, делаем мы или заказчик). Нужно ли вводить параметры в clauses (`text` с jinja-плейсхолдерами + поле `params` в записи) или достаточно держать варианты как разные clauses? **Решение:** начать с разных clauses (проще), вводить параметризацию только когда вариантов одного пункта станет >3.

- **Многоязычность.** Сейчас не нужна. Если в будущем понадобятся договоры на английском (ЕАЭС, экспорт), добавляется поле `text_en` в clause. В v2 это **out of scope**.

- **Версионирование clauses.** Если юрист изменил формулировку clause, нужно ли в исторических договорах сохранить «как было», или достаточно git-истории? **Решение:** достаточно git-истории + commit-hash в записи договора. Версионирование внутри `clauses.yaml` не вводим.
