# Сценарии проверки качества генерации КП / спецификаций / договоров

Назначение: систематическая ручная сверка генерации приложения против
эталонных `.md` в корне проекта. Используется в отдельном чате для приёмки
перед деплоем.

**Метод одного раунда:**
1. Взять реквизиты из карточки сценария → вставить в поле «Распознать».
2. **Сразу проверить распознавание** (ИНН/КПП/ОГРН не слиплись, банк не
   разорван, телефон показан).
3. Сконфигурировать КП по параметрам сценария, сгенерировать КП + договор
   + спецификацию.
4. Скинуть 3 docx ассистенту → он парсит и сверяет с указанным эталоном по
   чеклисту: механику флагует сам, смысловое (не тот пункт обязательств)
   выносит на решение.

**Что считать ожидаемым отличием (НЕ баг):**
- НДС в приложении **22%**, в части эталонов 20% (эталоны 2024-2025 гг.) —
  это правильное поведение приложения для 2026 г.
- Суммы, реквизиты, адреса, номера договоров, конкретные сроки — специфичны
  для сделки, различаются всегда.
- Приложение не воспроизводит эталон дословно. Сверяем **набор пунктов
  обязательств под scope**, а не побайтовое совпадение.

**Реквизиты:** во всех карточках ИНН/ОГРН с валидными контрольными суммами,
КПП/счета верной длины, БИК+корсчёт — реальная публичная пара Сбербанка.

## Зафиксированные баги (сценарии 1-2, для будущего фронта фиксов)

### БАГ-1 (P0, доменный) — неверные клаузы для «рама+пандусы»
Сценарий 1. Рама+пандусы (фундамент не строится) получил клаузы
`customer_builds_foundation` (строительное задание + контрольный лист фото),
вместо клаузы про твёрдую площадку 30×4м. Эталон `Автовесы_рама_монтаж` п.6.
Обратная ветка (подрядчик строит, сценарий 2) — корректна, значит проблема
локальна к scope «рама/пандусы без фундамента». Фикс — Opus (scope→clauses,
edge-кейсы, не сломать соседние ветки).

### БАГ-2 (P1, системный, 2/2) — кавычки Заказчика прямые вместо ёлочек
`ООО "..."` вместо `ООО «...»` в общем договоре+спецификации. Фикс ea24b50 был
на шаблонах договора поставки, до общего флоу не дошёл. Сценарий 8 (поставка) —
обратная проверка, там должно быть корректно.

### БАГ-3 (P2, системный, 2/2) — задвоенная ёлочка Подрядчика
`ООО «ТПК «Тензосила»»` (`»»`) в связном тексте спецификации; в договоре
одинарная. Непоследовательный рендер вложенного названия.

### БАГ-4 (P1, системный, 2/2) — дублирование в преамбуле договора
`...именуемые совместно «Стороны», именуемые совместно «Стороны», заключили...`
Только в теле договора, воспроизводится идентично. Баг склейки шаблона.

## Подтверждено корректным (контроль регресса)
- Клаузы «подрядчик строит фундамент» (площадка под монолит) — верны.
- Телефон: форматы без префикса+4знач, «8»+4знач — распознаются, в реквизитах.
- ИНН/КПП/ОГРН не слипаются. Суммы бьются КП↔спец↔договор. P1-5 не ложнит.

## Порядок и рекомендация
Проверять по порядку 3 → 4 → 5 → 6 → 7 → 8 (1-2 уже сделаны). Приоритет по
ценности ветвления: **4 (шеф-монтаж)** и **7 (ОРИОН+фундамент)** — самые
насыщенные уникальными клаузами, дают больше всего сигнала. 5, 6 могут
вскрыть непокрытые scope (зимний режим, материал заказчика) — если фич нет в
приложении, это не баг, а вопрос охвата MVP.

Все баги копить до **консолидированного фронта фиксов** после сверки, не
чинить по одному. БАГ-1 — отдельный Opus-фронт. БАГ-2/3/4 — вероятно один
sonnet-фронт (общий шаблон договора), но сначала найти код общего флоу
(не supply_contract).
