# Памятка по работе с Claude Code в GitHub Codespaces

Полная инструкция для ежедневной работы. Открывай этот файл когда что-то забыл.

---

## Что у меня настроено

- **Codespaces** — облачная Linux-машина в браузере, открывается с github.com
- **Claude Code** в Codespace — авторизован через `CLAUDE_CODE_OAUTH_TOKEN` (живёт год, до апреля 2027)
- **Streamlit-конфигуратор** — запускается в Codespace, доступен через forward порта 8501
- **Биллинг** — идёт через Pro подписку Claude (отдельных денег за API не плачу)
- **Лимит Codespaces** — 60 часов работы 2-ядерной VM в месяц на бесплатном GitHub Free

## Ключевые файлы проекта (запомнить)

В корне проекта есть **два файла-навигатора**, которые управляют контекстом Claude Code:

### `CLAUDE.md` — правила работы

Лежит **в корне проекта**, не в `docs/`. Claude Code автоматически читает его при старте каждой сессии. В нём:
- Описание проекта (что делаем, для кого)
- Стек технологий
- Структура папок
- Архитектурные решения (классы цен A/B/C, плоский session_state и т.п.)
- Правила работы (что коммитить, чего не делать)
- Правила git (см. ниже)

**Когда обновлять:** только при структурных изменениях (новая зависимость, новая папка, новое правило). Не при каждой мелочи.

### `docs/STATUS.md` — текущая фаза

Единственный источник правды о том, **где мы сейчас**. Там:
- Текущая фаза проекта
- Что закрыто, что в работе, что в backlog
- Открытые вопросы

**Когда обновлять:** при закрытии каждого крупного шага (фазы или подфазы).

### Команды управления статусом

В чате со мной (не в Claude Code, а здесь в Claude.ai):

- **«статус»** или **«покажи статус»** — короткая сводка где мы (нужен приложенный STATUS.md)
- **«обнови статус»** или **«обнови STATUS»** — выдаю полную обновлённую версию файла для коммита
- **«продолжаем»** или **«начинаем»** — в начале новой сессии, чтобы восстановить контекст из STATUS.md

## Ежедневный workflow

### Начало рабочего дня

1. Открой Firefox, перейди: **https://github.com/codespaces**
2. В списке найди существующий Codespace для `tenzosila-kp-dogovor` (он на паузе)
3. Кликни по нему — откроется VS Code в браузере
4. Подожди 30-40 секунд пока VM просыпается
5. Готов к работе

**Если Codespace удалён или его нет:**
- На странице репозитория `tenzosila-kp-dogovor` зелёная кнопка **Code** → вкладка **Codespaces** → **Create codespace on main**
- Жди 3-5 минут пока соберётся (это бывает только при первом создании)

### Конец рабочего дня

- Просто закрой вкладку браузера. Codespace через 30 минут уйдёт на паузу автоматически
- Все файлы сохраняются в Codespace до следующего раза
- **НЕ нужно** ничего специально останавливать

### Перед закрытием — обязательно закоммить

Если делал изменения — отправь их в GitHub:

```bash
git add .
git commit -m "описание что сделал"
git push
```

Иначе при следующем запуске или если Codespace сломается — потеряешь работу.

Дома потом можешь подтянуть:
```powershell
cd D:\Projects\Tenzosila_KP_Dogovor
git pull
```

## Структура окна Codespace (что где)

```
┌─────────────────────────────────────────────────────────────┐
│ Меню (File, Edit, View...)                                  │
├──────────┬──────────────────────────────────────────────────┤
│          │                                                  │
│ Файлы    │  Редактор кода                                   │

│          │  PROBLEMS | OUTPUT | TERMINAL | PORTS  ← вкладки │

│          │  Сюда вводятся команды                           │
```

**Как открыть терминал:**
- Горячие клавиши: **Ctrl + ~** (тильда, слева от единицы)
- Или меню: **Terminal → New Terminal**

**Как открыть несколько терминалов** (полезно когда Streamlit и Claude Code одновременно):
- В правой части панели терминалов кнопка **+** (плюс)
- Каждый новый терминал — отдельная вкладка справа от названия типа `1: bash`, `2: bash`

**Как переключаться между терминалами:**
- Кликом на название (`1: bash`, `2: bash`) в правой части
- Или горячая клавиша **Ctrl + Page Up / Page Down**

## Запуск конфигуратора (Streamlit)

### Стандартный запуск

В свежем терминале:

```bash
streamlit run src/app.py
```

Терминал покажет:
```
You can now view your Streamlit app in your browser.
Local URL: http://localhost:8501
```

**Не закрывай этот терминал!** Streamlit живёт пока он открыт.

### Открыть UI в браузере

1. Внизу окна Codespace есть вкладка **PORTS** (рядом с TERMINAL)
2. В списке должна быть строка с портом **8501**
3. В колонке **Forwarded Address** — длинный URL вида `https://имя-codespace-8501.app.github.dev`
4. Наведи мышкой на этот URL → появятся иконки → кликни **глобус** (Open in Browser)
5. Откроется новая вкладка Firefox с приложением

### Если порт не отображается

- В панели **PORTS** нажми **Forward a Port**
- Введи `8501` → Enter
- Правый клик на строке → **Port Visibility** → **Public** (если приложение публично нужно)

### Остановка Streamlit

В терминале где он крутится — нажми **Ctrl+C**. Появится приглашение `$`.

## Работа с Claude Code

### Запуск

В отдельном терминале (не там где Streamlit):

```bash
claude
```

После короткой загрузки появится приглашение `>`. В него вводишь промты.

### Базовые команды Claude Code

Все команды начинаются со **слэша** `/` и вводятся прямо в приглашение `>`.

| Команда | Что делает |
|---|---|
| `/help` | Полный список команд |
| `/model` | Меню выбора модели (см. ниже) |
| `/effort` | Меню/слайдер выбора уровня обдумывания (см. ниже) |
| `/login` | Перелогиниться (обычно не нужно — токен живёт год) |
| `/status` | Показывает текущую модель и метод авторизации |
| `/clear` | Очистить текущую сессию (история промптов сбрасывается) |
| `/cost` | Показать сколько запросов и токенов ушло в текущей сессии |
| `/permissions` | Управление разрешениями (что Claude может делать без подтверждения) |
| `/config` | Настройки Claude Code |
| `/bug` | Отправить багрепорт в Anthropic |

### Выбор модели

Главная команда. Введи в приглашении:

```
/model
```

Появится меню вида:

```
Select a model:
❯ 1. Claude Opus 4.7 (default)
  2. Claude Sonnet 4.6
  3. Claude Haiku 4.5
  4. Claude Opus 4.6
```

**Какую выбирать:**

- **Opus 4.7** — для сложных задач: архитектурные решения, многофайловые рефакторинги, нетривиальная логика. Дорогая по подписке. Используй редко.
- **Sonnet 4.6** — рабочая лошадка. Обычные правки, написание кода, тесты. **Дефолт для большинства задач.**
- **Haiku 4.5** — мелкие правки, простые рефакторинги. Самая быстрая и дешёвая.
- **Opus 4.6** — почти как 4.7 но с более стабильной авторизацией. Если 4.7 показывает странные ошибки авторизации, используй её.

**Важно про Opus 4.7 1M:** если в `/model` есть пункт **"Opus 4.7 1M"** (с миллионным контекстом) — НЕ выбирай. С ней OAuth-токены работают нестабильно. Используй обычный Opus 4.7 (200K контекст) или Sonnet.

После выбора в меню — модель меняется до следующего `/model`.

### Режимы работы (что Claude делает с правками)

Снизу в интерфейсе Claude Code обычно показано три режима:

| Режим | Что значит | Когда использовать |
|---|---|---|
| **Plan mode** | Сначала Claude показывает план, потом ты подтверждаешь | Архитектурные задачи, сложные изменения |
| **Accept edits** | Claude делает правку, потом подтверждаешь применение | Стандартный режим для кода |
| **Auto-accept** | Все правки применяются автоматически | Только для очень простых рутинных задач |

**Переключение режимов:**

- Внутри Claude Code: нажми **Shift + Tab** для переключения между режимами
- Текущий режим виден внизу окна

**Дефолт:** оставь **Accept edits**. Это безопасный стандарт.

### Effort — глубина обдумывания задачи

Effort — это **реальный параметр Claude Code**, отдельный от модели. Он управляет тем, сколько "thinking-токенов" модель тратит на обдумывание перед ответом. Чем выше effort — тем глубже рассуждение, тем выше качество на сложных задачах, но и больше расход подписки.

**Effort работает только на Opus 4.7, Opus 4.6 и Sonnet 4.6.** На Haiku его нет.

### Уровни effort

| Уровень | Что значит | Когда использовать |
|---|---|---|
| **low** | Минимум обдумывания, быстро | Переименование, простые правки, batch-операции, быстрые вопросы |
| **medium** | Средне, дефолт Opus 4.6 | Обычное кодирование, написание функций, небольшие рефакторинги |
| **high** | Глубоко, дефолт Opus 4.7 | Сложная отладка, многофайловые рефакторинги, ревью кода, архитектурные вопросы |
| **max** | Максимум | Очень сложные баги, проектирование с нуля, критическая логика. В 2-10 раз дороже high по токенам |
| **auto** | Сбросить на дефолт модели | Когда хочешь вернуться к стандарту |

### Как ставить effort — четыре способа

**Способ 1. Команда `/effort` в приглашении (главный):**

```
/effort
```

— открывает интерактивный слайдер. Стрелками влево/вправо выбираешь уровень.

```
/effort low
/effort medium
/effort high
/effort max
/effort auto
```

— ставит уровень напрямую без слайдера.

**Способ 2. Через `/model`:**

Открой `/model`. После выбора модели — стрелками **влево/вправо** регулируй слайдер effort прямо в этом меню.

**Способ 3. При запуске Claude Code:**

```bash
claude --effort high
```

— стартует сессию сразу с нужным уровнем.

**Способ 4. Через переменную окружения (для постоянного дефолта):**

```bash
export CLAUDE_CODE_EFFORT_LEVEL=medium
claude
```

Эта переменная имеет **приоритет** над всеми другими способами в этой сессии.

### Где видно текущий effort

В Claude Code рядом с логотипом и спиннером показывается надпись типа **"with low effort"** или **"with high effort"**. Можно не открывая `/model` понять, какой уровень активен.

### Дополнительно — слова-триггеры в самом промте

Помимо `/effort` есть **слова в промте**, которые действуют только на этот один запрос:

- `think` — небольшой подъём
- `think hard` — средний
- `think harder` / `ultrathink` — максимальный

Пример:

```
> ultrathink почему тесты в test_payment_renderer падают только в CI
```

Это не меняет глобальный `/effort`, но даёт Claude больше "пространства" подумать конкретно над этим запросом.

### Effort и модель — разные вещи

| Параметр | Что определяет |
|---|---|
| **Модель** (`/model`) | Какой интеллект работает (Opus 4.7 / Sonnet 4.6 / Haiku 4.5) |
| **Effort** (`/effort`) | Сколько он думает перед ответом |
| **Mode** (Shift+Tab) | Как обращаться с правками (Plan / Accept edits / Auto-accept) |

Эти три рычага независимы. Можешь взять Sonnet с max effort (быстрая модель которая думает долго) — иногда это лучшая комбинация цены и качества.

### Что писать в Claude Code (промты)

Шапка для логирования и осознанности:

```
**Модель:** sonnet
**Effort:** medium
**Mode:** accept edits
**Время работы:** ~10 мин
**Сессия:** новая

[сам промт коротко, что нужно сделать]
```

**Перед отправкой промта установи параметры:**

1. `/model` → выбрать модель
2. `/effort <уровень>` → выбрать глубину
3. **Shift+Tab** → выбрать режим

Это требует осознанности — но именно поэтому шапка в промте полезна.

### Рекомендуемые комбинации под типичные задачи

| Задача | Модель | Effort | Mode |
|---|---|---|---|
| Простая правка в одном файле, переименование | Haiku | — (нет) | auto-accept |
| Обычный код, написание функции | Sonnet | medium | accept edits |
| Многофайловое изменение, нетривиальная логика | Sonnet или Opus 4.6 | high | accept edits |
| Архитектура, проектирование с нуля | Opus 4.7 | high или max | plan |
| Очень сложный баг | Opus 4.7 | max | plan |
| Тяжёлый ревью существующего кода | Opus 4.7 | high | plan |

### Безопасный дефолт

Если сомневаешься — **Opus 4.7 + high + plan**. Это разумный максимум для серьёзной задачи без перебора по токенам.

Для рутины — **Sonnet + medium + accept edits**.

### Выход из Claude Code

В приглашении `>` введи:
```
/exit
```

Или просто закрой терминал — все правки в файлах остаются.

## Работа Claude Code с Git (важно)

### Правила, которые Code знает из CLAUDE.md

Эти правила прописаны в `CLAUDE.md` проекта — Code их соблюдает автоматически:

- **Code сам делает коммиты** после каждого закрытого логического блока
- **Сообщения коммитов** — Conventional Commits на русском: `feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`
- **Один коммит = один шаг** из промта или STATUS.md
- **Code НЕ делает `git push`** — пуш в облако только по моему явному запросу
- **Code НЕ создаёт новых веток** — работает только в `main`
- **Перед коммитом** Code проверяет `pytest tests/` — если красное, не коммитит

### Что я делаю руками после работы Code

1. **Проверить что закоммичено:**
```bash
git log --oneline -5
```
Должны быть свежие коммиты от Code, осмысленные имена.

2. **Проверить что нет незакоммиченных правок:**
```bash
git status
```
Должно быть `working tree clean` или только то, что Code намеренно оставил.

3. **Запустить тесты:**
```bash
pytest -v
```
Все зелёные — отлично. Если что-то красное — разбираться через Code.

4. **Запустить приложение и проверить руками:**
```bash
streamlit run src/app.py
```
Открыть UI, прощёлкать сценарий который правился.

5. **Запушить в GitHub:**
```bash
git push
```

### Тег-точка отката перед рискованной работой

Перед началом большой/рискованной работы (рефакторинг, новая фаза) ставь тег — это страховка, к которой можно вернуться одной командой:

```bash
git tag v0.X-описание
git push --tags
```

Например `v0.5-e2e-tests`, `v0.6-deploy-ready`. Если что-то пошло не так:

```bash
# Посмотреть теги
git tag

# Откатиться к тегу
git reset --hard v0.5-e2e-tests
```

(Откат с `--hard` сотрёт незакоммиченное! Перед откатом — `git stash` или коммит того что хочешь сохранить.)

### Pre-flight checklist перед сложным промтом

Перед запуском нетривиального промта (фаза, рефакторинг, многофайловые правки):

- [ ] `git status` — чистый, всё закоммичено
- [ ] `git push` — последние правки в GitHub
- [ ] `pytest -v` — все зелёные
- [ ] Поставлен тег `v0.X-something` если меняем что-то крупное
- [ ] Codespace работает стабильно, нет странных ошибок
- [ ] Знаю чего хочу (промт чёткий, без «сделай как-нибудь»)

## Что писать в Claude Code (правила промтов)

### Короткие промты — по умолчанию

**2-5 строк, без структуры, без разделов «Задачи/Тесты/Критерии готовности».**

Пример хорошего короткого промта:

```
Найди в src/ui/specification_section.py баг с пересчётом суммы при ручной правке цены. Сумма должна меняться при изменении цены или количества. Сейчас не меняется.
```

Этого Code хватает. Он знает архитектуру из CLAUDE.md, читает STATUS.md, понимает контекст.

### Длинные промты — только при необходимости

Длинная структура с разделами допустима если:
- Задача многошаговая (>3 файлов или >3 независимых правок)
- Решение неочевидное (нужно объяснить логику или дать примеры кода)
- Легко уйти не в ту сторону (архитектурные решения)
- Многофазная работа со связанными файлами

### Первая строка новой сессии Code

В начале **новой** сессии Code (не в продолжающейся) первой строкой пишу:

```
Прочитай CLAUDE.md и docs/STATUS.md перед началом работы.
```

Это гарантирует что Code подхватит контекст. После этого можно сразу описывать задачу.

## Production Trial — текущий режим работы

### Что это

Я сейчас не пишу код фичами «вперёд» — я **обкатываю** уже сделанный конфигуратор на реальных клиентах. Каждый день делаю КП через приложение, копию находки в файл.

### Куда писать находки

Все правки и баги — в **`docs/manual_review_findings.md`**. Формат записи:

```markdown
## 2026-04-29: КП для ООО "Пример"
**Сценарий:** ВЕСТА-Ф-60-18 + фундамент + монтаж, prepay_50_postpay_50

**Что не так:**
- В колонке "Срок исполнения" пустые ячейки выглядят странно — может, поставить прочерк "—"?
- Кнопка "Сгенерировать КП" не показывает loading state, кажется что зависло

**Приоритет:** P2 (UX, не блокер)
```

### Приоритеты

- **P1** — баг блокирует работу, КП с ошибкой клиенту нельзя отправить
- **P2** — неудобство, мешает но обходится

## Работа с Git

### Через интерфейс (без терминала)

Слева в панели есть значок **Source Control** (трёхточечный логотип git). Там видно изменённые файлы.

- **+** рядом с файлом — добавить в коммит
- В поле сверху ввести описание коммита
- Галочка → коммит локально
- Три точки наверху → **Push** → отправить в GitHub

### Через терминал

Стандартные команды:

```bash
# Что изменилось
git status

# Добавить все изменения в коммит
git add .

# Закоммитить
git commit -m "feat: добавлено что-то"

# Отправить в GitHub
git push

# Подтянуть изменения с GitHub (если работал на другой машине)
git pull
```

### Обязательно делать перед концом дня

Если работал — закомить и запушь. Иначе изменения останутся только в Codespace, который может потеряться:

```bash
git add .
git commit -m "wip: незаконченная работа"
git push
```

## Контроль расхода ресурсов

### Сколько часов Codespace осталось

1. Открой https://github.com/settings/billing
2. Раздел **Codespaces** — там видно "X out of 60 core-hours used"
3. Если близко к 60 — Codespace остановится до начала следующего месяца

**Расход:** 1 час реальной работы 2-ядерной VM = 2 core-hours. То есть 60 core-hours = 30 часов работы.

### Сколько подписки Claude осталось

В Claude Code:
```
/cost
```

Покажет сколько токенов потрачено в текущей сессии.

Полная статистика по подписке — на claude.ai → твой профиль → Settings → Usage.

### Удаление старых Codespaces

Если делал много — могут жрать **15 GB storage** бесплатной квоты:

1. https://github.com/codespaces
2. Найди старые/ненужные → троеточие справа → **Delete**

**Важно:** перед удалением убедись что всё закоммичено и запушено в GitHub. Удалённый Codespace не восстановить.

## Решение типовых проблем

### Codespace не открывается / зависает на запуске

- Закрой вкладку, открой заново через github.com/codespaces
- Если это не помогло — троеточие → **Stop codespace** → подожди 30 сек → **Open**
- Крайний случай: создать новый Codespace (но потеряешь незакоммиченное!)

### Streamlit упал или не отвечает

В терминале где он крутится:
- **Ctrl+C** — остановить
- Запустить заново: `streamlit run src/app.py`

### "Port already in use" при запуске Streamlit

Старый процесс не закрылся. Убей все Python-процессы:

```bash
pkill -f streamlit
```

Подожди 2 секунды, запусти заново.

### Claude Code говорит "не авторизован" / "OAuth token expired"

Возможные причины:
1. Токен случайно отозвался — нужно дома сделать `claude setup-token` заново и обновить секрет в GitHub
2. Используется Opus 4.7 1M — переключи на Sonnet через `/model`

### Git зависает после `git show` или `git log`

Git вызывает пейджер `less` для длинного вывода — там нужно нажать **q** для выхода.

Чтобы это никогда не повторялось — отключи пейджер навсегда:

```bash
git config --global core.pager ""
```

После этого вывод идёт сразу в терминал, ничего нажимать не надо.

### `git push` отвергнут (rejected)

Кто-то (скорее всего ты сам с домашней машины) запушил в `main` раньше. Подтяни и пушь заново:

```bash
git pull --rebase
git push
```

Если есть конфликты при `pull --rebase` — пиши, разберёмся.

### Code упорно правит файл который не должен трогать

Например лезет в `data/prices.json` или `03_knowledge_base/`. Это значит правила в `CLAUDE.md` не подхватились. Проверь:

```bash
cat CLAUDE.md | head -20
```

Должна быть строка типа "Не переписывай data/*.json". Если её нет — обнови CLAUDE.md.

В текущей сессии Code останови работу `/exit` или Ctrl+C, потом запусти заново — он перечитает CLAUDE.md.

### Изменения в файлах не сохраняются

В VS Code файл не автосохраняется. Нажми **Ctrl+S** в редакторе. Или включи автосохранение: **File → Auto Save** (поставить галочку).

### Codespace внезапно перезагрузился, всё пропало

- Незакоммиченные изменения потеряны (и в этом главный урок — коммитить часто)
- Закоммиченные — лежат в локальном Git. Сделай:
```bash
git status
git log --oneline -5
```
Чтобы видеть что было

### Claude Code «думает что в окружении нет чего-то» (например LibreOffice)

Code иногда видит свой sandbox, не наше окружение Codespace. Если он пишет «soffice не найден» / «poppler отсутствует» — проверь сам:

```bash
which soffice
which pdftoppm
```

Если команды находят файлы — значит Code запутался, в Codespace они есть. Скажи ему явно «у меня в окружении эти инструменты доступны, проверь сам через which».

### Перед серьёзным шагом — а всё ли закоммичено?

Это **главный урок** из истории нашей работы. Когда что-то идёт не так и непонятно почему — **первый вопрос всегда `git status`**. Часто проблема в том, что меняли файл, но не закоммитили, и тесты/Code/что-то ещё видят старую версию.
