# План миграции: Streamlit-MVP → FastAPI + React

Статус стека: согласован, не пересматривается. Backend — FastAPI как тонкий
транспорт над доменом-пакетом; фронт — React + Tailwind + shadcn/ui, тупой
рендерер; БД — Supabase (фаза 0–2) → свой Postgres-контейнер (фаза 3, триггер:
месяц стабильной работы compose); деплой — compose 1–2 контейнера + Caddy;
auth — общий bearer-токен с первого публичного дня.

Исполнитель — Claude Code, промт за промтом. Каждая задача в §4 нарезана под
один промт. Правило проекта: файлы ≤200 строк.

---

## 0. Принципы и инварианты (проверяются на каждой фазе)

- **И-1. Один источник истины по логике.** Каскад модель→опции→цены→
  спецификация→оплата существует только в Python. Во фронте нет ни одной
  формулы цены, НДС, сроков, валидации. Проверка: ревью-правило «grep по
  фронту на арифметику с ценами» (см. §6).
- **И-2. Форма КП-снапшота заморожена.** `kps.data` (JSONB) переносится
  байт-в-байт по структуре; добавляется только поле `snapshot_version: 1`.
  Любое изменение формы — отдельное осознанное решение с версионированием.
- **И-3. DOCX-пайплайн не трогаем.** python-docx / docxtpl / docxcompose,
  шаблоны, `clauses.yaml` DSL, vmerge-логика — переносятся как есть.
  Унификация двух движков шаблонизации — НЕ в этом плане.
- **И-4. Порт ≠ рефакторинг.** Фаза 0 переносит поведение 1:1, включая
  известные баги (в т.ч. `custom_N`). Багфиксы — отдельные задачи после
  зелёного golden-gate, каждый со своим контролируемым обновлением эталонов.
- **И-5. Параллельная работа без дрейфа.** Пока Streamlit жив, он импортирует
  тот же домен-пакет `core/`, что и FastAPI. Две копии логики не существуют
  ни одного дня.
- **И-6. Одно изменение за раз.** БД, стек, схема, баги — не смешиваются
  в одной задаче.

## 1. Пофазовый роадмап

### Фаза 0 — Домен как пакет + FastAPI-обёртка (фронта нет)

**Цель:** вся бизнес-логика живёт в импортируемом пакете `core/` без
Streamlit-зависимостей; поверх — FastAPI с Pydantic-границами; выход нового
бэкенда бит-в-бит (по нормализованному дампу) совпадает с эталонами текущего
MVP.

**Объём:** golden-master harness; выделение `core/` (kp, contracts, admin,
storage, docx); развязка `st.cache_data` / `st.secrets`; Pydantic-схемы;
эндпоинты `/api/kp/*`, `/api/contracts/*`; репозиторий над Supabase;
миграция схемы (`created_by`, `snapshot_version`); bearer-auth скелет.

**Параллельно на старом стеке:** весь UI — менеджеры работают в Streamlit
как раньше; Streamlit переключён на импорт из `core/` (И-5).

**Критерий завершения (gate G0):**
1. `pytest` зелёный, включая перенесённые 90 файлов тестов.
2. Golden-diff: все эталонные кейсы (§2) совпадают через новый API-путь.
3. Streamlit работает на `core/` в бою ≥1 неделю без регрессий (отчёт
   менеджеров).
4. Ни одного `import streamlit` внутри `core/` (машинная проверка).

### Фаза 1 — React-фронт для модуля КП + прод-контур

**Цель:** менеджеры делают КП в новом интерфейсе (десктоп + мобильный
браузер по Wi-Fi/интернету); договоры и админка — по-прежнему Streamlit.

**Объём:** Vite + React + TS + Tailwind + shadcn; страница логина (bearer);
конфигуратор КП по паттерну «изменение поля → POST /recalculate → рендер
полного состояния»; генерация/сохранение/поиск КП; compose + Caddy + HTTPS
на VPS; резервный доступ к Streamlit сохраняется.

**Параллельно на старом стеке:** страницы «Договор» и «Админка»; страница
КП в Streamlit остаётся доступной как fallback до конца фазы.

**Критерий завершения (gate G1):**
1. КП, собранный в React, идентичен КП из Streamlit при тех же вводных
   (golden-сравнение снапшотов + DOCX).
2. Все 5 менеджеров сделали ≥1 боевое КП в новом UI; список замечаний
   по вёрстке закрыт (глаз владельца — машинного «готово» нет).
3. HTTPS работает, без токена API отвечает 401, health-check зелёный.
4. Мобильная вёрстка проверена владельцем на реальном телефоне.

### Фаза 2 — Договоры на новом стеке

**Цель:** страница «Договор» (режимы A и B, оба документных класса —
spec v2 и договор поставки) в React поверх бэкенда фазы 0.

**Объём:** UI режима A (выбор КП из базы → подготовка спецификации →
scope-overrides → редактор платёжных строк → генерация); UI режима B
(загрузка карточки контрагента → AI-экстракция с regex-fallback → ручная
правка реквизитов); ручные поля договора; приложения (строит. задание,
контрольный лист); скачивание склеенного DOCX; сохранение в `contracts`.

**Параллельно на старом стеке:** только «Админка» (прайс). Streamlit-страницы
КП и Договор помечаются read-only fallback.

**Критерий завершения (gate G2):**
1. Golden-кейсы договоров (§2) воспроизводятся через новый UI-путь
   (API-вызовы фронта = API-вызовы golden-теста).
2. Fallback без AI: при отключённом OPENROUTER-ключе режим B доступен через
   regex-парсер + ручной ввод (машинный тест + ручная проверка).
3. ≥3 боевых договора сгенерированы менеджерами в новом UI, юр. вычитка
   одного договора каждого класса владельцем.

### Фаза 3 — Консолидация: БД, админка, Bitrix, агенты

**Цель:** один VPS = вся система; Streamlit выключен; заделы под Bitrix и
агентов активированы.

**Объём (последовательными под-этапами, каждый со своим gate):**
- 3a. Переезд БД: Postgres-контейнер в compose, `pg_dump`/`pg_restore` из
  Supabase, cron-бэкап + выгрузка на S3-совместимое хранилище, **учебное
  восстановление** из бэкапа на чистом контейнере. Триггер старта: месяц
  стабильной работы compose (G1+30 дней без инцидентов деплоя).
- 3b. Порт админки прайса (используется редко и только владельцем —
  потому последняя). После 3b Streamlit удаляется из репозитория.
- 3c. Bitrix24 (облачный): регистрация локального приложения, iframe-эмбед
  React-бандла, проверка подписи placement-параметров, маппинг
  `member_id → created_by`. Bearer-auth остаётся для прямого доступа.
- 3d. Агентный слой: MCP-обёртка (или CLI-обёртка) над `core/` — функции
  `create_kp`, `get_kp`, `prepare_contract` вызываются агентом напрямую,
  без HTTP. Пилот: «тендерное ТЗ → черновик КП».
- 3e. Багфиксы из §7 дайджеста, начиная с `custom_N` (контролируемое
  обновление golden-эталонов, см. §2.4).

**Критерий завершения (gate G3):** Streamlit-код удалён; restore-учения
пройдены и задокументированы; договор с монтажом после фикса `custom_N`
содержит корректные обязательства сторон (новый golden-кейс); агентский
пилот создаёт валидный КП-снапшот, проходящий `validate()`.

## 2. Спека golden-master (ворота фазы 0)

Смысл: превратить «порт бэкенда» в машинно-верифицируемую задачу, которую
Claude Code может гнать полуавтономно. Эталон = выход ТЕКУЩЕГО кода на
замороженных входах.

### 2.1. Набор эталонных кейсов (минимум 9)

| # | Кейс | Что покрывает |
|---|------|----------------|
| G-01 | ООО, директор-мужчина, фундамент (пандусный) + монтаж full + поверка | Основной сценарий, clauses по монтажу/фундаменту |
| G-02 | ИП, директор-женщина, шефмонтаж | Склонения/род (`requisites_transforms`), installation_scope=shefmontazh |
| G-03 | Рама (rama_concrete) + зимний период (winter_concrete + surcharge) | Ветки clauses по зиме и раме |
| G-04 | Только поставка (supply, 3 шаблона docxcompose) | Отдельный документный класс, склейка |
| G-05 | ПАК ОРИОН (пакет + столбы) | has_orion / orion_poles_scope, individual_calc |
| G-06 | КП с custom_items + spec_overrides + оплата split_by_items | Ручные позиции, override qty/price, 4 группы оплаты |
| G-07 | Двухдиапазонные весы (dual_range) | Метрология в ТТХ/комплекте |
| G-08 | КП без опций, prepay_100 | Минимальный «пустой» путь |
| G-09 | Договор из КП с монтажом — ТЕКУЩЕЕ (баговое) поведение `custom_N` | Фиксация бага как эталона (И-4); заменяется в 3e |

Каждый кейс = fixture: (а) полный входной state конфигуратора КП (плоские
ключи, как в session_state), (б) КП-снапшот, (в) реквизиты + manual-поля
договора, (г) фиксированная «сегодняшняя» дата.

### 2.2. Заморозка эталонов

- Эталоны снимаются вызовом ТЕКУЩИХ функций напрямую (pytest-harness, без
  Streamlit-UI): `build_kp_snapshot` → `kp_generator` → DOCX; снапшот →
  `from_kp` → `spec_v2_filler`/`supply_filler`/`compose` → DOCX.
- Дата «сегодня» инжектится (freezegun или явный параметр) — иначе каждый
  прогон меняет даты в документах и diff бессмысленен.
- AI-экстракция в golden НЕ входит (недетерминирована, внешний сервис).
  Для `extractor` — записанные фикстуры сырого ответа AI; для
  `requisites_parser` — собственные текстовые фикстуры.
- Эталоны кладутся в `tests/golden/`: сами DOCX (для глаза) + нормализованные
  дампы (для машины).

### 2.3. Метод сравнения (DOCX недиффабелен побайтово)

DOCX — zip с недетерминированными полями (timestamps, rsid). Сравниваем не
файлы, а **канонический дамп**: скрипт `dump_docx.py` через python-docx
выгружает — последовательность параграфов (текст + стиль), таблицы
(ячейки построчно + факт vMerge), порядок секций склейки. Дамп = plain-text.
pytest сравнивает дамп нового выхода с эталонным дампом. Расхождение = красный
тест с построчным diff — Claude Code видит, что именно разошлось.

### 2.4. Процедура обновления эталонов

Эталон меняется ТОЛЬКО отдельным коммитом с причиной («фикс custom_N»),
никогда — внутри задачи порта. Обновление = перегенерация дампа + ручной
просмотр DOCX владельцем + фиксация в changelog эталонов.

## 3. API-контракт

Общее: префикс `/api`, все эндпоинты кроме `/api/health` требуют
`Authorization: Bearer <token>`; ошибки — единый конверт
`{error: {code, message, details?}}`; на границах — только Pydantic-схемы
(словари/TypedDict остаются внутри `core/` на фазе 0, схемы валидируют
вход/выход транспорта).

### 3.1. Справочники (read-only, кэш TTL в памяти)

- `GET /api/refs/bundle` → `{models, prices_meta, options_meta, payment_terms,
  managers, equipment}` — один запрос при загрузке фронта (модели ~90 шт.,
  трафик копеечный; пагинация не нужна).

### 3.2. Модуль КП

- `POST /api/kp/recalculate` — ядро паттерна «тупой фронт».
  Request: `KPStateIn` (полное состояние формы: cascade, equipment,
  construction, options{key: {enabled, price?, qty?, ...}}, custom_items,
  spec_overrides, payment, header-поля).
  Response: `KPStateOut` = нормализованное состояние + derived:
  `{resolved_model, slider_params по позициям, spec_items[], totals
  {with_vat, without_vat, vat}, validation {errors[], warnings[]},
  term_days}`. Любое изменение любого поля на фронте → этот вызов.
- `POST /api/kp/generate` — вход `KPStateIn`; ответ — DOCX
  (`application/vnd...`, `Content-Disposition` с именем из `build_filename`).
  Внутри `run_in_threadpool`.
- `POST /api/kp` — сохранить: вход `KPStateIn` → строится снапшот →
  upsert по `kp_number`; ответ `{id, kp_number}`. Пишет `created_by`.
- `GET /api/kp/{kp_number}` → `{row, snapshot}`.
- `GET /api/kp?recent=N` / `GET /api/kp?contractor=строка` — списки
  (лимит как сейчас; cursor-пагинация — задел в схеме ответа
  `{items[], next_cursor|null}`, реализация при росте).
- `DELETE /api/kp/{id}`.

### 3.3. Модуль Договор

- `POST /api/contracts/prepare-from-kp` — вход `{kp_number | kp_id}`;
  ответ `ContractDraftOut`: spec v2 data + items + deal-контекст +
  дефолтные payment_lines + предвычисленные scope + подсказка типа договора.
  (Эквивалент `build_spec_v2_data` + скелет `contract`-state.)
- `POST /api/contracts/extract-requisites` — multipart-файл (PDF/DOCX);
  ответ `{requisites: RequisitesOut, source: "ai"|"regex", ai_raw?}`.
  При недоступности AI — автоматический fallback на regex (принцип из §7
  дайджеста сохраняется контрактно).
- `POST /api/contracts/generate` — вход `ContractGenerateIn`:
  `{kind: "spec_v2"|"legacy_v1"|"supply", kp_snapshot | kp_id, requisites,
  manual{number,date,address,spec_number,valid_until}, payment_lines[],
  flags{winter_*}, scope_overrides{}, attachments{...}}`.
  Ответ — DOCX. `run_in_threadpool`.
- `POST /api/contracts` — сохранить (`save_contract`), пишет `created_by`.
- `GET /api/contracts?kp_id=` — список по КП.

### 3.4. Админка (фаза 3b, контракт фиксируем сейчас)

- `POST /api/admin/prices/analyze` — multipart (PDF дилер/розница или JSON);
  ответ `{items_preview, validation_split, diff, business_summary}`.
- `POST /api/admin/prices/write` → `{write_result, backup_ref}`;
  `POST /api/admin/prices/rollback`.
- `GET /api/admin/prices/diagnostics`.

### 3.5. Pydantic-схемы (пакет `core/schemas/`)

`KPStateIn/Out`, `SpecItemModel` (зеркало TypedDict `SpecItem`),
`KPSnapshotV1` (точное зеркало §2 дайджеста + `snapshot_version`),
`RequisitesModel` (ЗАКАЗЧИК_* поля), `ContractDraftOut`,
`ContractGenerateIn`, `PaymentLineModel` (dataclass → Pydantic),
`RefsBundle`, `PriceAnalyze*`. Правило: схема ≤200 строк на файл,
по файлу на домен.

### 3.6. Изменение схемы БД (фаза 0, один SQL-скрипт в Supabase)

`kps`: + `created_by text null`, + `snapshot_version int default 1`.
`contracts`: + `created_by text null`, + `created_at/updated_at` если
отсутствуют. Заполнение `created_by` до Bitrix — из выбора менеджера
на логине/в шапке.

## 4. Разбивка задач (гранулярность = один промт Claude Code)

Формат: **ID. Название** — затрагиваемое → критерий проверки.

### Фаза 0 (порядок обязателен: golden раньше порта)

- **P0-01. Дамп-скрипт DOCX** — новый `tests/golden/dump_docx.py` →
  прогон на 2 существующих DOCX даёт стабильный (повторяемый) текстовый дамп.
- **P0-02. Фикстуры входов G-01…G-09** — `tests/golden/fixtures/` (state,
  снапшот, реквизиты, дата) → фикстуры проходят текущий `validate()` без
  errors (кроме намеренных).
- **P0-03. Заморозка эталонов** — harness, вызывающий текущий код на
  фикстурах с freezegun; DOCX + дампы в `tests/golden/expected/` →
  два подряд прогона дают идентичные дампы.
- **P0-04. Golden-тест** — `tests/golden/test_golden.py`: текущий код против
  эталонов → зелёный на нетронутом коде (санити).
- **P0-05. Каркас пакета** — `core/` с подпакетами `kp/`, `contracts/`,
  `admin/`, `storage/`, `docx/`, `schemas/`, `settings.py` → пакет

- **P0-06. Развязка секретов** — `core/settings.py` (env-only), правки
  `extractor`, `supabase_client` → grep `st.secrets` по `core/` пуст.
- **P0-07. Развязка кэша** — `data_loader` → `functools.lru_cache`/TTL-обёртка
  без Streamlit → grep `st.cache_data` по `core/` пуст; тесты loader зелёные.
- **P0-08…P0-12. Перенос доменов пачками** (по одному промту на пачку):
  kp-логика (filters/pricing/spec_builder/validation/term_days/snapshot);
  generators; contracts (22 файла — резать на 3 промта: from_kp+spec_items+
  clauses_*, filler+spec_v2+supply+compose, requisites_*+renderers+utils);
  admin; storage → после каждой пачки: pytest пачки зелёный + P0-04 зелёный.
- **P0-13. Streamlit → импорты из core** — правка import-путей в
  `src/pages`, `src/ui` → приложение Streamlit работает вручную (владелец),
  golden зелёный. С этого момента И-5 выполняется.
- **P0-14. Pydantic-схемы** — `core/schemas/*` по §3.5 → round-trip тест:
  fixture-state → схема → dict → идентичен входу.
- **P0-15. Репозиторий БД** — интерфейс `KPRepository`/`ContractRepository` +
  текущая supabase-py реализация за ним → CRUD-тесты на тестовой таблице.
- **P0-16. SQL-миграция схемы** — скрипт §3.6, применить в Supabase →
  `created_by` пишется при сохранении из harness.
- **P0-17. FastAPI: app + auth + health + refs** → `/api/health` 200 без
  токена, `/api/refs/bundle` 401 без / 200 с токеном.
- **P0-18. Эндпоинты КП** (§3.2, generate через threadpool) →
  golden-кейсы КП проходят через HTTP-клиент теста (не прямой вызов).
- **P0-19. Эндпоинты Договора** (§3.3) → golden-кейсы договоров через HTTP;
  extract-requisites с выключенным AI-ключом возвращает `source: "regex"`.
- **P0-20. Gate G0** — чек-лист §1 фазы 0, недельная боевая обкатка
  Streamlit-на-core → owner подписывает фазу.

### Фаза 1

- **P1-01. Скаффолд фронта** — Vite+React+TS+Tailwind+shadcn, прокси на API,
  layout с навигацией → `npm run build` собирается, пустые страницы рендерятся.
- **P1-02. API-клиент + auth** — типизированный клиент (типы из OpenAPI
  FastAPI), экран логина, хранение токена, 401-редирект → ручная проверка.
- **P1-03. Хук состояния КП** — «единственный стейт = последний ответ
  /recalculate», debounce на ввод → юнит: изменение поля вызывает POST,
  ответ замещает стейт целиком.
- **P1-04…P1-08. Секции формы КП по одной на промт** — шапка; каскад модели +
  слайдер; оборудование + конструкция; опции по блокам; спецификация
  (таблица с override qty/price); оплата (5 пресетов) → каждая секция:
  визуальная проверка владельцем + derived-значения совпадают со Streamlit
  на контрольном примере.

## 6. Карта рисков и границы автономии Claude Code

### Автономия безопасна (машинный verify, можно гнать пачками)

Порт `core/` (P0-05…12) — golden + pytest ловят любое расхождение;
Pydantic-схемы (round-trip тесты); эндпоинты (golden через HTTP); SQLAlchemy-
репозиторий (CRUD-тесты); дамп-скрипт и harness.

### Автономия с обязательным ревью результата (полу-верифицируемо)

Compose/Caddy/Dockerfile — AI генерирует, но «готово» = ручной смоук на VPS;
SQL-миграции — прогон сначала на копии; auth-мидлварь — ручная проверка
именно негативных сценариев (нет токена, кривой токен).

### Только с проверкой владельца (машинного «готово» нет)

Весь React-UI: вёрстка, responsive, UX форм — единственный критерий это глаз
и пилот менеджеров. Юридический текст договоров после любого изменения
clauses/эталонов. Restore-учение БД. Bitrix-iframe (поведение внутри чужого
продукта).

### Специфические риски и контрмеры

- **Утечка логики во фронт (нарушение И-1).** Контрмера: ревью-правило в
  конце каждой P1/P2-задачи — grep фронта на `price`, `vat`, `* 0.22`,
  арифметику с ценами; любое совпадение = дефект задачи.
- **Golden фиксирует баг как норму.** Осознанно (И-4, G-09); риск —
  забыть снять фикс. Контрмера: P3e-01 в плане с собственным gate.
- **Дрейф двух UI в параллельный период.** Контрмера: И-5 (один пакет
  core) + G1-критерий идентичности DOCX двух путей.
- **Контекст-лимит AI-сессий.** Контрмера: файлы ≤200 строк, задачи =
  один промт, contracts-порт порезан на 3 пачки, схемы — по файлу на домен.
- **Недетерминизм дат/AI в эталонах.** Контрмера: freezegun обязателен в
  harness (P0-03), AI исключён из golden (записанные фикстуры).
- **Публичный HTTPS раньше auth.** Контрмера: порядок задач P1-11 не
  выполняется раньше P0-17; Caddy не выставляется без включённого
  bearer-мидлваря (пункт SMOKE.md).
- **Переезд БД ломает бой.** Контрмера: триггер «месяц стабильного compose»,
  сверка строк после restore, Supabase не удаляется до G3 (остаётся
  холодным резервом ещё месяц).
