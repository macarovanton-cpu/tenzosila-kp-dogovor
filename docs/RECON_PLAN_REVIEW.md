# RECON: Ревью плана миграции — попытка сломать (2026-07-12)

Read-only. Проверялись: `docs/MIGRATION_PLAN.md`, `docs/MIGRATION_PLAN_DELTA.md`
против кода на коммите 3eb5fb2 и `docs/RECON_ARCH_AUDIT.md`.
Маркировка: **ФАКТ** — прочитано в коде (файл:строка), **ГИПОТЕЗА** — вывод.

## Вердикт

Каркас плана здоров: golden-first уже отработал (эталоны сняты по полному
боевому пути), инварианты И-1…И-6 осмысленны, дельта сняла реальный дрейф.
Но в текущей записи план **встанет дважды и молчит о трёх вещах**:

1. Пачка P0-10 (contracts) упадёт о **собственные стражи** проекта — кросс-импорты
   contracts→kp и `import streamlit` в spec_v2_filler (В-1, В-2).
2. P0-19 «одним промтом» невозможен: оркестрация генерации договора живёт
   в UI-слое и не переносится ни одной пачкой (В-3).
3. В плане нет вообще: эндпоинта пересчёта договора — без него Фаза 2
   нарушает И-1 (В-4); межпроцессной инвалидации прайса — рвёт инвариант
   КП=договор с первого дня двух процессов (В-6); прод-бага B9, который
   golden уже узаконил (В-7).

## Возражения

### В-1. КРИТИЧНО. P0-10 развалится о стража границ Д-2 — конфликт заложен в самом правиле

**Возражение.** Правило Д-2 «kp/ и contracts/ не импортируют друг друга» +
grep-gate (Д-2 → P0-20) несовместимы с кодом, который план велит перенести 1:1 (И-4).

**ФАКТ.** `src/contracts/from_kp.py:11-12` — `from src.spec_builder import
format_platform_size, resolve_payment_group`, `from src.term_days import ...`;
там же ленивые импорты `build_spec_items` (строки 281, 450) и `data_loader`
(строка 448). `src/contracts/terms_renderer.py:6` и `supply_filler.py:36`
тоже импортируют `term_days`. По Д-2 `spec_builder` и `term_days` уходят в
`core/kp/` → страж `tests/test_core_boundaries.py:43`
(`test_core_modules_do_not_import_each_other`) краснеет в момент переноса
from_kp. Страж уже существует и работает.

**Что изменить.** До нарезки P0-08 — отдельный микрошаг «карта кросс-импортов
и распределение shared/»: `term_days` → `core/shared/` (три потребителя в
contracts — это кросс-модульный примитив, как payment_wording в Д-5.2).
С `build_spec_items` так нельзя — это ядро КП-логики; варианты: (а) осознанное
исключение в страже на переходный период + пост-G0 задача «handoff через
kp_load.build_kp_payload» (совпадает с местом единого стража из аудита §3),
или (б) разрешить одностороннее contracts→kp. Рефакторить handoff в Фазе 0
нельзя — И-4. Решение владельца, но ДО P0-08, иначе term_days переедет дважды.

### В-2. КРИТИЧНО. Та же пачка упадёт о стража стерильности — B15 в плане отсутствует

**Возражение.** План не содержит задачи на снятие `import streamlit` с DOCX-ядра.

**ФАКТ.** `src/contracts/spec_v2_filler.py:7` — `import streamlit as st`;
строка 262 — `st.warning(...)`. Страж `test_core_boundaries.py:27` запрещает

план должен явно разрешить одну строку.

**Что изменить.** Микрозадача (аналог B15 аудита: st.warning → logging)
отдельным шагом ДО contracts-пачек, с явной оговоркой к И-3 и прогоном
golden (текст warning в DOCX не попадает — эталоны не тронутся; проверить).

### В-3. КРИТИЧНО. P0-19 опирается на код, которого в core/ не будет

**Возражение.** «P0-19. Эндпоинты Договора — один промт» предполагает, что
сборка договора вызываемая. Это не так: оркестрация (collect → fill_spec_v2 →
compose → именование файлов → чтение байтов) — это UI-код.

**ФАКТ.** `src/app_pages/2_Договор.py:1059-1169`: `OUTPUT_DIR.mkdir`,
`collect_for_template()`, `fill_spec_v2(...)`, `compose_spec_with_attachments(...)`,
плюс traceback-дамп в docs/ при падении (строка ~1164). Ни одна пачка
P0-08…12 не переносит `src/app_pages`; `collect_for_template` живёт в
`src/contracts/state.py`, который аудит (и план по духу) велит НЕ портировать.
Вторая копия этой оркестрации уже существует: `tests/autoverify/runner.py:94`
(`generate_all`, «зеркало кнопки»). P0-19 в текущем виде создаст **третью** —
прямое нарушение духа И-5.

**ФАКТ (следствие для B14).** Аудит отнёс обвязку B14 (cwd-зависимый
`_SUPPLY_TEMPLATES` в compose.py, общий output/ с детерминированными именами)
к Фазе 2. Но план сам требует «golden-кейсы договоров через HTTP» уже в P0-19
— из чужого cwd относительные пути не разрешатся, конкурентные тестовые
запросы столкнутся именами. B14 блокирует **Фазу 0**, не Фазу 2.

**Что изменить.** Новая задача перед P0-19 (условно P0-13b): извлечь
оркестрацию из 2_Договор.py + runner.py в одну функцию
`core/contracts/assemble` (вход — DTO, выход — bytes; tmp-директория на вызов,
пути шаблонов от `__file__`; traceback-дамп в docs/ НЕ переносить);
переключить на неё и Streamlit-страницу, и runner. Golden охраняет
эквивалентность. После этого P0-19 — действительно один промт (тонкая обёртка).

### В-4. КРИТИЧНО (Фаза 2). Нет эндпоинта пересчёта договора — P2-04 нарушит И-1

**Возражение.** §3.3 содержит prepare-from-kp / extract-requisites / generate /
save / list. Эндпоинта «пересчитай платёжные строки и итоги» нет. Редактор
строк оплаты в React (P2-04) без него обязан считать `round(pct/100*база)`
и добор остатка сам — арифметика с деньгами во фронте, прямое нарушение И-1.

**ФАКТ.** Логика пересчёта и валидации живёт в UI-слое:
`src/ui/payment_lines_editor.py:170` (`_recompute_amounts`),
`:202` (`_validate_rows`). `src/ui/` не входит ни в одну пачку P0-08…12 и
по плану умирает вместе со Streamlit в Ф3b. То есть к началу Фазы 2 этой
логики на новом стеке не существует нигде.

**Что изменить.** (а) В §3.3 добавить `POST /api/contracts/recalculate`
(вход: payment_lines + spec items + база; выход: пересчитанные amounts,
errors/warnings) — контракт зафиксировать сейчас, как сделано для админки
§3.4. (б) Новая задача до P2-04: перенос `_recompute_amounts`/`_validate_rows`
в core (это порт, не рефакторинг — поведение 1:1, включая известные Р-3/Р-4).
(в) Ужесточение «недобор — warning» (Р-3) — отдельным осознанным решением,
не молчаливо при порте.

### В-5. ПОРЯДОК/МЕХАНИКА. Окно двух копий между P0-08 и P0-13 — И-5 нарушается неделями

**Возражение.** План: пачки P0-08…12 переносят код в core/, и только P0-13
переключает Streamlit на новые импорты. Если «перенос» = копирование,
то весь интервал P0-08…P0-13 в репозитории живут две копии логики —
ровно то, что И-5 запрещает «ни одного дня». Хотфикс прода в этот период
уйдёт в src/-копию и молча потеряется при переключении.

**ФАКТ** (косвенный): ~90 файлов тестов импортируют `src.*` — большой взрыв
импортов на P0-13 означает одновременную правку тестов и приложения, один
промт это не вместит.

**Что изменить.** Механику зафиксировать в P0-08: каждая пачка = move +
reexport-shim (`src/spec_builder.py` → `from core.kp.spec_builder import *`).
Streamlit и тесты продолжают работать после каждой пачки; И-5 выполняется
с первой пачки, а не с P0-13; P0-13 вырождается в чистку shim'ов и прямых
импортов в `src/app_pages`, `src/ui`.

### В-6. ОТСУТСТВУЕТ. Межпроцессная инвалидация прайса (B13) — инвариант КП=договор рвётся операционно

**Возражение.** В плане и дельте нет ни задачи, ни упоминания. С P1-11
(первый день, когда FastAPI и Streamlit живут рядом в проде) запись прайса
из Streamlit-админки не инвалидирует кэш FastAPI: до часа (TTL 3600,
`src/data_loader.py:23-48`) КП в React и договор в Streamlit считаются
по РАЗНЫМ прайсам. Это операционный разрыв инварианта «сумма КП = сумма
договора», который golden не ловит (golden — один процесс).

**ФАКТ.** `src/admin/price_write_service.py:254` — `load_prices.clear()`:
Streamlit cache API, инвалидация только своего процесса. Бонус-поломка:
при замене на `functools.lru_cache` (P0-07) у функции не будет метода
`.clear()` (у lru_cache — `.cache_clear()`) — строка 254 упадёт `AttributeError`
при первой записи прайса, а её правка в объёме P0-07 не значится
(«data_loader» — и всё).

**Что изменить.** P0-07 расширить: (а) правка вызова в price_write_service;
(б) сразу mtime-проверка файла в загрузчике (кэш с ключом по mtime — решает
и межпроцессную инвалидацию, и TTL). Критерий P0-07 дополнить: «запись
прайса из админки видна из второго процесса без рестарта» (тест на два
импорта/процесса). Дедлайн — не позже P1-11, дешевле всего внутри P0-07.

### В-7. ОТСУТСТВУЕТ. B9 (договор игнорирует spec_overrides) — golden уже узаконил разрыв, план молчит

**Возражение.** Главный известный разрыв инварианта (аудит Р-1/Р-2: ручная
правка цены в КП не доходит до договора) не упомянут ни в плане, ни в дельте.
Д-6.5 называет примером «оставшихся багов» только Дефект 3 (qty>1).

**ФАКТ.** `tests/golden/fixtures/G-06.json` содержит `spec_overrides`,
и в `tests/golden/expected/` заморожены и `G-06_kp.docx`, и `G-06_dogovor.docx`
— расхождение сумм КП≠договор зафиксировано эталоном как норма. По И-4 это
корректно, но фикс B9 потребует re-freeze G-06 по §2.4 — и если план его
не называет, исполняющая сессия Ф3e о нём не узнает (список 3e по Д-7 —
это TECH_DEBT.md, куда B9 ещё только предстоит внести из аудита).

**Что изменить.** (а) В Д-6.5 (риск «golden фиксирует баг») добавить B9/Р-1
рядом с Дефектом 3, с пометкой «re-freeze G-06». (б) Решение владельца
о сроке: это живой прод-баг денег, аудит рекомендует чинить до/независимо
от миграции — тогда re-freeze G-06 случится до порта, что дешевле
(порт сверяется уже с правильным поведением).

### В-8. ДАННЫЕ. Миграция данных сведена к ADD COLUMN; политика по legacy-снапшотам не определена

**Возражение.** §3.6 добавляет колонки — и всё. Судьба существующих строк
`kps` не решена: legacy-снапшоты с пустым `model.price` при восстановлении
пересчитываются по ЖИВОМУ prices.json (аудит Р-6, `kp_restore.reconstruct_kp_state`).
Открытие старого КП в React (Фаза 1) после обновления прайса покажет не ту
сумму, что была у клиента; договор из такого КП — тоже.

**ГИПОТЕЗА** (масштаб): сколько строк без price — не считал; может быть ноль.

**Что изменить.** В P0-16 добавить шаг разведки (`SELECT count(*)` по
снапшотам без model.price) и решение владельца: бэкфилл цены в старые
снапшоты (это изменение ДАННЫХ снапшота — требует явной оговорки к И-2)
либо задокументированное «legacy плавает, принимаем».

### В-9. СРЕДНЕ. P0-14: KPStateIn ≠ форма state, которую ждёт core — задачи-адаптера нет

**Возражение.** §3.2 описывает `KPStateIn` с вложенными
`options{key: {enabled, price?}}`; весь портируемый код
(`build_kp_snapshot`, `validate`, `build_spec_items`) ждёт ПЛОСКИЙ dict
с ключами `opt_{key}_enabled` (CLAUDE.md, аудит §1.2). Критерий P0-14
«fixture-state → схема → dict → идентичен входу» буквально неисполним:
формы разные, нужен маппер, которого нет ни в одной задаче. Тихая потеря
ключа в маппере (spec_overrides, model_qty) = молчаливый разрыв КП=договор.

**Что изменить.** В P0-14 явно включить двусторонний маппер flat↔schema и
round-trip прогнать на ВСЕХ G-01…G-09 фикстурах (они и есть перечень живых
ключей). Страховка уже в плане: P0-18 «golden через HTTP» поймает потерю —
подтвердить, что фикстуры действительно идут через адаптер, а не в обход.

### В-10. МЕЛОЧИ (по одной строке)

- **P0-06 критерий пуст:** «grep st.secrets по core/» тривиально зелёный —
  core/ пуст; критерий должен целить `src/` (кроме app_pages/ui). ФАКТ: правки

- **attachments в API:** это выбор серверных файлов-шаблонов
  (`2_Договор.py:347-427`, `build_task_path`/`control_sheet_path`), не

- **Traceback-дамп в docs/** (2_Договор.py, при падении fill_spec_v2) —
  при извлечении оркестрации (В-3) не переносить: запись в рабочую копию
