## 0. Карта архитектуры и границы ответственности

Поток данных (подтверждён кодом, совпадает с ARCHITECTURE_DIGEST §6):

```
КП (плоский session_state) → build_kp_snapshot() → Supabase kps.data (JSONB, БЕЗ версии)
  → страница Договор: get_kp_by_number()
      → build_specification_items() [SpecItem[] + metadata.scope]
      → build_clauses_context() → build_contract_clauses() [clauses.yaml + DSL]
      → spec-флоу:   fill_spec_v2()  [python-docx + XML-синтез + jinja2 для clause-текста]
      → supply-флоу: build_supply_context() → compose_supply() [docxtpl ×3 + python-docx двупроход + docxcompose]
```

### Где границы размыты (подтверждено):

1. **compose.py импортирует приватные `_remove_marker` / `_replace_marker_with_paragraphs` из spec_v2_filler** (compose.py:10). Модуль «композиции» зависит от внутренностей «филлера» — при рефакторинге spec_v2_filler молча ломается supply-флоу.
2. **spec_v2_filler читает data/models.json и data/equipment_specs.json напрямую с диска** (spec_v2_filler.py:196-197), минуя data_loader и его кэш. Два пути чтения одних справочников = два источника поведения.
3. **Эвристики payment_group по имени позиции живут в двух местах:** `_payment_group_by_name` (from_kp.py:550) и `_bucket_to_pg` (2_Договор.py:259). Переименование позиции меняет её платёжную группу молча.
4. **Три представления одного снапшота** в from_kp.py: `build_specification_from_kp_snapshot` (legacy v1, плоские СПЕЦ_*), `build_spec_rows_from_snapshot` (supply rows), `build_specification_items` (SpecItem[]). Фильтры расходятся: rows пропускает qty==0, items пропускает price<=0 (from_kp.py:541).
5. **2_Договор.py (1019 строк)** держит бизнес-логику в UI-слое: `_rows_to_items`, бакет-эвристики, условная логика генерации. Для сравнения 3_Админка.py — 68 строк чистой делегации (правильный образец).

### P0-1. ПОКУПАТЕЛЬ_ТЕЛЕФОН: цепочка кода исправна, дефект — в покрытии парсера
`requisites_parser.py:67-69, 150-152` · **суть:** трассировка всей цепочки телефона выполнена: парсер :150-152 → `merge_requisites` (2_Договор.py:551) → `collect_for_template` (contracts/state.py:92) → `_buyer_context` (supply_filler.py:133) → шаблон. Каждое звено корректно; поле есть в REQUISITE_FIELDS (2_Договор.py:92) и в обоих AI-промптах. Значит баг НЕ в маппинге. **Диагноз:** `_PHONE_RE` жёстко предполагает формат «+7|8 + 3-значный код + 3-2-2»: телефоны с 4-5-значным кодом города (`+7 (4732) 55-44-33`) и номера без префикса +7/8 (`тел.: (473) 214-58-62`) не матчатся вовсе. Второй кандидат — режим AI-экстракции (модель вернула пустой телефон). · **риск:** пустая строка «Тел./факс» в реквизитах (текущий открытый баг) · **усилие:** S (расширить regex: код 3-5 цифр, вариант без префикса при якоре «тел»; + лог того, что телефон не найден) · **в текущую фазу:** ДА — это и есть активная задача.

### P0-2. custom_N: диагностику влияния на spec-флоу поднять до немедленной
`from_kp.py:484-488 (неизвестный ключ опции → custom_{uuid8}, scope НЕ ставится)`, `from_kp.py:538-544 (custom_items → custom_{index})` → `clauses_context.py:54,69,72,85,94,98 (строгие id-lookup)` · **суть:** подтверждена вся цепочка из STATUS. Монтаж/фундамент, приехавшие как custom, невидимы для scope → в spec-договоре могут пропасть обязательства сторон при физически оплаченном монтаже (~90% договоров). В supply-флоу закрыто фильтром payment_group (supply_filler.py:245-261) — но фильтр питается эвристикой по имени (см. P1-5). · **риск:** юридически неполный договор, менеджер не заметит · **усилие:** диагностика S (один прогон реального КП с монтажом), фикс M (scope по payment_group + под-признак монтаж/поверка) · **в текущую фазу:** диагностика — ДА (STATUS уже называет её «следующим шагом»), фикс — по результату.

### P0-3. Тихо-неполный документ: возврат маркер-замены игнорируется + маркеры в таблицах не ищутся
`compose.py:42-46`, `spec_v2_filler.py:296-309` · **суть:** `_replace_marker_with_paragraphs`/`_remove_marker` возвращают bool «нашёл/нет» — все 4 вызова игнорируют его. Плюс поиск идёт по `doc.paragraphs`, который НЕ включает параграфы внутри таблиц: маркер, оказавшийся в ячейке после правки шаблона, не найдётся никогда. Готовая страховка уже есть в кодовой базе — `filler.get_unfilled_placeholders()` — но после генерации она не вызывается. · **риск:** договор уходит с literal `{{PAYMENT_SECTION}}` или без блока оплаты; сломается при следующей правке шаблонов (а их правят регулярно — вся волна 07-01) · **усилие:** S (проверять возврат + прогонять get_unfilled_placeholders после рендера, показывать st.warning) · **в текущую фазу:** ДА — дешёвая страховка перед тегом v2.4.

## P1 — в текущую фазу

### P1-1. `_load_model_and_deps`: except Exception → None без следа
`spec_v2_filler.py:237-238` · **суть:** любое исключение (битый JSON, отсутствие модели, ошибка логики) молча превращается в None → ТТХ и комплект поставки тихо не заполняются (placeholder'ы остаются/секции пустые). Для сравнения: `requisites_transforms.py:157` делает это правильно (лог + fallback). · **риск:** spec-договор без ТТХ уходит заказчику; дебаг вслепую · **усилие:** S (лог + предупреждение в UI) · **фаза:** ДА.

### P1-2. Supabase-клиент без таймаутов, создаётся на каждый вызов
`supabase_client.py:33` · **суть:** `create_client(url, key)` без опций таймаута; при сетевой деградации вызов виснет — это уже проявляется как «tests/storage зависает» из STATUS. Исключения обёрнуты в StorageError с логом (хорошо), но от зависания это не спасает. · **риск:** зависшая страница Договор/КП при сетевых проблемах · **усилие:** S (httpx-таймаут через ClientOptions + кэшировать клиент) · **фаза:** ДА — дёшево, закрывает известный пункт техдолга.

### P1-3. `_clear_prices_cache`: except Exception: pass
`price_write_service.py:246-253` · **суть:** сброс кэша `load_prices.clear()` глотает всё. Вне Streamlit это оправданный no-op (так и задумано), но внутри Streamlit реальная ошибка сброса тоже молчит → админ записал прайс, а КП продолжает считать по старому кэшу (TTL 3600с). · **риск:** цены в КП расходятся с только что записанным прайсом до часа · **усилие:** S (сузить except до ImportError/AttributeError, остальное логировать) · **фаза:** ДА (админ-трек живой).

### P1-4. filler.py: falsy-значение → пустая строка
`filler.py:64` (`str(value) if value else ''`), та же идиома в `_replace_textbox_placeholders` :83 · **суть:** значение 0 / 0.0 рендерится как пустота. Сегодня контексты почти всюду строковые, но конвенция «0 = пусто» — мина под любой числовой ключ (проценты, сроки, суммы). · **риск:** тихая потеря легитимного нуля в документе · **усилие:** S (`'' if value is None else str(value)`) · **фаза:** ДА — одна строка, пока не наступили.

### P1-5. payment_group по тексту имени — единственная защита supply-суммы
`from_kp.py:550 (_payment_group_by_name)`, `2_Договор.py:259 (_bucket_to_pg)` · **суть:** фильтр, исключающий монтаж/фундамент из суммы поставки (P1-фикс волны 06-29), опирается на классификацию по подстрокам имени. Менеджер переименовал позицию («Работы по установке» вместо «Монтаж») → позиция уехала в сумму поставки. Связано с P0-2: канонический признак (id/scope) отсутствует именно у custom-позиций. · **риск:** неверная сумма договора поставки · **усилие:** S (warning в UI при неклассифицированном имени) / M (решается вместе с custom_N) · **фаза:** ДА как минимум warning.

*Сверка со STATUS (подтверждаю, оставить как есть в фазе):* группировка % по тексту «Объект» (payment_lines_editor.py:146-152) — жива, P2 STATUS корректен; EOL prices.json — жив.
