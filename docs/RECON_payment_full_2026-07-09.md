# Разведка: полный каталог формулировок блока оплаты (2026-07-09)

Read-only. Ничего не менялось, фиксы не предлагаются. Финальный заход
перед F1 — цель: закрыть все формулировки, без непокрытых веток.

Входные доки (не дублируются, только ссылки):
- `docs/RECON_payment_2026-07-09.md` — механика (пресеты, вызовы,
  почему бандл ОРИОН не делится).
- `docs/RECON_payment_wording_2026-07-09.md` — базовый сценарий
  (весы+фундамент+монтаж+поверка+доставка) разобран дословно с реальными
  числами из теста — это же сценарий 8 ниже, не повторяется.

**Методологическая оговорка.** Эталоны (`docs/contract_templates_v1/`)
— документы Договора/Спецификации, НЕ документы КП. Часть 2 сверяет
«Спецификация vs эталон» дословно по всем 9 сценариям; «КП vs эталон»
— только по формуле кода (эталонной пары для КП в этом наборе файлов
нет). КП никогда не печатает суммы — формула воспроизводится точно для
всех 9 сценариев без исключений. Спецификация печатает суммы — точные
рубли даны там, где известны суммы по бакетам (сценарии 1,4,5,6,9);
там, где эталон — бланк-заготовка без чисел (сценарий 2) или без
таблицы позиций (сценарий 3) — используется символьная форма `<сумма>`,
сравнение идёт по словам/структуре, не по цифрам.

## ЧАСТЬ 1. Инвентарь рычагов

### 1.1 Пресеты — их ровно 6 (`data/payment_terms.json`, `default_preset_id: "split_by_items"`)

| id | строки | default_percents | editable_percent_keys | дни | КП/Спец |
|---|---|---|---|---|---|
| `v1_prepay_postpay` | 22-31 | `{prepay:50}` | *(нет поля)* | 5 | оба (через `render_v1`/`_non_split_phases`) |
| `v2_prepay_preship_postpay` | 32-42 | `{prepay:30,preship:40}` | *(нет поля)* | 5 | оба |
| `v3_postpay_only` | 43-58 | *(нет — `trigger_options`+`default_trigger_id`)* | *(нет)* | 15 | оба |
| `prepay_100` | 59-71 | `{p1:100}` | `["p1"]` (декоративно — `render_prepay_100` шлёт `p1=100` хардкодом) | 5 | оба |
| `split_by_items` | 72-129 | по группам (см. 1.2) | per-group `["prepay","postpay"]` | 5 | оба |
| `custom` | 130-141 | `{}` | `[]` | *(нет, `editable_days:false`)* | оба (freeform-текст) |

Оба генератора (`payment_renderer.render_payment_block` для КП,
`payment_line.build_lines_from_snapshot`/`_build_non_split_lines` для
Договора/Спецификации) читают одни и те же 6 id, но **это два
независимых кодовых пути** — `payment_line.py` не импортирует
`payment_renderer.py` и хранит свою копию дефолтов
(`_DEFAULT_SPLIT_PERCENTS`, `payment_line.py:187-192`, комментарий:
«страховка для битых снапшотов»). Синхронизация — вручную, двумя
людьми в двух файлах.

### 1.2 `resolve_payment_group()` — дословно (`src/spec_builder.py:226-245`)

```python
def resolve_payment_group(item_key: str) -> str:
    if item_key.startswith("foundation_"): return "foundation"
    if item_key.startswith("construction_works_"): return "foundation"
    if item_key.startswith(("concrete_base", "road_slabs_", "pag_slabs_")): return "foundation"
    if item_key == "delivery_default": return "delivery"
    if item_key in ("install_default", "verification_default", "orion_install"):
        return "installation_and_verification"
    if item_key == "orion_cable_poles": return "foundation"  # опоры ОРИОН — с фундаментом (эталон A1)
    return "scales"
```

| Объект | item_key | payment_group | Источник |
|---|---|---|---|
| Рама | `frame_*` | **scales** (fallback) | `src/config.py:70` |
| Пандусы | `ramp_set_*` | **scales** (fallback) | `src/config.py:69` |
| Шеф-монтаж | `install_default` (тот же ключ, что обычный монтаж!) | **installation_and_verification** | display-имя меняется по `is_shefmontazh`/`installation_scope=="shefmontazh"`, group — нет (`from_kp.py:192-193`, `spec_builder.py:174-175`) |
| Опоры/кабель-трассы ОРИОН | `orion_cable_poles` | **foundation** (явное исключение) | реальный, независимо включаемый ключ (`data/prices.json:863-870`), НЕ авто-добавляется (`from_kp.py:121-123`) |
| Бандл ОРИОН (orion_lite/standard/auto) | `orion_*` | **scales** (fallback) | вся цена бандла (весы+вшитый шеф-монтаж) целиком, `_expand_orion_options` расщепляет только для отображения (`from_kp.py:113-171`), НЕ для расчёта оплаты |
| Курирование фундамента | `foundation_supervision` | **scales** (не начинается с `foundation_`!) | пропущено в whitelist — потенциально мёртвая зона, не покрыта ни одним `if` |

Также: **`foundation_supervision` не матчится ни одним условием** —
падает в `"scales"`, хотя концептуально это работа по фундаменту.

### 1.3 Триггеры

`TRIGGER_TEXTS` (`payment_line.py:19-26`) vs `SUPPLY_TRIGGER_TEXTS`
(`supply_filler.py:43-48`, используется только для «Договора поставки»):

| Trigger | TRIGGER_TEXTS (Спецификация) | SUPPLY_TRIGGER_TEXTS (Договор поставки) |
|---|---|---|
| SPEC_SIGNED | «подписания настоящей Спецификации» | «подписания настоящего Договора» |
| FOUNDATION_ACT | «подписания Акта выполненных работ по строительству фундамента» | *(не переопределён)* |
| SHIPMENT_READY | «получения уведомления о готовности Весов к отгрузке» | *(не переопределён)* |
| BRIGADE_READY | «уведомления о готовности принять монтажную бригаду на месте монтажа» | *(не переопределён)* |
| WORK_ACT | «подписания Акта выполненных работ по настоящей Спецификации» | «поставки Весов Покупателю» |
| DELIVERED | «поставки Весов Заказчику» | «поставки Весов Покупателю» |

`v3_postpay_only.trigger_options` (КП, три варианта текста) →
`_V3_TRIGGER_MAP` (Спец, схлопывает два варианта в один trigger):
```python
_V3_TRIGGER_MAP = {
    "after_delivery":     PaymentTrigger.DELIVERED,
    "after_installation": PaymentTrigger.WORK_ACT,
    "after_act":          PaymentTrigger.WORK_ACT,   # ← то же, что after_installation
}
```
КП различает «после выполнения монтажа» и «после подписания акта
приёмки выполненных работ» текстом; Спец даёт ОДИН и тот же
`TRIGGER_TEXTS[WORK_ACT]` для обоих — расхождение между двумя
генераторами внутри одного и того же пресета.

### 1.4 Слово-тип (Предоплата/Доплата/Оплата) — НЕ функция от процента

Явная находка: правила «0%/100% vs обе>0», которое искалось в задании,
**в коде не существует**. Слово — хардкод per (preset, фаза):

| Preset / фаза | kind | Где |
|---|---|---|
| v1 предоплата / доплата | предоплата / доплата | `payment_line.py:111-112` |
| v2 предоплата / перед-отгрузкой / доплата | предоплата / доплата / доплата | `payment_line.py:120-123` |
| v3 (единственная фаза) | **оплата** (всегда, единственный источник слова «оплата» в Спец) | `payment_line.py:131` |
| prepay_100 | предоплата | `payment_line.py:136` |
| split L1 (весы[+фунд]) | предоплата | `payment_line.py:286` |
| split L2 (фундамент доплата) | доплата | `payment_line.py:298` |
| split L3 (весы[+доставка]) | доплата | `payment_line.py:318` |
| split L4 (монтаж предоплата, только если `iv.prepay>0`) | предоплата | `payment_line.py:331` |
| split L5 (монтаж доплата) | доплата | `payment_line.py:340` |

Слово не переключается по значению процента нигде; переключается
только *наличие* строки (если сумма/процент = 0 — строка пропускается,
слово не участвует в решении).

### 1.5 `share_prep` — предлог/база

| Значение | Где выбирается | Автоматически? |
|---|---|---|
| `"от"` + object `"общей цены договора"` | все non-split пресеты, всегда (`payment_line.py:173-174`) | да |
| `"от стоимости"` | split_by_items, все строки, пока проценты объединяемых групп совпадают | да |
| `None` (percент и объект вообще не печатаются) | split_by_items L1/L3, когда `f_prepay != s_prepay` или `d_post != s_post` (`payment_line.py:282-283,314-315`) | да (это защёлка кода) |
| `"за"` | **нигде не генерируется автоматически** | только ручная правка в `payment_lines_editor.py` (`_PREPS = ["от стоимости","за","от","—"]`, строка 40) |

КП (`render_split_by_items`) вообще не знает `share_prep` — там
всегда фиксированные фразы «стоимости весов»/«стоимости фундамента»/
«стоимости доставки», плюс наблюдение: **в отличие от Спец, КП никогда
не «схлопывает» percent в None при несовпадении — он всегда печатает
обе доли через « + »**, даже если проценты разные.

### 1.6 Объект оплаты — словесные варианты

| Контекст | Текст объекта | Источник |
|---|---|---|
| Весы, без ОРИОН | «Весов» (Спец) / «стоимости весов» (КП) | `payment_line.py:274`, `payment_renderer.py:54` |
| Весы + ОРИОН | «Весов (включая ПАК ОРИОН)» (Спец) / «стоимости весов (включая ПАК ОРИОН)» (КП) | то же место, `has_orion` |
| + фундамент (L1, проценты равны) | добавляется суффикс « и фундамента Весов» | `payment_line.py:278` |
| Фундамент отдельно (L2) | «фундамента Весов» | `payment_line.py:298` |
| + доставка (L3, проценты равны) | суффикс « и доставки» | `payment_line.py:310` |
| Монтаж/поверка | «монтажных работ и поверки» (всегда это, **даже при шеф-монтаже** — флаг `is_shefmontazh` меняет только имя SpecItem в таблице, не строку оплаты) | `payment_line.py:298,332,341` |
| Рама/пандусы | **никогда не называются отдельно** — тихо входят в сумму «Весов» (payment_group=scales) | нет отдельного кода |
| Опоры/кабель-трассы ОРИОН | **никогда не называются отдельно** — тихо входят в сумму «фундамента Весов» (payment_group=foundation) | нет отдельного кода |

### 1.7 Тип фундамента (scope) — подтверждено: НЕ влияет на текст оплаты

Grep по `foundation_scope`/`installation_scope`/`scope_overrides`/
`metadata["scope"]` в `payment_renderer.py` и `payment_line.py` — **ноль
совпадений**. Эти значения читают только `clauses_context.py` →
`clauses_renderer.py` (клаузы: `install_site_label`, `scales_or_with_orion`)
и `terms_renderer.py` (раздел «Сроки»). `FOUNDATION_ACT` срабатывает
безусловно при наличии любой позиции с `payment_group=="foundation"`,
независимо от того, строительство это/доработка/курирование/материал
заказчика. Подтверждено на реальном эталоне (сценарий 6, материал
заказчика) — триггер-фраза «Акта выполненных работ по строительству
фундамента» идентична базовому сценарию.

### 1.8 Зимний бетон — подтверждено: НЕ влияет на блок оплаты

`winter_concrete`/`winter_surcharge`/`winter_surcharge_amount` — ноль
совпадений в `payment_renderer.py`, `payment_line.py`,
`payment_section.py`, `payment_lines_editor.py`. Влияют только на 3
клаузы в `data/clauses.yaml` (`winter_foundation_surcharge`,
`winter_foundation_surcharge_payment`, `winter_concrete_heating_option`),
гейтятся `winter_surcharge_allowed(foundation_scope)`
(`clauses_context.py:26-36`) — отдельно от графика оплаты. Подтверждено
на эталоне (сценарий 7): надбавка 200 000 руб. живёт в отдельных п.6-8
вне «2. Порядок оплаты», с явной отсылкой «в срок и на условиях,
предусмотренных п. 2.2» — не собственная строка оплаты. Дополнительно:
`winter_concrete` — мёртвая переменная (не тестируется ни одним
`applies_when` в `clauses.yaml`, только `winter_surcharge`), это уже
зафиксировано в `docs/audit_clauses_2026-06-10.md:138`.

### 1.9 Прочие находки инвентаря

- UI-превью split_by_items содержит статичную строку «Предоплата
  перечисляется в течение N банковских дней с момента подписания
  договора» (`payment_section.py:244-251`) — этой строки НЕТ ни в одном
  сгенерированном документе (`render_split_by_items` не читает
  `payment_days` вообще). Мёртвый текст для документов, живой только в
  UI-превью мастера КП.
- UI-лейбл группы «весы» в редакторе пресета статично всегда
  «Весы (включая ПАК ОРИОН)» (`payment_terms.json:82`, `label`),
  независимо от реального `has_orion` сделки — расходится с
  условной логикой самого рендера.
- `render_v2` может дать `postpay<0` без ошибки — только UI-warning
  (`payment_section.py:116-120`), не блокирует генерацию.
- Ни один из 9 эталонов не построен на `v1`/`v2`/`v3`/`custom` — все 9
  укладываются либо в `split_by_items`-подобный вывод, либо в
  `prepay_100`.

## ЧАСТЬ 2. Вывод по сценариям

### Сценарий 1 — Простая поставка, предоплата 100%

Эталон: `Автовесы _Поставка (1)_gemini.md:39-43`. Единственный документ
из 9 без раздела «Порядок оплаты» — заголовок «4. ЦЕНА И ПОРЯДОК
РАСЧЕТОВ», п.4.2, вывод буллетом. Структура/шаблон — `supply_contract.docx`
через `supply_filler.py` (единственный путь, где живёт `SUPPLY_TRIGGER_TEXTS`).
Только «весы», без фундамента/монтажа/доставки. Пресет — `prepay_100`.

**(a) КП** (`render_prepay_100`, `p1` хардкод 100):
```
100% предоплаты в течение 5 банковских дней с момента подписания договора. Производство начинается после поступления оплаты.
```

**(b) Спец/Договор** (`_build_non_split_lines`, `prepay_100`-фаза,
`SUPPLY_TRIGGER_TEXTS[SPEC_SIGNED]`):
```
1. Предоплата 100% от общей цены договора в размере 2 242 000 (Два миллиона двести сорок две тысячи) рублей, в т.ч. НДС 22%, в течение 5 (пяти) банковских дней с момента подписания настоящего Договора.
```

**(c) Эталон:**
```
- Предоплата 100% от стоимости настоящего договора в размере 2 242 000 (два миллиона двести сорок две тысячи) рублей в т.ч. НДС 22%, в течение 5 (пяти) банковских дней с момента подписания настоящего договора, на основании выставленного Поставщиком счета.
```

Расхождения: (1) объект «от общей цены договора» (код) vs «от стоимости
настоящего договора» (эталон); (2) нумерация «1.» vs буллет «-»;
(3) регистр прописи «Два» vs «два»; (4) **фраза «на основании
выставленного Поставщиком счета» не имеет аналога НИ В ОДНОМ коде** —
мёртвая эталонная фраза; (5) КП вообще не содержит суммы — эталон и
Спец её печатают.

### Сценарий 2 — Весы+монтаж+доставка+поверка, без фундамента

Эталон: `Автовесы_монтаж_gemini.md:20-24` — бланк-заготовка без чисел
(суммы `__________)`), проценты в файле **60/40** (весы) и **50/50**
(монтаж) — НЕ системный дефолт. Ниже — вывод кода на системном дефолте
(scales 50/50, delivery 0/100, install 0/100), сравнение по структуре.

**(a) КП:**
```
— Предоплата: 50% стоимости весов.
— Доплата за весы: 50% по уведомлению о готовности к отгрузке + 100% стоимости доставки.
— Оплата монтажа и поверки: 100% по факту выполнения монтажа и поверки.
```

**(b) Спец** (на дефолте `scales.postpay(50) ≠ delivery.postpay(100)` →
L3 уходит в flat):
```
1. Предоплата 50% от стоимости Весов в размере <сумма1> (<Пропись>) рублей, в т.ч. НДС 22%, в течение 5 (пяти) банковских дней с момента подписания настоящей Спецификации.
2. Доплата в размере <сумма2> (<Пропись>) рублей, в т.ч. НДС 22%, в течение 5 (пяти) банковских дней с момента получения уведомления о готовности Весов к отгрузке.
3. Доплата 100% от стоимости монтажных работ и поверки в размере <сумма3> (<Пропись>) рублей, в т.ч. НДС 22%, в течение 5 (пяти) банковских дней с момента подписания Акта выполненных работ по настоящей Спецификации.
```

**(c) Эталон** (проценты не дефолтные — 60/40/40/50):
```
2.1. Предоплата 60% от стоимости Весов в размере __________) рублей, в т.ч. НДС 22%, в течение 5 (пяти) банковских дней с момента подписания настоящей Спецификации.
2.2. Доплата 40% от стоимости Весов и доставки в размере __________) рублей, в т.ч. НДС 22% в течение 5 (пяти) банковских дней с момента получения уведомления о готовности Весов к отгрузке.
2.3. Предоплата 50% за монтаж и поверку Весов в размере __________) рублей, в т.ч. НДС 22%, в течение 5 (пяти) банковских дней с момента уведомления о готовности проведения монтажа автомобильных весов.
2.4. Доплата 50% за монтаж и поверку в размере __________) рублей, в т.ч. НДС 22%, в течение 5 (пяти) банковских дней с момента подписания Акта выполненных работ по настоящей Спецификации.
```

Ключевая находка: **эталон использует 60/40, где доплата весов (40%)
РАВНА доплате доставки (40%)** — единственный способ получить в коде
«чистую» процентную строку L3 вместо flat. На системном дефолте
(50/100) такое совпадение невозможно в принципе (0/100 доставки
никогда не равно 50/50 весов). Также: эталон систематически называет
монтаж через «за монтаж и поверку», код (Спец) — всегда «от стоимости
монтажных работ и поверки»; предлог «за» не встречается ни разу в коде
автоматически. Плюс — эталон всегда даёт предоплату монтажа (2.3), код
на дефолте (`iv.prepay=0`) её не даёт никогда.

## ЧАСТЬ 4. Чек-лист полноты

### Эталонные формулировки БЕЗ аналога в коде (нужно добавлять)

1. «на основании выставленного Поставщиком счета» (сценарий 1) — нет
   ни в одном `body_template`/`TRIGGER_TEXTS`.
2. Полностью безпроцентный/безобъектный формат «Предоплата/Доплата в
   размере X рублей» для ОДНОЙ группы без комбинирования (сценарий
   4, L1/L2) — код физически не может дать flat без коллизии двух
   групп; такой конфигурации (одна группа, но flat) не существует.
3. «Опоры и кабель-трассы ОРИОН» как отдельно называемый объект в
   строке оплаты + расширенный триггер «...фундамента и установке
   опор и кабель-трасс» (сценарий 9) — сумма есть, слов нет нигде.
4. Предлог «за» как авто-генерируемый вариант для монтажа/весов
   (сценарии 2,4,5) — в коде это либо «от стоимости», либо `None`
   (flat), никогда «за» без ручной правки в редакторе.
5. «Шеф-монтаж» как слово в строке оплаты (сценарий 5) — код всегда
   пишет «монтажных работ и поверки», даже когда `is_shefmontazh=true`.
6. Вариант триггера WORK_ACT «...по настоящему Договору» (сценарии
   4,5) — ни `TRIGGER_TEXTS` («по настоящей Спецификации»), ни
   `SUPPLY_TRIGGER_TEXTS` («поставки Весов Покупателю») не дают такую
   формулировку.
7. Указание типа фундамента в объекте оплаты («работ по строительству
   фундамента», не просто «фундамента») при материале заказчика
   (сценарий 6) — код всегда даёт «фундамента Весов» безотносительно
   scope.
8. Упоминание ОРИОН внутри текста триггера SHIPMENT_READY («готовности
   Весов **и ОРИОН** к отгрузке», сценарии 3,9) — `TRIGGER_TEXTS`
   хардкодит «Весов» без вариативности.
9. Полное название «Программно-аппаратного комплекса «ОРИОН»» вместо
   сокращения «(включая ПАК ОРИОН)» (сценарии 3,9).

### Код-ветки БЕЗ эталонного аналога (возможно мёртвые/непроверенные)

1. `render_v1`/`render_v2`/`render_v3`/`custom` — ни один из 9
   эталонов не использует эти пресеты; полностью непроверены реальными
   документами.
2. UI-превью-строка split_by_items «Предоплата перечисляется в течение
   N банковских дней…» — нет ни в одном сгенерированном документе.
3. Статичный UI-лейбл «Весы (включая ПАК ОРИОН)» независимо от
   реального `has_orion` — не встречается в документах (там условная
   логика верна).
4. `foundation_supervision` как единственный foundation-подобный
   item_key, не покрытый `resolve_payment_group` (падает в `scales`)
   — ни в одном из 9 эталонов курирование фундамента не встречается,
   поэтому неясно, баг это или намеренно.
5. `_V3_TRIGGER_MAP` схлопывание `after_installation`/`after_act` в
   один `WORK_ACT` — не проверено ни одним эталоном (v3 не используется
   нигде).
