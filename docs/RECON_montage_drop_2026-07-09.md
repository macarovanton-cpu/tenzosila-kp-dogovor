# Разведка: строка монтажа выпадает из Спецификации договора (шеф-монтаж)

Read-only. Код не менялся. Ветка `f1-payment-wording`.

## Сценарий

КП № 223311 (Кот Вася, ВЕСТА-СЛ-80-18), `installation_scope="shefmontazh"`.
Сумма КП **3 528 000** ≠ сумма договора **3 348 000**, разрыв **180 000** = цена
строки монтажа. Расходится только монтаж, всё остальное — копейка в копейку.

Живой снапшот КП № 223311 в Supabase/локально не найден в рамках разведки →
сценарий воспроизведён программно (весы СЛ-80-18 + фундамент-лайт + шеф-монтаж
+ доставка + поверка) через реальные продакшн-функции, минуя Streamlit UI.

## Итог одной строкой

**Детерминированный билдер-пайплайн строку монтажа НЕ теряет** — воспроизведено
прогоном `build_kp_snapshot → build_specification_items` на точной копии сценария,
строка «Шеф-монтаж и пусконаладка» с ценой 180 000 присутствует на обеих сторонах.
Разрыв — не в билдерах, а в интерактивном слое `st.session_state` страницы
`2_Договор.py` (см. «Где на самом деле теряется строка» ниже). F1/W6 не задет —
подтверждено диффом коммита.

## 1. Позиции КП (`src/spec_builder.py`)

`build_spec_items()` (spec_builder.py:235) итерируется по `state["options"]` без
фильтрации по `installation_scope`/`is_shefmontazh` — опция `install_default`
включается в spec_items КП всегда, если `enabled=True`, независимо от шеф-монтажа.

Имя позиции переопределяется в `_option_name()`:
```
src/spec_builder.py:161
    if item_key == "install_default" and state.get("is_shefmontazh"):
        name = "Шеф-монтаж и пусконаладка"
```
`item_key` остаётся **`"install_default"`** — тот же ключ, что и для обычного
монтажа, меняется только `name` (label). Цена берётся из
`opt_state.get("price")` — 180 000 в сценарии.

Подтверждено прогоном (см. приложение — репро-скрипт): в списке КП строка
`install_default` присутствует с `total=180000`.

## 2. Позиции договора (`src/contracts/from_kp.py`)

Два независимых билдера читают снапшот, оба смотрят на **тот же самый**
`data.options["install_default"]`:

- `build_spec_rows_from_snapshot()` (from_kp.py:354) — для старых 5-слотовых
  плейсхолдеров `СПЕЦ_П{1..5}` (используется только `build_specification_from_kp_snapshot`
  для текстовых полей, НЕ для таблицы позиций).
- `build_specification_items()` (from_kp.py:543) — основной путь, отдаёт
  `list[SpecItem]` для таблицы `Спецификации` (`spec_v2`), это то, что реально
  идёт в `fill_spec_v2` → `fill_spec_with_items` → строки docx-таблицы.

Оба билдера строят `options = _expand_orion_options(data.get("options") or {}, prices)`
(from_kp.py:388, 558) — без ОРИОН-бандла (наш сценарий) это просто `data.options`
без изменений, `install_default` остаётся в словаре.

Имя резолвится в `_resolve_option_name()`:
```
src/contracts/from_kp.py:192
    if key == "install_default" and installation_scope == "shefmontazh":
        return _SHEFMONTAZH_NAME   # "Шеф-монтаж и пусконаладка"
```
`spec_id` резолвится через `_option_key_to_spec_id("install_default")` →
`"installation"` (`src/contracts/spec_items.py:54-55`) — **безусловно**, до и
после проверки scope. Ни один из билдеров НЕ содержит условия вида
`if installation_scope == "shefmontazh": skip` или аналога — я явно искал такую
ветку и её нет ни в `build_spec_rows_from_snapshot`, ни в `build_specification_items`,
ни в `fill_spec_v2`/`fill_spec_with_items` (`src/contracts/filler.py:284-361`,
`src/contracts/spec_v2_filler.py:247-296` — там просто `for item in reversed(items)`,
без фильтра по scope/id).

**Репро (см. приложение) подтверждает**: `build_specification_items(kp_row, prices)`
на точной копии сценария (весы + фундамент + шеф-монтаж + доставка + поверка)
возвращает 5 строк, включая `id="installation", name="Шеф-монтаж и пусконаладка",
total=180000.0` — идентично КП-стороне. **Строка не теряется в билдере.**

## 3. item_key монтажа — один и тот же

`install_default` — единственный ключ и для обычного монтажа, и для шеф-монтажа,
на обеих сторонах (КП и договор). Разница только в `installation_scope`/
`is_shefmontazh`, которые управляют ТОЛЬКО текстом имени (label), не наличием
позиции. Договорный билдер матчит ключ шеф-монтажа корректно — это не «только
полный монтаж, шеф мимо» баг. Единый источник scope зафиксирован явно комментарием
`payment_wording.py:154-155` (W6, зеркалит `is_shefmontazh ⟺ installation_scope=="shefmontazh"`).

## Где на самом деле теряется строка

Раз детерминированный пайплайн (`state → build_kp_snapshot → build_specification_items
→ fill_spec_with_items`) строку не теряет, разрыв — в интерактивном слое
`st.session_state` на странице `src/pages/2_Договор.py`. Два конкретных
кандидата, оба вокруг «протухшего» состояния при переключении КП в одной
сессии браузера:

**(a) Тихо проглоченное исключение при загрузке КП — `src/pages/2_Договор.py:513-520`:**
```python
try:
    items = build_specification_items(kp_row, prices)
    set_spec_items(items)
    ...
except Exception as exc:
    _logger.warning("build_specification_items failed: %s", exc)
```
Если на РЕАЛЬНОМ (не синтетическом) снапшоте КП № 223311 `build_specification_items`
падает — `set_spec_items` просто не вызывается, `cs["specification"]["items"]`
остаётся тем, что было в session_state ДО этого рендера (пусто при первой
загрузке за сессию, или **позиции предыдущего КП**, если менеджер до этого уже
открывал другой КП в той же вкладке браузера). Ошибка видна только как
WARNING в логе — не блокирует «Сгенерировать» и не показывается в UI.

**(b) `st.data_editor` с фиксированным key не сбрасывается при смене КП —
`src/pages/2_Договор.py:805-850`:**
```python
edited_df = st.data_editor(
    _items_to_rows(spec_items), num_rows="dynamic", ...,
    key="spec_items_editor", ...,
)
...
_synced = _rows_to_items(edited_df, spec_items)
set_spec_items(_synced)          # ← перезаписывает КАЖДЫЙ рендер, не только по клику
```
Ключ `"spec_items_editor"` сбрасывается (`del st.session_state["spec_items_editor"]`)
только в двух местах — кнопка «+ Добавить позицию» (строка 836-838) и при
изменении сумм (847-850). При загрузке НОВОГО КП (блок 500-521) сброса нет.
`st.data_editor` хранит внутреннее состояние правок/удалений строк по ИНДЕКСУ,
привязанное к `key`, между реранами — если в этой же сессии ранее уже
взаимодействовали с редактором (другой КП, другой набор строк), протухшее
состояние может тихо применить старое удаление/правку по индексу к новому
списку позиций уже на первом рендере после загрузки КП № 223311, до нажатия
«Сгенерировать». `items_for_docx = get_spec_items()` (строка 1017) читает
именно этот засинхроненный список.

**Почему тесты/autoverify это не ловят:** `tests/autoverify/runner.py` — прямое
зеркало ТОЛЬКО блока генерации `2_Договор.py:959-1010` (см. комментарий в шапке
файла) и вызывает `build_specification_items()` напрямую, **минуя** и
try/except загрузки КП (513-520), и весь блок `data_editor` (805-865). Класс
бага структурно невидим для харнесса — совпадает с «Уроком цикла» в
`docs/STATUS.md` (баг выглядит как баг генератора, а на деле — протухший
session_state; воспроизводится только на живом сценарии).

Разграничить (a) и (b) можно только на живой сессии — прочитать логи
Streamlit вокруг загрузки КП № 223311 на WARNING `build_specification_items
failed` (подтвердит (a)), либо воспроизвести переключение между двумя КП в
одной вкладке и проверить, теряется ли строка сразу после загрузки, до
касания редактора (подтвердит (b)). Это вне объёма текущей read-only разведки.

## 5. Побочно — расхождения наименований КП↔договор (не баг, известные различия)

- **Весы «-Ц»**: договорный путь (`from_kp.py:376`, `:565`) жёстко приписывает
  суффикс `-Ц` в имени модели: `f"...ВЕСТА-{line}-{max_t}-{length}-Ц, max..."`.
  КП-путь (`spec_builder._format_model_name`) берёт `model["full_name"]` из
  `models.json` как есть — суффикс `-Ц` там не гарантирован для всех линеек.
- **Поверка**: КП-путь тянет `label` из `prices.json` через
  `resolve_dynamic_option_label` (spec_builder.py:171-178). Договорный путь
  использует захардкоженное `_SIMPLE_OPTION_NAMES["verification_default"] =
  "Поверка автомобильных весов с доставкой эталонов"` (from_kp.py:18) —
  **независимо** от `prices.json`.
- **Фундамент**: КП-путь строит имя шаблоном `_foundation_option_name()`
  (spec_builder.py:145-155): `"Фундамент железобетонный {execution} под весы
  {model_code}, {length}м"`. Договорный путь использует отдельный набор regex-
  шаблонов `_FOUNDATION_PATTERNS` (from_kp.py:51-64) с другой формулировкой
  (например, `"Фундамент пандусный «ЛАЙТ» под весы автомобильные ВЕСТА-{line},
  {N}м"`).

Все три — **намеренное** разделение систем именования, задокументированное в
самом файле:
```
src/contracts/from_kp.py:25-29
    # Эталонные наименования FIX_SPEC §E3b — ТОЛЬКО для пути договор/спецификация.
    # data/prices.json (label) не трогаем: тот же ключ читает и КП через
    # resolve_dynamic_option_label ... короткое эталонное имя там не
    # проверялось и уместно не везде
```
К разрыву сумм 180 000 эти расхождения отношения не имеют — цена в обоих путях
берётся из одного и того же `opt.get("price")`/`data.options[key]["price"]`,
меняется только текст.

## Приложение — репро-скрипт (не коммитился, временный)

`build_kp_snapshot(state)` → `installation_scope == "shefmontazh"`,
`options` содержит `install_default`. `build_specification_items(kp_row, prices)`
вернул 5 позиций, включая:
```
id="installation", name="Шеф-монтаж и пусконаладка", total=180000.0
```
Совпадает с КП-стороной (`build_spec_items` → `item_key="install_default",
total=180000`). Полный лог прогона — в истории команд сессии разведки.
