## 🟡 Корневой баг маппинга позиций (custom_N) — ОТЛОЖЕН, но важен

Диагностирован при разборе автовыбора. Шире, чем автовыбор.

- [ ] **Монтаж из конфигуратора КП сохраняется как custom-item (`id="custom_N"`),
  без `metadata["scope"]`.** `build_clauses_context` ищет строго
  `items_by_id["installation"]` → не находит → `installation_scope="none"`.
  Аналогично foundation. Цепочка: `from_kp.py:538-554` → `clauses_context.py:54-65`.
- **Последствия:**
  1. Автовыбор типа предлагает «Поставку» при наличии монтажа (монтаж невидим для scope).
  2. **ПОД ВОПРОСОМ (проверить!):** scope-обязательства в spec-договоре для
     монтажа/фундамента, когда они идут как custom. Монтаж в ~90% договоров. Если
     обязательства НЕ появляются на реальных spec-договорах — баг крупный (основной
     флоу). Если появляются — `custom_N` только про автовыбор.
  3. Монтаж попадает в сумму поставки (в supply-флоу это закрыто фильтром по
     `payment_group`, см. P1; но корневой scope по-прежнему слеп к custom).
- **Решение НЕ принято.** Кандидат: scope по `payment_group`
  (`installation_and_verification`) вместо строгого id. Нюанс: `payment_group`
  объединяет монтаж И поверку — нужен под-признак (диагностика по поверке не завершена).
- **Автовыбор типа договора — ОТЛОЖЕН.** Менеджер ставит тип вручную.

**Следующий шаг:** проверить на реальном КП с монтажом — появляются ли в
договоре-спецификации обязательства по монтажу. Разводит «custom_N только автовыбор»

## 🟢 Парсер реквизитов (label-anchored) — ЗАКРЫТ ПОКА (07-05)

> Остаточные проблемы есть — доработка отдельной сессией (в техдолге). Не блокер.

**Развилка решена:** формат вставки — полуструктурированный текст с русскими метками
(«ИНН: X КПП: Y» в одну строку). Это идеальный кейс для label-anchored парсинга, DaData
не нужен (избыточен, гонял бы реквизиты клиентов наружу). Подход — двухслойный:
(1) резка по меткам-якорям (значение = от метки до следующей метки),
(2) валидация по форме (ИНН \d{10}|\d{12}, БИК \d{9}, счета \d{20}) как страховка.

**История заходов:**
- Заход 1 (`c519aad`) — **откачен**. Sonnet-исполнение по Opus-плану налепило дыр:
  банк рвался на кавычках, основание жрало телефон, «Директор» попадал в ФИО.
  Урок: резка сегментов — задача «думать по ходу», не «выполнить по плану» → Opus, не opus-plan.
- Заход 2 — **закрыт (07-05)** (xhigh, plan). Тест-корпус: 4 реальные карточки
  (Ромашка/ИП Сидорова/Вектор/Гранит) с явными ожиданиями по каждому полю.
  Три корня: (1) банк — метка «Банк» только как начало поля, не граница; сегмент до
  следующей реальной метки, кавычки не участвуют; (2) слитный директор — срезать
  должность-приставку до ФИО; (3) основание — до метки, не до точки.

**ИНН — НЕ баг парсера.** Гейт по контрольной сумме (`_valid_inn`) верный и сохраняется:
битый ИНН в юр-документ пускать нельзя. Мои тестовые ИНН были невалидны по чек-сумме —
в тестах заменены на валидные, поведение не трогаем.

**Побочно закрыто:** залипание полей реквизитов — не очищались между «Распознать»,
показывали данные прошлой карточки. Фикс через `set_requisites` (replace + сброс
виджетов `w_*` + пересчёт пола). Проверено: 4 карточки подряд без перезагрузки — чисто.

⚠️ **После закрытия парсера:** проверить/применить UI/UX аудит (Playwright-отчёт) — он

## Известные ограничения

- `named_form` (преамбула «именуемое/ый») покрывает ИП vs ООО/АО/ПАО/ЗАО/НАО.
  Колхоз/Компания/Фирма и пр. → «именуемое» (не всегда грамматически точно). Принято
  как ограничение MVP.
- Между двумя таблицами docx нужен ≥1 абзац-разделитель, иначе Word их сливает
  (см. урок выше).
- ОРИОН-приложения (Шаг 10 договоров) — не реализованы как пакет документов.
- Контрольный лист: только пандусный и приямок.
- `монолитная_плита`: без стройзадания нет унифицированных чертежей.
- Supply-флоу на втором движке (docxtpl) — при изменениях шаблонов отдельная проверка
  плейсхолдеров + колонтитулов.
- Удаление позиций прайса через UI — пока no-op.
- Автовыбор типа договора не работает корректно (`custom_N`) — тип ставится вручную.
