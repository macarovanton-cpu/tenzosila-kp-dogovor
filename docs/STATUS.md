## 🟡 Корневой баг маппинга позиций (custom_N) — ОТЛОЖЕН, но важен

Диагностирован при разборе автовыбора. Шире, чем автовыбор.

- [ ] **Монтаж из конфигуратора КП сохраняется как custom-item (`id="custom_N"`),
  без `metadata["scope"]`.** `build_clauses_context` ищет строго
  `items_by_id["installation"]` → не находит → `installation_scope="none"`.
  Аналогично foundation. Цепочка: `from_kp.py:538-554` → `clauses_context.py:54-65`.
- **Последствия:**
  1. Автовыбор типа предлагает «Поставку» при наличии монтажа (монтаж невидим для scope).
  2. **ПОД ВОПРОСОМ (проверить!):** scope-обязательства в spec-договоре для
     монтажа/фундамента, когда они идут как custom. Монтаж в ~90% договоров. Если
     обязательства НЕ появляются на реальных spec-договорах — баг крупный (основной
     флоу). Если появляются — `custom_N` только про автовыбор.
  3. Монтаж попадает в сумму поставки (в supply-флоу это закрыто фильтром по
     `payment_group`, см. P1; но корневой scope по-прежнему слеп к custom).
- **Решение НЕ принято.** Кандидат: scope по `payment_group`
  (`installation_and_verification`) вместо строгого id. Нюанс: `payment_group`
  объединяет монтаж И поверку — нужен под-признак (диагностика по поверке не завершена).
- **Автовыбор типа договора — ОТЛОЖЕН.** Менеджер ставит тип вручную.

**Следующий шаг:** проверить на реальном КП с монтажом — появляются ли в
договоре-спецификации обязательства по монтажу. Разводит «custom_N только автовыбор»
vs «custom_N ломает основной флоу».

- Между двумя таблицами docx нужен ≥1 абзац-разделитель, иначе Word их сливает
  (см. урок выше).
- ОРИОН-приложения (Шаг 10 договоров) — не реализованы как пакет документов.
- Контрольный лист: только пандусный и приямок.
- `монолитная_плита`: без стройзадания нет унифицированных чертежей.
- Supply-флоу на втором движке (docxtpl) — при изменениях шаблонов отдельная проверка
  плейсхолдеров + колонтитулов.
- Удаление позиций прайса через UI — пока no-op.
- Автовыбор типа договора не работает корректно (`custom_N`) — тип ставится вручную.
