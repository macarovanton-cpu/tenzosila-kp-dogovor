## 🟡 Корневой баг маппинга позиций (custom_N) — ОТЛОЖЕН, но важен

Диагностирован при разборе автовыбора. Шире, чем автовыбор.

- [ ] **Монтаж из конфигуратора КП сохраняется как custom-item (id="custom_N"),
  без metadata["scope"].** build_clauses_context ищет строго
  items_by_id["installation"] → не находит → installation_scope="none".
  Аналогично foundation (id="foundation").
  Цепочка: from_kp.py:538-554 (build_specification_items, ветка custom) →
  clauses_context.py:54-65.
- **Последствия:**
  1. Автовыбор типа предлагает «Поставку» при наличии монтажа (монтаж невидим
     для scope). → из-за этого автовыбор и отложен.
  2. **ПОД ВОПРОСОМ (проверить!):** scope-обязательства в spec-договоре для
     монтажа/фундамента, когда они идут как custom. Монтаж в ~90% договоров.
     Если обязательства по монтажу НЕ появляются на реальных spec-договорах —
     баг крупный (затрагивает основной флоу). Если появляются — значит путь
     id="installation" где-то отрабатывает, и custom_N только про автовыбор.
  3. Монтаж попадает в сумму поставки (есть как позиция, scope не считается).
- **Решение НЕ принято.** Кандидат: определять scope по payment_group
  (installation_and_verification) вместо строгого id. Нюанс: payment_group
  объединяет монтаж И поверку — нужен под-признак чтобы не путать
  (диагностика по поверке не завершена).
- **Автовыбор типа договора — ОТЛОЖЕН** до решения по этому корню. Менеджер
  ставит тип вручную (он и так знает, нужен ли договор поставки).

**Следующий шаг по spec-договору (когда вернёшься к проверке):** проверить на
реальном КП с монтажом — появляются ли в договоре-спецификации обязательства
по монтажу. Это разводит «custom_N только автовыбор» vs «custom_N ломает
основной флоу».
