# Админ-панель прайса — фазы и задачи

## Дорожная карта

| Фаза | Название | Цель | Не входит |
|------|----------|------|-----------|
| **0** | Разведка (R1–R5) | Подтвердить факты кода до реализации. Выход: заполненный раздел разведки в ARCHITECTURE.md. | Код |
| **1** | PDF-first обновление прайса | Цикл: загрузил → проверил → применил → откатил | Коэффициенты, история версий >1, правка справочников |
| **1.5** | Уборка | Удаление по утверждённой описи R5, атомарными коммитами, тесты после каждого | — |
| **2** | Ценовые правила | Коэффициенты вилки из `config.py` → `data/pricing_rules.json`, редактируются в UI, КП их читает | — |
| **3** | Бизнес-диагностика и защита | Подсветка аномалий (скачок цены >X%, осиротевшая опция, расхождение вне вилки), предупреждение о просроченном прайсе | — |
| **4** | UX-полировка | Только то, что всплыло в эксплуатации. Ограничить списком из практики | — |
| **5** | Регрессия и безопасный выпуск | e2e КП и договора на обновлённом прайсе, тег версии | — |

**Риск Фазы 2:** КП завязан на числа коэффициентов — нужна регрессия расчёта.
**Риск Фазы 3:** ложные срабатывания диагностики.

**Отложенное (enterprise, по конкретной боли):** история версий с датами, управление
`payment_terms.json`, роли, аудит-лог, согласования, БД-версионирование. Заранее не проектируем.

### Задача 2 — Парсер дилерского PDF

**Цель:** дилерский PDF → `list[PriceItem]` (модели + железные опции, до раздела ВЕСТА-М).

**Создать:** `src/admin/price_pdf_dealer.py`; наполнить тест.

**Не трогать:** `contracts/*`, существующий backend.

**Границы парсинга:** парсить ТОЛЬКО секцию автовесов ВЕСТА (линейки ФЛ/СЛ/Ф/С/П/СБ).
Остановиться на строке-заголовке «Автомобильные весы ВЕСТА-М» — всё после неё (М1/М2,
платформенные, прочее) НЕ парсить, это вне scope.

**Дилерская цена:** брать из PDF напрямую (колонка дилерской цены), НЕ вычислять формулой.

**Разведка внутри задачи (выполнить ПЕРВЫМ делом, до написания парсера):** проверить в коде,
есть ли формула retail×0.92 / dealer_discount в генерации prices.json или в расчёте КП;
убедиться, что дилерская цена в prices.json ХРАНИТСЯ числом, а не вычисляется на лету.
Если обнаружится, что КП вычисляет дилерскую цену формулой на лету (а не читает из
prices.json) — ОСТАНОВИТЬСЯ и сообщить, не продолжать. Иначе продолжать по плану.

**Маппинг ключей (критично):** парсер обязан строить model_id через ФИКСИРОВАННУЮ таблицу
соответствия «линейка в PDF → буква ключа». Ключи в prices.json кириллические:
vesta-фл-60-18 (НЕ vesta-fl). Тест обязан проверять ТОЧНОЕ совпадение всех model_id
с ключами в текущем prices.json (загрузить prices.json, сверить множества ключей моделей).
Несовпадение даже одного ключа = провал задачи (иначе diff покажет ложное «удалено 59 +
добавлено 59», round-trip сломается).

**Тест:**
- Число строк моделей в ожидаемом диапазоне
- ≥N опций
- Выборочные цены точны: ФЛ 60т-12м = 1 140 296 / 1 049 072; пандус Ф/С = 380 000
- Все model_id точно совпадают с ключами моделей в prices.json

**Ручная:** первые 10 позиций глазами.

**Review:** Codex. **Модель:** Opus если R3 показал грязный вывод, иначе Sonnet/medium-high. **Коммит:** `feat: парсер дилерского PDF`.

### Задача 5 — Сервис записи: backup + atomic + rollback

**Цель:** безопасная запись и откат.

**Создать:** `src/admin/price_write_service.py`; тест на temp-каталоге.

**Изменить:** после записи нового `prices.json` ОБЯЗАТЕЛЬНО вызвать `load_prices.clear()`
(функция `load_prices` в `src/data_loader.py`, декорирована `@st.cache_data(ttl=3600)`).
Без этого КП и договор считают по старому прайсу до истечения TTL (1 час).

**Не трогать:** схему `prices.json`.

**Тест:**
- Запись создаёт бэкап и валидный прайс
- Round-trip проверяет идемпотентность формата (prices.json → запись → чтение → структурно
  идентично исходному), НЕ побайтовое совпадение значений (дилерские цены могут отличаться
  на ±1 руб, см. ARCHITECTURE п.1a)
- Откат возвращает прежний
- Имитация сбоя не бьёт исходный

**Review:** Codex (критично). **Модель:** Opus/high. **Коммит:** `feat: запись прайса с бэкапом и откатом`.

### Задача 7 — Разделение валидации на блокеры/предупреждения

**Цель:** обёртка над `validate_prices` по согласованному списку.

**Не трогать:** `price_validator.py`.

**Тест:**
- Блокеры: нулевая/пустая цена при `on_request: false`, розница < дилера, дубль.

**Review:** нет. **Модель:** Sonnet/low-medium. **Коммит:** `feat: разделение валидации прайса`.
