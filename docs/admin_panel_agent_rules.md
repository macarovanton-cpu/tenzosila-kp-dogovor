# Admin Panel Agent Rules

Правила для задач `AP-*` (`tasks/`, `docs/admin_panel_task_breakdown.md`,
`docs/admin_panel_status.md`). Контекст: один разработчик + AI-агенты (Codex,
автономные агенты). Цель — польза и безопасность MVP, а не enterprise-масштаб.

## Рабочий режим

- **Брать только одну задачу за запуск** — ту, что указана в `tasks/NEXT_TASK.md`.
- Открыть task-файл, выполнить **только его scope** и остановиться.
- **Не переходить к следующей задаче автоматически.** Следующую задачу берёт
  только человек (обновив `NEXT_TASK.md`) или по явной команде пользователя.
- **После задачи — commit и стоп.** Один commit на задачу, затем краткий отчёт.
- Работать в `main`: новые ветки в этом проекте не создавать.
- Все shell-команды — с префиксом `rtk`.
- Перед исследованием кода сначала CodeGraph, затем чтение конкретных файлов.
- В начале читать `docs/STATUS.md`; для админки основной status —
  `docs/admin_panel_status.md`.
- **Если задачу можно сделать проще без потери пользы — выбрать простой вариант**
  и зафиксировать это в `notes`.

## Гейт по версии (v2.1)

- Задачи **Фазы 1** (локальные, JSON-only, без UI/БД) можно делать в любой момент.
- Задачи **Фазы 2+** (любой Streamlit-UI, БД, миграции, pricing, договор) —
  **не начинать до закрытия v2.1** (см. `docs/STATUS.md`). Если v2.1 не закрыт и
  задача не из Фазы 1 — пометить `blocked` (причина: «гейт v2.1») и остановиться.

## Уровни безопасности агента

Каждая задача в `admin_panel_status.md` имеет один из уровней. Агент обязан его
проверить **до** начала работы:

| Уровень | Можно ли автономно/ночью | Что делать |
|---|---|---|
| `safe_for_autonomous_agent` | Да | Выполнять, тестировать, коммитить. |
| `requires_human_review_after` | Да, но | Выполнить, **пометить `human_review: pending`**, не считать задачу «готовой к использованию» до проверки человеком. |
| `requires_human_decision_before` | Нет | Нужно решение человека (схема БД, бизнес-порог, список ролей). Без решения — `blocked`. |
| `do_not_run_autonomously` | **НЕТ** | Только с человеком в цикле. Автономный/ночной агент эту задачу **не берёт** — останавливается с пометкой. |

`do_not_run_autonomously` распространяется на всё, что трогает: расчёт цены
(`pricing.py`, виджеты цен), snapshot/HANDOFF КП→Договор, договорный экран
`src/pages/2_Договор.py`, генерацию DOCX, применение миграций к реальной
Supabase.

## Ограничения изменений (hard rules)

- **Не убирать fallback на `data/prices.json`.** Любой active-loader обязан
  безопасно откатываться на JSON при недоступности БД/отсутствии active-версии.
- **Не писать в `data/`-справочники из UI/кода** без отдельной approved-задачи и
  команды пользователя. Прайс и справочники в `data/` правятся вручную/в git.
- **Не менять расчёт цены** (`src/pricing.py`, ценовые виджеты) вне задач Фазы 4
  и только при `do_not_run_autonomously` + parity-тестах.
- **Не менять snapshot КП** (`src/storage/snapshot_builder.py`) и HANDOFF
  КП→Договор без явной задачи и проверки человеком.
- **Не менять договорный экран** `src/pages/2_Договор.py` без отдельной задачи,
  явно это разрешающей.
- **Не применять миграции к реальной Supabase автономно.** Миграция = отдельный
  файл в `supabase/migrations/`; применение к production — только человеком.
- **Не удалять существующие рабочие функции** и чужой dead code.
- Не редактировать `knowledge_base/`.
- Не добавлять зависимости в `requirements.txt` без согласования.
- Не делать Битрикс-интеграцию, ORM или FastAPI/React rewrite в задачах AP, пока
  это не оформлено как отдельный approved task-файл.
- НДС в РФ = 22%. Не менять на 20%. Дефолт оплаты — `split_by_items`.

## Если задача упирается в решение бизнеса

Пометить `blocked` и остановиться, если требуется выбрать:

- реальные пороги скидок, маржи или согласования;
- список ролей и прав сверх базового набора;
- юридически значимый текст договора или КП;
- формат реального прайс-листа, не описанный в task-файле;
- регламент хранения файлов и персональных данных;
- форму/состав схемы БД.

Причину указать в `notes` в `docs/admin_panel_status.md`.

## Тесты и проверка

- Запускать релевантные тесты из task-файла.
- Для pricing/storage/snapshot — добавлять unit/storage tests.
- Для UI — добавлять хотя бы smoke/AppTest.
- Перед commit: `rtk python -m pytest tests/` (или явно объяснить, почему полный
  прогон невозможен; для чисто локальных задач допустим focused-прогон новых
  тестов + затронутых).
- Если красное — **не коммитить**.

## Status и commit

После работы агент обязан:

1. Обновить `docs/admin_panel_status.md`:
   - `status`: `done` / `blocked` / `in_progress`;
   - `commit`: hash или `not_committed`;
   - `tests`: что запускалось;
   - `human_review`: `pending`, если уровень это требует или есть риск;
   - `notes`: коротко важное (включая «выбран простой вариант», если так).
2. Если менялись project-status шаги — обновить `docs/STATUS.md`.
3. Один commit, Conventional Commits на русском (напр. `feat: добавить валидатор
   формата прайса`).
4. **Остановиться и кратко отчитаться. Не брать следующую задачу.**

`git push` не делать без явной команды пользователя.
