# План тендерного модуля (фаза ФТ)

Дата: 2026-07-11. Статус: детальный план фазы ФТ по Д-3
(`docs/MIGRATION_PLAN_DELTA.md`). Исполнение — строго после Ф2 (решение
автора от 2026-07-11: один открытый фронт). Инварианты И-1…И-6 и правило
границ модулей Д-2 действуют без изменений.

Killer-фича MVP-1: **нормализация любого ТЗ в единую каноническую форму**.
Загрузил тендерный пакет (20–30 стр., ~половина — сканы) → на выходе всегда
одна и та же форма + детерминированный флаг нестандарта. Принцип модуля:
**AI не источник истины** — LLM читает и заполняет форму с цитатами, код
сверяет с каталогом и ставит флаги, человек подтверждает.

---

## 1. Скоуп-лок

**Входит в MVP-1:**
- Загрузка пакета: PDF (текстовый и скан — один путь), DOCX, XLSX, ZIP;
  чекбокс-выбор файлов в анализ (человек-фильтр вместо классификатора).
- `extract()`: один vision-вызов LLM на весь выбранный пакет → каноническая
  форма (Pydantic), каждое листовое поле с цитатой-источником.
- `verify()`: детерминированная сверка твёрдых полей с единым каталогом
  (`core/catalog/` ← `prices.json` + `models.json`); вне каталога =
  нестандарт/`needs_review`. Флаг ставит код, не модель.
- Нарративная база `knowledge_base/tender_nuances.md` — контекст для LLM,
  грузится целиком.
- Хранение: `ai_extraction` (иммутабельно) + `current_values` (правки
  человека), JSONB.
- Редактируемая форма в портале (модуль в оболочке Д-1, AntD).
- Флаг «работы вне базовой зоны» (правило §3, без расчёта).

**НЕ входит (закреплено, не возвращать):**
go/no-go «наш/не наш»; генерация задачи техотделу; заполнение тендерных
форм заказчика; формульный пересчёт дальних регионов; архив прошлых ТЗ как
обучающая база; вектора/pgvector/embeddings/hybrid search; Bitrix24/CRM/
автономные агенты/MCP; деплой; auth (закрыт общим bearer-токеном портала);
реквизиты площадки (НМЦ, дедлайн, наименование площадки — автор видит их
на площадке за 10 секунд).

**Предпосылки фазы:** `core/` существует (P0-05+), каталог выделен в
`core/catalog/` (Д-2), портал-оболочка живёт (Ф1), договоры въехали (Ф2).
Задачи ФТ-02/ФТ-03 (нарратив, корпус) выполнимы заранее — кода не требуют.

## 2. Каноническая схема (`core/tender/schema.py`)

### 2.1. Обёртка листового поля

```python
Status = Literal["ok", "needs_review", "missing"]

class ExtractedField(BaseModel, Generic[T]):
    value: T | None = None
    source_quote: str | None = None   # дословная цитата из документа
    doc: str | None = None            # имя файла-источника
    page: int | None = None           # страница (для PDF)
    status: Status = "missing"
```

**Правило заполнения** (дублируется в промт LLM и в валидатор `verify()`):
- нет прямого основания в документе → `missing` (value=None);
- значение выведено косвенно / неоднозначно / вне каталога → `needs_review`;
- `ok` — только с непустой `source_quote`. LLM НЕ имеет права дозаполнять
  «здравым смыслом» — это главный урок старого экстрактора (§6).

### 2.2. Блоки схемы

```python
class TenderExtraction(BaseModel):
    meta: TenderMeta
    positions: list[TenderPosition]   # ~15-20% тендеров многопозиционные
    works: TenderWorks
    terms: TenderTerms
    nonstandard: list[NonstandardItem]
```

- `TenderMeta`: `customer_name`, `delivery_place`, `install_place`,
  `install_region` (enum субъектов РФ — нужен для правила §3),
  `procurement_mode: Literal["44fz", "223fz_custom", "223fz_structured"]`
  (44-ФЗ / 223-ФЗ по нашей форме / 223-ФЗ структурированный).
- `TenderWorks`: монтаж, фундамент (кто строит + тип), шеф-монтаж, ПНР,
  доставка, поверка (мы/заказчик — зеркало `allow_customer_value` прайса).
  Каждое — `ExtractedField`.
- `TenderTerms`: срок поставки (дни + тип дней как в документе), гарантия
  (месяцы), **условия оплаты** (аванс/постоплата/график — критичны для
  решения об участии; решение автора №3).
- `NonstandardItem{description, source_quote, doc, page, reason}` — всё,
  что не уложилось в твёрдые поля; всегда `needs_review`. LLM аннотирует
  ПОЧЕМУ это нестандарт, но флаг остаётся за кодом.

### 2.3. `TenderPosition` — твёрдые поля и их источники в каталоге

Каждое твёрдое поле обосновано реальной структурой `data/prices.json` /
`data/models.json` / справочника — не выдумано:

| Поле | Тип | Источник верификации |
|---|---|---|
| `qty` | int | — (число комплектов; в КП — `model_qty`) |
| `platform_type` | str | `models.json line_defaults[].platform_type` (Сплошная / Сплошная облегчённая / Колейная / Колейная облегчённая / Сплошная усиленная) |
| `line` | str | `models.json _meta.scope.lines` (С/СЛ/Ф/ФЛ/П — MVP); экстрактор знает и Б/К/М1/М2/СБ/ФБ из справочника §«Правила обозначения модификаций» — они валидны для извлечения, но вне MVP-каталога → нестандарт |
| `max_load_t` | int | `_meta.scope.max_loads_t[line]` (С: 40–120; СЛ/ФЛ: 40–80; Ф: 40–100; П: 80–100) |
| `length_m` | float | `_meta.scope.lengths_m` = {18, 20, 22, 24}; ряд 7–16 м существует в справочнике, но вне MVP → нестандарт |
| `width_m` | float | `models[].width_m` (= 3 м у всех моделей MVP) |
| `sections` | int | `models[].sections` (3 для 18 м, 4 для 20–24 м) |
| `sensors_count` | int | `models[].sensors_count` (8/10) |
| `sensor_model` | str | `equipment_defaults.sensor.alternatives[].id` (9 моделей: Zemic/Keli/HBM/МВ-150) |
| `sensor_signal` | digital/analog | литера «Ц» обозначения + `indicator.alternatives[].signal` |
| `indicator_model` | str | `equipment_defaults.indicator.alternatives[].id` (ТИТАН 3ЦС/12/12С, Микросим М0601) |
| `temp_min_c` | int | `temp_range_c` датчиков/индикаторов; код проверяет, покрывает ли хоть одна комбинация требование ТЗ (напр. −40 °C → дефолтный Zemic −30…+40 не проходит, Keli/HBM проходят; −55 °C → нестандарт) |
| `axle_load_t` | float | `models[].axle_loads_t` (single/double/triple/quad) |
| `accuracy` | e_kg, n, dual | `models[].verification_division_kg`, `n_intervals`, `dual_range` (Таблица 6 описания типа) |
| `mounting` | str | `line_defaults[].mounting_options` (приямок 0,5–2 м / рама с пандусами 7°) + семейство `options.foundation_*` |
| `options[]` | list[str] | ключи `prices.json options` (ограждение ЛАЙТ/НОРМА, пандусы, люки, закладные, Т-резина, бытовка, навес, ПАК ОРИОН Лайт/Стандарт/+/Автоматика/+, рама, калибровка) + проверка `applies_to_lines` / `applies_to_lengths` |
| `model_explicit` | str/None | если ТЗ прямо называет модель ВЕСТА (или конкурента — тогда `needs_review`) |

### 2.4. КП-совместимость (жёсткое требование)

`verify()` детерминированно резолвит
`matched_model_id = f"vesta-{line}-{max_load_t}-{length_m}"` — это ровно
ключ `prices.json models{}` и ровно `model_id` КП-конфигуратора.
`options[]` — ровно ключи `prices.json options{}`. Долгосрочный мост
«разобрал ТЗ → сразу сгенерил КП» заложен на уровне идентификаторов,
конвертер не понадобится.

## 3. Каталог-верификатор

**Без скрипта-генератора** (осознанное отклонение: генерируемый артефакт —
второй файл, который разъезжается с прайсом при каждом обновлении;
рантайм-вывод дрейфовать не может). Enum'ы и диапазоны строятся в рантайме
из уже загруженных `prices.json` + `models.json` — функция
`catalog_view()` в `core/catalog/tender_view.py` (@lru_cache поверх тех же
загрузчиков, что использует КП; обновился прайс — обновился верификатор).

`CatalogView` (обычный frozen-dataclass/BaseModel):
- `lines`, `lengths_m`, `max_loads_by_line` — из `models.json _meta.scope`;
- `model_ids` — ключи `prices.json models{}` (наличие цены = продаваемость);
- `sensor_ids/temp_ranges`, `indicator_ids/signals` — из `equipment_defaults`;
- `platform_types`, `mounting_options`, `warranty_months` — из `line_defaults`;
- `option_keys` + `applies_to_lines/lengths` — из `prices.json options{}`;
- `axle_loads`, `accuracy` (e/n/dual_range) — из `models[]`.

**В LLM-контекст** каталог попадает как компактный markdown-дайджест,
рендеримый той же `catalog_view()` (функция `to_markdown()`), — не руками,
не вторым файлом.

**Дальний регион (решение автора №4).** Whitelist регионов «зоны прайса»
не существует и не изобретается: оборудование продаётся по единому прайсу
по всей РФ — по региону НЕ флагится никогда. Работы (монтаж/фундамент/ПНР)
считаются по месту; формально зафиксированной зоны нет. Правило `verify()`:
в ТЗ есть работы И `install_region` ≠ Воронежская область →
`needs_review` с пометкой «монтажные работы вне базовой зоны, стоимость
определяется по месту».

## 4. Нарративный слой

`knowledge_base/tender_nuances.md` — пишет автор (задача ФТ-02: Code ведёт
интервью в чате, автор отвечает, Code структурирует в markdown). Коммитится
в репозиторий (решение автора №5): инженерная кухня без данных клиентов,
без неё модуль не работает.

Формат — markdown, секции-темы (ориентир, автор дополняет):
- конструктив и смысл линеек «своими словами» (когда СЛ вместо С, почему П
  почти не продаётся, что такое Б/К/М1/М2 и почему мы их не предлагаем в MVP);
- что мы НЕ делаем: ЖБ-платформы на производстве не льём (СБ/ФБ не
  производились), поосные без Госреестра;
- работы в прайсе рассчитаны на ~300–400 км от Воронежа, дальше —
  индивидуальный пересчёт (это контекст для LLM-аннотаций; жёсткий флаг —
  правило §3);
- спецдатчики и температурные требования (какие ТЗ-формулировки к чему ведут);
- нестандартные функции (интеграции, ПО, автоматизация → семейство ОРИОН
  или нестандарт);
- типовые ловушки ТЗ (противоречивые требования, ГОСТ-ссылки, «аналог»).

Грузится в system-промт **целиком** вместе с каталог-дайджестом §3.
Векторов/pgvector/embeddings нет — KB маленькая, влезает в контекст;
это осознанное решение, не упущение.

## 5. `extract()` / `verify()` — сигнатуры, границы, инфраструктура

```python
# core/tender/extract.py — чистая функция (И-1): не знает про Streamlit,
# FastAPI, session_state, файловую систему проекта.
def extract(docs: list[TenderDoc], *, llm: LLMClient,
            context: TenderContext) -> TenderExtraction: ...
# TenderDoc{name: str, mime: str, data: bytes}
# TenderContext{catalog_digest_md: str, nuances_md: str}

# core/tender/verify.py — детерминированный: БЕЗ LLM, БЕЗ I/O.
def verify(x: TenderExtraction, catalog: CatalogView) -> TenderExtraction: ...
# возвращает копию с пересчитанными status, matched_model_id,
# дополненным nonstandard[]; ai_extraction до verify не сохраняется —
# сохраняется результат verify (он тоже детерминирован от входа)
```

### 5.1. LLM-провайдер — вилка (решение автора №1)

Провайдер НЕ фиксируется до прогона golden-корпуса. Протокол в
`core/shared/llm.py` (потребители в перспективе — тендеры и реквизиты):

```python
class LLMClient(Protocol):
    def extract_structured(self, *, system: str,
        blocks: list[ContentBlock],          # text | image (PNG bytes)
        schema: type[BaseModel],
        max_retries: int = 2) -> BaseModel: ...
```

Две реализации, выбор — одна строка settings
(`TENDER_LLM=anthropic|openrouter` + `TENDER_LLM_MODEL`):
- `AnthropicLLM` — официальный SDK (новая зависимость, добавляется только
  с одобрения автора, в ФТ-06);
- `OpenRouterLLM` — уже установленный `openai`-клиент + существующий ключ.

**Общий путь (обе реализации дают одинаковый результат):**
любой PDF → `pymupdf` (уже в requirements) растеризует страницы в PNG,
кап ~50 стр./документ (превышение — явная ошибка пользователю, не молчание)
→ image-блоки. Текстовой слой НЕ детектируем — не ветвим: текстовые PDF
идут тем же vision-путём. JSON-схема (`schema.model_json_schema()`)
вставляется в промт; ответ парсится и валидируется Pydantic; невалиден →
ретрай с текстом ошибки валидации.

Native PDF-блоки Anthropic и forced tool call в общем пути НЕ используются:
OpenRouter их гарантированно не даёт, а два разных пайплайна дали бы
несравнимые результаты корпуса. Чем реализации отличаются: только
транспорт/аутентификация и формат image-блока конкретного API. Что
теряется: на Anthropic — server-side PDF-рендер и жёсткий tool-forcing
(компенсировано валидацией + ретраем); на OpenRouter — риск даунгрейда на
не-vision провайдера (пиновать провайдера в параметрах запроса).

### 5.2. Конвертация не-PDF

DOCX → markdown (python-docx: таблицы построчно, параграфы); XLSX →
markdown-таблицы (openpyxl — приходит с pandas, отдельная зависимость не
нужна); ZIP → распаковка + список файлов для чекбоксов. Всё в
`core/tender/convert.py`.

### 5.3. Один вызов на пакет

Все выбранные файлы пакета уходят ОДНИМ вызовом (изображения + markdown
блоками, каждый блок подписан именем файла) — кросс-документный контекст
(спецификация в XLSX уточняет ТЗ в PDF). Распознавание и извлечение слиты:
отдельного OCR-пайплайна нет.

### 5.4. Что переиспользуется из существующей инфраструктуры

- OpenRouter-ключ и `openai`-клиент (как транспорт `OpenRouterLLM`);
- паттерн секретов через settings (после P0-06 — env, не `st.secrets`);
- принцип `requisites_parser.py` «неоднозначно → пусто, не угадываем» —
  переносится в промт и в `verify()` как правило статусов.

Код `src/contracts/extractor.py` образцом НЕ является (см. §6).

## 6. Чему учит существующий экстрактор: что делать иначе

По итогам разведки `src/contracts/extractor.py` + промтов:

1. **Ответ = `json.loads` сырого текста**, ни валидации схемы, ни ретрая →
   у нас JSON-схема в промте + Pydantic-валидация + ретрай с текстом ошибки.
2. **LLM нормализует юридически значимые данные** (суммы прописью, падежи,
   «Аванс»→«Предоплата», а при несходящейся арифметике — пересчёт сумм
   позиций под ИТОГО) → у нас LLM только копирует с цитатой; любые
   преобразования — код, после подтверждения человеком.
3. **«Если обозначение неполное — восстанови по контексту»** — прямое
   приглашение к галлюцинации → у нас запрет в промте + `needs_review`;
   резолвит модель-ид код (`verify()`), а не LLM.
4. **Пустая строка для «не нашёл»** неотличима от «нашёл пустое» → у нас
   трёхзначный `status` + обязательная `source_quote` для `ok`.
5. **Жёстко зашитые страницы 3–5 КП** — документ другой структуры молча
   теряет данные → у нас документ целиком; кап страниц — явная ошибка.
6. **Сканы**: pdfplumber возвращает пустой текст, модель фантазирует на
   пустом входе → у нас vision-путь для любого PDF без детекции слоя.
7. **Захардкожены модель и провайдер, связка с `st.secrets`** → у нас
   `LLMClient` + settings, `core/` без Streamlit (И-5/P0-06).

## 7. Пайплайн

```
upload (файлы/ZIP) ──► список файлов + число страниц
        │                    │ чекбоксы человека (шум — договор площадки,
        ▼                    ▼  инструкции — не идёт в анализ)
convert.py: PDF→PNG-страницы (кап 50), DOCX/XLSX→markdown
        ▼
extract(docs, llm, context)         ← 1 vision-вызов на пакет
        ▼
Pydantic-валидация (внутри LLMClient, ретрай)
        ▼
verify(extraction, catalog_view())  ← детерминированно: статусы,
        ▼                              matched_model_id, nonstandard[]
сохранение: tenders.ai_extraction   ← ИММУТАБЕЛЬНО (что сказала модель
        ▼                              после verify; больше не трогается)
форма в портале (статусы подсвечены: ok / needs_review / missing)
        ▼
правки человека ──► tenders.current_values (JSONB)
```

Diff `ai_extraction` ↔ `current_values` = бесплатный аудит качества
извлечения (какие поля человек правит чаще всего → куда крутить промт).

**Хранение** — таблица `tenders` (Supabase, через репозиторий-паттерн
P0-15, в реляционные колонки не нормализуем):
`id, title, created_at, created_by, status, files_meta jsonb,
ai_extraction jsonb, current_values jsonb`.
Исходные файлы ТЗ в MVP-1 не храним (files_meta — имена/страницы/хэши);
если понадобится — Supabase Storage отдельной задачей.

## 8. Место в архитектуре

```
core/
  catalog/
    tender_view.py      # CatalogView + markdown-дайджест (§3)
  shared/
    llm.py              # LLMClient + AnthropicLLM + OpenRouterLLM (§5.1)
  tender/
    schema.py           # каноническая схема (§2)
    convert.py          # PDF/DOCX/XLSX/ZIP (§5.2)
    extract.py          # чистая функция извлечения (§5)
    verify.py           # детерминированный верификатор (§3, §5)
    prompts/extract_tender.txt
```

Правило границ Д-2 соблюдается: `core/tender/` импортирует только
`catalog/`, `shared/`, `storage/`, `schemas/` — не `kp/`, не `contracts/`
(grep-проверка G0 расширяется на `tender/`).

**API** (`/api/tender/*`, зарезервирован Д-3; bearer, конверт ошибок §3
оригинала):
- `POST /api/tender/upload` — multipart → `{files: [{name, pages, mime}]}`
  (для чекбоксов);
- `POST /api/tender/analyze` — `{files: [...], selected: [names]}` →
  `TenderExtraction` (после verify); `run_in_threadpool`;
- `POST /api/tender` — сохранить `{title, ai_extraction, current_values}`;
- `GET /api/tender/{id}`, `GET /api/tender?recent=N`;
- `PATCH /api/tender/{id}/values` — только `current_values`.

**UI** — модуль портала (оболочка Д-1, AntD `Upload`/`Form`/`Table`),
строится ПОСЛЕДНИМ (§9, риск вперёд). **Golden/тесты:** LLM-вызовы вне
golden (принцип §2.2 оригинала) — записанные фикстуры сырого ответа;
живой вызов только в смоуках ФТ-06/ФТ-08 и eval.

## 9. Задачи фазы ФТ (loop-структура)

Принцип: **сила верификатора = уровень автономии**. Порядок «риск вперёд»:
качество извлечения доказывается на реальных ТЗ (ФТ-08) ДО постройки UI.
Если извлечение — мусор, UI не нужен.

Формат: stop condition / верификация / тип loop / шапка.

---

**ФТ-01. Каталог-view + дайджест** — `core/catalog/tender_view.py`
- Stop: `catalog_view()` возвращает все поля §3; `to_markdown()` рендерит
  дайджест ≤ ~2К токенов.
- Верификация: pytest — enum'ы поэлементно совпадают с `prices.json`/
  `models.json`; смена значения в JSON видна во view без пересборки.
- Loop: goal-based. | sonnet / medium / code / ~40 мин.

**ФТ-02. Нарративная база** — `knowledge_base/tender_nuances.md`
- Stop: автор подтверждает: «всё, что держу в голове о нестандарте, — тут».
- Верификация: глаз автора (источник — его голова, машинного критерия нет).
- Loop: turn-based (интервью: Code спрашивает по секциям §4, автор
  отвечает, Code структурирует). | opus / high / чат / ~1–2 ч автора.

**ФТ-03. Golden-корпус ТЗ** — локальная папка, `TENDER_CORPUS_DIR` в env
- Stop: 4–5 реальных комплектов (чистый PDF; скан; DOCX+XLSX-микс;
  многопозиционный) + к каждому эталонная каноническая форма, размеченная
  автором (JSON по схеме §2).
- Верификация: глаз автора (он — разметчик).
- Loop: turn-based. | opus-plan для шаблона разметки, дальше автор / — /
  чат / ~2 ч автора.
- ⚠️ **Выполнима ЗАРАНЕЕ, вне фазы ФТ** — от кода не зависит; автор
  собирает в ближайшие дни. Корпус и записанные LLM-фикстуры — ВНЕ репо
  (данные заказчиков, решение автора №2).

**ФТ-04. Каноническая схема** — `core/tender/schema.py`
- Stop: схема §2 целиком; `model_json_schema()` генерится; примеры
  валидные/невалидные ведут себя ожидаемо.
- Верификация: pytest — round-trip dict→schema→dict; отказ на `ok` без
  цитаты (model_validator).
- Loop: goal-based. | sonnet / medium / code / ~30 мин.

**ФТ-05. Конвертация** — `core/tender/convert.py`
- Stop: PDF→PNG-страницы (кап 50 — явная ошибка), DOCX/XLSX→markdown,
  ZIP→список файлов.
- Верификация: pytest на синтетических фикстурах (мини-PDF, docx, xlsx,
  zip) — счётчики страниц/строк, ошибки капа.
- Loop: goal-based. | sonnet / medium / code / ~40 мин.

**ФТ-06. LLM-клиент (вилка)** — `core/shared/llm.py`
- Stop: протокол + `AnthropicLLM` + `OpenRouterLLM`, settings-переключатель,
  ретрай на невалидном JSON, режим записи фикстур (сырой ответ → файл в
  `TENDER_CORPUS_DIR`).
- Верификация: pytest с мок-транспортом (ретрай-логика, парсинг) + 1 живой
  смоук на каждой реализации (картинка → структурный ответ).
- Loop: goal-based. | sonnet / medium / code / ~1 ч.
- ⚠️ Здесь добавляется `anthropic` в requirements — только с одобрения
  автора (правило проекта).

**ФТ-07. Eval-скрипт** — `tools/tender_eval.py` (вне пакета, dev-утилита)
- Stop: скрипт гонит корпус через extract+verify, сравнивает с эталонной
  разметкой, печатает % верных твёрдых полей — суммарно и по каждому полю.
- Верификация: pytest на синтетической паре «извлечение/эталон» с заранее
  известным счётом.
- Loop: goal-based. | sonnet / medium / code / ~30 мин.

**ФТ-08. `extract()` + промт — ВОРОТА КАЧЕСТВА**
- Stop: **≥80% твёрдых полей верно на golden-корпусе** (метрика ФТ-07).
- Верификация: eval-скрипт (машинный критерий) + просмотр диффов автором.
- Loop: goal-based с высокой автономией — крутим промт / порядок блоков /
  дайджест каталога / модель на ЭТОМ шаге; **не прошли — дальше не идём**.
- | opus / high / code+eval-итерации / ~2–4 ч.

**ФТ-09. `verify()`** — `core/tender/verify.py`
- Stop: статусы/`matched_model_id`/`nonstandard[]` по правилам §2–§3,
  включая: работы вне Воронежской области → `needs_review`; оборудование
  по региону не флагится; температурный подбор датчиков.
- Верификация: pytest — таблица кейсов из корпуса (стандарт → ok,
  вне ряда длин → нестандарт, −40 °C → замена датчика, «аналог» → review).
- Loop: goal-based. | sonnet / medium / code / ~40 мин.

**ФТ-10. Хранение** — таблица `tenders` + репозиторий
- Stop: SQL-миграция + `TenderRepository` за интерфейсом (паттерн P0-15);
  `ai_extraction` после создания не обновляется никаким методом.
- Верификация: CRUD-тесты на тестовой таблице; тест «PATCH values не
  трогает ai_extraction».
- Loop: goal-based. | sonnet / low / code / ~30 мин.

**ФТ-11. API** — `/api/tender/*` (§8)
- Stop: 5 эндпоинтов, bearer, конверт ошибок, `run_in_threadpool` на analyze.
- Верификация: HTTP-тесты с фикстурным LLMClient (без живых вызовов);
  401 без токена; analyze на корпусном пакете возвращает валидную схему.
- Loop: goal-based. | sonnet / medium / code / ~40 мин.

**ФТ-12. UI-форма модуля** — портал, AntD
- Stop: upload → чекбоксы файлов → «Анализ» → форма с подсветкой статусов
  (ok/needs_review/missing + цитата-тултип) → правка → сохранение;
  многопозиционный тендер — вкладки/секции позиций.
- Верификация: глаз автора (машинного верификатора вёрстки нет); grep-
  правило И-1 — во фронте нет логики статусов/сверки.
- Loop: turn-based. | sonnet / medium / code+preview / ~2–3 ч.

**ФТ-13. Gate MVP-1**
- Stop: чек-лист §10 закрыт полностью.
- Верификация: машинные пункты — прогоном, (е) — автор.
- Loop: turn-based. | — / — / чек-лист / ~1 ч.

## 10. Критерий «MVP-1 готов»

1. **(машинно)** Eval на golden-корпусе: ≥80% твёрдых полей верно.
2. **(машинно)** Каждый корпусный тендер проходит полный путь
   upload → analyze → форма → правка → сохранение (HTTP-тесты + UI-прогон).
3. **(машинно)** Каждый нестандарт корпуса пойман `verify()` — кодом,
   не моделью (тесты ФТ-09 покрывают все нестандарт-кейсы разметки).
4. **(машинно)** Ни одного `ok`-поля без `source_quote` (валидатор схемы).
5. **(машинно)** `ai_extraction` неизменен после правок формы (тест ФТ-10).
6. **(автор)** Один живой НОВЫЙ тендер (не из корпуса) прогнан от загрузки
   до сохранённой формы; автор принял форму глазами.

## 11. Решения автора (закрыты 2026-07-11)

1. **LLM-провайдер не фиксируется.** Вилка `LLMClient` в `core/shared/`
   (Anthropic SDK / OpenRouter), выбор — одна строка settings. Решение —
   ПОСЛЕ прогона golden-корпуса. Общий путь: растеризация страниц +
   JSON-схема в промте + Pydantic-валидация — обе реализации дают
   одинаковый результат (§5.1).
2. **Golden-корпус — вне репо**: локальная папка + `TENDER_CORPUS_DIR`
   в env (данные заказчиков). Записанные LLM-фикстуры — там же.
3. **Условия оплаты — в `terms`**: аванс/постоплата критичны для решения
   об участии.
4. **Whitelist регионов не существует — не изобретать.** Оборудование по
   региону не флагится (прайс единый по РФ). Работы: монтаж/фундамент/ПНР
   И место монтажа ≠ Воронежская область → `needs_review` «монтажные
   работы вне базовой зоны, стоимость определяется по месту».
5. **`tender_nuances.md` — коммитим** в `knowledge_base/`: инженерная
   кухня без данных клиентов, без него модуль не работает. Корпус — нет
   (п. 2).
