## Задачи

### Итерация B — отдельные строки монтаж/поверка (текущая)
Не схлопывать «Монтаж и поверка» в одну строку. Канонические
формулировки. Затрагивает src/contracts/from_kp.py, тесты.

### Итерация C — Конструктор схем оплаты
Текущие пресеты в payment_terms.json не покрывают все реальные
схемы (пример Лебедянский: «10% от общей суммы предоплата + 
доплаты по группам после конкретных событий»).

Решение — конструктор строк оплаты:
- Каждая строка: тип / процент / база (общая или группа) / 
  сумма (вычисляется) / срок (N дней) / тип дня / основание
- Тексты собираются по шаблону: 
  «{название} – {%} {за что} {сумма цифрами} ({пропись}) рублей 
   в т.ч. НДС 22% в течение {N} {рабочих|банковских} дней {основание}»
- UI: добавление/редактирование строк, автоматический пересчёт сумм
- Сохранение пользовательских схем для повторного использования
- Backward-совместимость с текущими пресетами (split_by_items как 
  частный случай)

Объём: opus, ~6-8 ч. Самая большая задача Этапа 3.

### Итерация D — Приложение №1 (строительные задания)
Папка templates/foundation_drawings/ — JPG-комплекты:
- 3 типа по числу секций (2 / 3 / 4)
- 2 варианта линеек (Ф/С vs ФЛ/СЛ)
- Аналогичные комплекты для рам (если потребуется)

5-7 JPG на комплект, по 1 JPG на страницу.

Функция выбора комплекта: число секций определяется из 
длины платформы (≤12 → 2, 14-18 → 3, 20-24 → 4); линейка — 
из модели.

На каждой странице приложения подставляется ФИО директора 
заказчика в ячейку «Утверждаю» (текст в таблице DOCX, не в JPG).

### Итерация E — реестр шаблонов + UI выбора
Создать 5 недостающих шаблонов на базе текущего spec_foundation_install.
Dropdown в UI: пользователь выбирает шаблон вручную.
Тесты на каждый шаблон (генерация с тестовой карточкой → 
проверка корректности плейсхолдеров).

### Итерация F — Технические характеристики и комплект поставки
Сейчас ТТХ в спецификации статичны. Должны подтягиваться 
по модели из equipment_specs.json:
- Максимальная нагрузка, наибольшая нагрузка на ось
- Цена поверочного деления
- Габаритные размеры, температурный диапазон, электропитание
- Канал внешней связи, потребляемая мощность

Комплект поставки — таблица с количеством датчиков, типом 
терминала, типом коробки. Уже частично есть в моделях 
(`equipment_specs.json` / `models.json`).

### Итерация G — Шеф-монтаж vs монтаж (отложено)
Должно подтягиваться из КП. Возможно, отдельная позиция 
в spec_items с term_role='supervision' vs 'installation'.
Уточнить после Итерации B.

### Прочее (не блокирует)
- Рефакторинг data_loader: устранить дублирование 
  equipment_specs.json ↔ models.json
- vMerge слияние ячеек в таблице спецификации DOCX

## Порядок работы

B → C → E → D → F → G

Логика: сначала закрываем структуру одной строки (B), затем
конструктор оплаты как самый ёмкий блок (C), затем размножаем 
работающее на 5 шаблонов (E), потом приложение с чертежами (D),
потом ТТХ (F), потом шеф-монтаж (G).

## Открытые вопросы

1. Формулировки для ПАК ОРИОН, рамы, стройработ — какой 
   канонический текст?

2. В Лебедянском «рабочих» дней, в твоём примере выше — 
   «банковских». Это всегда выбор пользователя? Или есть 
   правило (оплата=банковские, выполнение=рабочие)?

3. Цены в КП и в спецификации совпадают? В КП цены вроде 
   «без НДС» с пометкой «+22% НДС», а в спеке сразу 
   «с НДС». Это значит одна и та же позиция в КП и в 
   спеке может иметь разную цифру?

4. ТТХ в спецификации (П.13 в Лебедянском) — обязательно 
   во всех 6 шаблонах? В «Поставке» (только весы) тоже?

5. Комплект поставки в спецификации — обязательная таблица 
   или опциональная?

6. Юридические пункты (выезд бригад, обязанности заказчика, 
   автокран, балласт) — одинаковы во всех шаблонах или 
   различаются по содержанию? В «Поставке» и «Монтаже без 
   фундамента» эти пункты должны быть короче.
