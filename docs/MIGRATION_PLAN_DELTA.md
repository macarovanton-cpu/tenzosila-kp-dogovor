## Д-1. Цель выросла: не миграция, а портал

**Что в оригинале.** Преамбула (стр. 1–10) и §1 Фаза 1: цель — перенос текущего
приложения на FastAPI+React, Фаза 1 = «React-фронт для модуля КП». Bitrix (3c) и
агентный слой (3d) — «заделы» в конце Фазы 3.

**Что меняем.**
- Целеполагание: конечный продукт — **внутренний AI-портал отдела продаж**, визуально
  близкий к Bitrix24 (знакомый сотрудникам интерфейс). Модули: КП, договоры, тендеры,
  калькулятор рентабельности; дальше больше. Агентный слой поверх `core/` и интеграция
  в Bitrix24 — не «заделы», а часть целевой картины (сроки — по-прежнему Фаза 3).
- Фаза 1 переформулируется: **«Оболочка портала + КП как первый жилец»**. Оболочка =
  левое меню модулей + рабочая область + логин. Строится один раз и качественно —
  в неё потом въезжают все модули. Внутренние формы модулей — функционально-просто.
- Инварианты И-1…И-6 — **без изменений**. Портал не меняет главного: вся логика в
  Python-`core/`, фронт — тупой рендерер.

**Почему.** Оболочка, спроектированная под один модуль КП, при появлении тендеров
потребует переделки навигации, роутинга и layout. Дешевле сразу строить контейнер
для N модулей — это одна страница-каркас, а не спекулятивная абстракция.

**Влияние на задачи.**
- P1-01: «скаффолд фронта» → «оболочка портала»: layout с левым меню модулей
  (КП / Договоры / далее по мере появления), рабочая область, логин. Критерий тот же
  (`npm run build`, пустые страницы рендерятся) + меню переключает модули.
- Gate G1 (§1): замечания владельца по оболочке собираются отдельно от замечаний по
  форме КП — оболочка переживёт КП-модуль, её дефекты дороже.

## Д-2. Модульные границы `core/` + единый каталог продукта

**Что в оригинале.** P0-05: каркас `core/` с подпакетами `kp/`, `contracts/`,
`admin/`, `storage/`, `docx/`, `schemas/`, `settings.py`. Загрузка справочников
(`data_loader`, `filters`) в нарезке P0-08 идёт в пачке «kp-логика».

**Что меняем.** Состав подпакетов `core/`:

```
core/
  catalog/    # data_loader, filters, прайс-мета — ЕДИНЫЙ каталог продукта
  kp/         # pricing, spec_builder, validation, term_days, snapshot
  contracts/  # 26 модулей текущего src/contracts/
  shared/     # payment_wording, utils/format — кросс-модульные примитивы
  admin/      # админка прайса
  storage/    # supabase_client, репозитории
  docx/       # генераторы, dump-утилиты рендера
  schemas/    # Pydantic (§3.5)
  settings.py
```

Правило границ: модули (`kp/`, `contracts/`, будущие `tender/`, `margin/`) **не
импортируют друг из друга напрямую** — только из `catalog/`, `shared/`, `docx/`,
`storage/`, `schemas/`. (`contracts/from_kp` работает с КП-снапшотом — это данные,
а не импорт кода из `kp/`; снапшот и так заморожен И-2.)

`tender/` и `margin/` при этом **не создаются пустыми** — фиксируется только правило,
куда они встанут. Пустой пакет «на будущее» — это то, что запрещает принцип
Simplicity First.

**Почему.** Портал = несколько модулей поверх одного каталога продукта. Тендерный
верификатор (Д-3) сверяет извлечённые позиции с тем же `prices.json`, что и
конфигуратор КП. Если загрузка каталога останется внутри kp-логики, тендеры породят
вторую копию — два расходящихся каталога, классический дрейф.

**Влияние на задачи.**
- P0-05: список подпакетов — по схеме выше.
- P0-08: пачки переноса пересчитать — `catalog/` выносится отдельной (маленькой)
  пачкой первой, `payment_wording` уходит в `shared/` (см. Д-5), остальная kp-логика —
  как было.
- P0-20 (gate G0): к машинной проверке «нет `import streamlit` в core» добавить
  grep-проверку правила границ: `core/kp/` не импортирует `core/contracts/` и наоборот.

## Д-3. Тендерный модуль — место в архитектуре

**Что в оригинале.** Тендеры упомянуты один раз — как пилот агентного слоя
(3d, «тендерное ТЗ → черновик КП»).

**Что меняем.** Тендеры — полноценный модуль портала, отдельная фаза **ФТ** после
Фазы 2 (см. последовательность фаз в конце). Детальный план тендерного модуля —
**отдельный документ позже**; здесь фиксируется только каркас, чтобы Фаза 0 не
заложила неверных границ:

- `core/tender/extract.py` — извлечение: PDF/скан/DOCX/XLSX → vision-LLM
  (Anthropic API, Sonnet) → каноническая схема тендера. Чистая функция
  `bytes → schema`, изолированная от UI и транспорта — тот же принцип, что у
  `extractor` реквизитов (§3.3 оригинала).
- `core/tender/verify.py` — детерминированная сверка твёрдых полей извлечённых
  позиций с каталогом `core/catalog/` (Д-2). Позиция вне каталога =
  нестандарт/`needs_review` → редактируемая форма. Верификация — код, не LLM.
- Схема: тендер = массив `positions[]` (~15–20% тендеров многопозиционные).
- База знаний — два слоя: machine-checkable каталог из `prices.json` (для
  верификатора) + нарративный markdown (контекст для LLM). Без векторов/pgvector.
- LLM-вызовы — вне golden (принцип §2.2 сохраняется: записанные фикстуры сырого
  ответа модели, как для AI-экстракции реквизитов).
- §3: префикс `/api/tender/*` зарезервирован; контракт эндпоинтов сейчас НЕ
  фиксируем — это работа детального плана.

**Почему.** Единственное, что тендерам нужно от Фазы 0 — правильно выделенный
`catalog/` и правило границ модулей (Д-2). Всё остальное можно (и нужно) решать
позже, когда КП и договоры уже живут в портале.

**Влияние на задачи.** Новых P-задач не порождает. P0-05/P0-08 затронуты через Д-2.
Заметка: `anthropic` SDK — новая зависимость, добавляется только с одобрения Антона
(правило проекта), в фазе ФТ, не раньше.

## Д-4. UI-библиотека: Ant Design вместо Tailwind + shadcn/ui

**Что в оригинале.** Преамбула: «фронт — React + Tailwind + shadcn/ui», «статус
стека: согласован, не пересматривается». P1-01: «Vite + React + TS + Tailwind +
shadcn».

**Что меняем.** Фронт-стек: **React + TS + Ant Design 5**. Tailwind и shadcn/ui не
берём. Тема — через ConfigProvider design tokens, один theme-файл (плотность,
синяя гамма «под Bitrix»).

**Почему (взвешенное решение, а не вкус).**
- **Bitrix24-подобная оболочка** — плотный корпоративный вид, левое меню
  (`Layout` + `Sider` + `Menu`), таблицы, формы — у AntD из коробки. На shadcn тот же
  вид — самостоятельная дизайн-работа (композиция, плотность, тема), худший сценарий
  для React-новичка.
- **Формо-/таблично-центричные модули.** AntD `Form`/`Table` декларативны и
  однородны; shadcn требует обвязки react-hook-form + zod + TanStack Table на каждую
  форму — больше bespoke-кода на каждый экран.
- **Кто сопровождает.** shadcn копирует исходники компонентов в репозиторий — автор
  владеет и сопровождает этот код. AntD — версионируемая зависимость, поддерживаемая
  снаружи. Для новичка, сопровождающего сгенерированный агентом код, меньше своего
  кода = лучше.
- **Агентная генерация.** Однородный декларативный API даёт более предсказуемый
  сгенерированный код; «оболочка качественно» сводится к одному theme-файлу, а не к
  дизайн-решениям на каждом экране.
- Минусы AntD (bundle size, меньше свободы пиксельной кастомизации) для внутреннего
  портала несущественны. И-1 (никакой логики во фронте) не затрагивается.

**Влияние на задачи.**
- P1-01: скаффолд = Vite + React + TS + AntD; оболочка `Layout`/`Sider`/`Menu` (Д-1).
- P1-04…P1-08: секции формы КП — на AntD `Form`.
- P2-01…P2-05: формы договора — на AntD `Form`/`Table`/`Upload`.
- §6: пункт «весь React-UI — только глаз владельца» — без изменений; grep-правило
  И-1 (нет арифметики с ценами во фронте) — без изменений.

**Почему.** Не правка курса — устранение дрейфа между текстом плана и кодом, чтобы
