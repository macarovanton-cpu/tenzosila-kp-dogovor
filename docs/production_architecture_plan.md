# Production Architecture Plan

Дата анализа: 2026-06-12.

Документ описывает практичный путь от текущего Streamlit MVP к управляемому
production-приложению для подготовки КП и договоров. Цель не в том, чтобы
переписать систему, а в том, чтобы сохранить рабочую ценность MVP и добавить
управляемость: версии прайсов, настраиваемые правила, роли, аудит и безопасные
операции для отдела продаж.

## 1. Current MVP Summary

Сейчас приложение состоит из двух Streamlit-страниц, подключённых через
`src/app.py`:

- `src/pages/1_Коммерческое_предложение.py` — конфигуратор КП.
- `src/pages/2_Договор.py` — генерация договора, спецификации и приложений.

Страница КП загружает справочники из `data/` через `src/data_loader.py`:

- `data/models.json` — модели, линейки, ТТХ, дефолты по оборудованию.
- `data/prices.json` — цены моделей и опций.
- `data/options.json` — описания опций, ПАК ОРИОН, фундаменты.
- `data/payment_terms.json` — пресеты оплаты.
- `data/managers.json` — менеджеры.

По текущему прайсу в `prices.json` есть 45 цен моделей и 65 цен опций. В
опциях используются классы цен:

- `A_retail_and_dealer` — 20 позиций.
- `B_retail_only` — 36 позиций.
- `C_manual_range` — 4 позиции.
- `UNKNOWN` — 5 позиций.
- `on_request` — 1 позиция.

Коммерческое предложение строится так:

1. Менеджер вводит номер КП, дату, срок действия, клиента, менеджера.
2. Выбирает линейку, нагрузку, длину и ширину платформы.
3. Настраивает оборудование, конструкцию, метрологию, опции и услуги.
4. Правит итоговую спецификацию: количество и цену отдельных строк.
5. Выбирает условия оплаты.
6. Генерирует DOCX КП и сохраняет snapshot КП в Supabase.

Ключевые модули КП:

- `src/pricing.py` — расчёт параметров ценовых виджетов и итогов с НДС.
- `src/spec_builder.py` — сборка позиций спецификации из state, прайсов и опций.
- `src/filters.py` — доступность моделей и опций по линейке, нагрузке и длине.
- `src/validation.py` — ошибки и предупреждения перед генерацией.
- `src/generators/kp_generator.py` — контекст шаблона КП и генерация DOCX.
- `src/storage/snapshot_builder.py` — компактный snapshot КП для Supabase.

Страница договора работает в двух режимах:

- Mode A: загрузка КП из Supabase по номеру или из списка последних КП.
- Mode B: legacy-путь через AI-извлечение старого PDF КП и карточки контрагента.

Ключевые модули договора:

- `src/contracts/from_kp.py` — восстановление спецификации договора из snapshot КП.
- `src/contracts/payment_line.py` — модель строк оплаты договора.
- `src/ui/payment_lines_editor.py` — редактор платежей договора.
- `src/contracts/clauses_loader.py`, `clauses_dsl.py`, `clauses_renderer.py` —
  загрузка и применение `data/clauses.yaml`.
- `src/contracts/spec_v2_filler.py` — генерация спецификации v2.
- `src/contracts/filler.py` — заполнение DOCX-шаблонов.
- `src/contracts/fundament_lookup.py` — подбор строительных заданий и контрольных
  листов из `data/fundament/`.
- `src/contracts/compose.py` — склейка спецификации с приложениями.

Хранение сейчас минимальное:

- `kps` — КП с отдельными колонками и JSONB `data`.
- `contracts` — договоры с JSONB `requisites` и `specification`.
- SQL-миграций или схем БД в репозитории не найдено; SQL был описан в старом
  плане, но не оформлен как управляемые миграции проекта.

## 2. Main Architectural Problems

Главная проблема MVP: приложение уже решает рабочую задачу менеджера, но
управление бизнес-данными и правилами пока остаётся разработческой операцией.

### 2.1 Прайс нельзя безопасно обновлять через приложение

`prices.json` хранит цены, классы цен, диапазоны, примечания и дату действия.
Это удобно для MVP и Git, но неудобно для эксплуатации:

- новый прайс требует ручной подготовки файла;
- нет загрузки прайса через UI;
- нет истории версий и активной версии;
- нет журнала ошибок импорта;
- нет механизма отката;
- нет проверки, какие КП были сформированы на старой версии прайса;
- при восстановлении КП часть данных может пересчитаться по актуальному
  `prices.json`, если не хранить версию или снимок использованных цен.

### 2.2 Ценовые правила частично зашиты в коде

В `src/config.py` зашиты:

- `VAT_RATE = 0.22`;
- `SYNTHETIC_DEALER_FACTOR = 0.92`;
- `MAX_COEFF = 1.4`;
- `MIN_COEFF_B = 0.6`;
- линейки, длины, порядок блоков опций;
- префиксы ключей опций по блокам.

В `src/pricing.py` зашита логика классов цен:

- класс A: дилерская цена как нижняя граница, розница как дефолт, максимум
  `retail * 1.4`;
- класс B: нижняя граница `retail * 0.6`, максимум `retail * 1.4`;
- класс C: ручной диапазон `range_min` - `range_max`;
- UNKNOWN: synthetic dealer через коэффициент.

Это понятная MVP-логика, но для production её нужно сделать управляемой:
администратор должен видеть правила, менять диапазоны и понимать, какая версия
правил применялась к конкретному КП.

### 2.3 Не хватает процесса исключений и согласований

Сейчас менеджер может вручную править цену в спецификации через
`src/ui/specification_section.py`, а также добавлять произвольные позиции через
`src/ui/options_section.py`. Это полезно, но нет production-контроля:

- нет обязательного комментария при выходе за рекомендованный диапазон;
- нет статуса "требует согласования";
- нет роли руководителя, который согласует нестандартную цену;
- нет аудита, кто изменил цену и почему;
- нет маржинальных предупреждений;
- нет разделения между "рекомендовано", "допустимо" и "запрещено".

### 2.4 UI, бизнес-логика и данные местами смешаны

Хорошие разделения уже появились: `pricing.py`, `spec_builder.py`,
`payment_renderer.py`, `snapshot_builder.py`, `contracts/*`. Но часть правил всё
ещё живёт рядом с UI:

- `src/ui/payment_section.py` содержит не только виджеты, но и ветвление по
  вариантам оплаты.
- `src/ui/model_section.py` управляет выбором модели и ценой модели.
- `src/ui/options_section.py` одновременно рендерит опции, применяет частные
  правила по фундаментам, бытовке, шеф-монтажу и поверке.
- `src/pages/2_Договор.py` содержит много логики экрана договора: поля,
  конвертацию строк спецификации, scope overrides, приложения, генерацию файлов.

Для MVP это нормально. Для production стоит постепенно выносить правила в
сервисные функции и конфигурации, оставляя Streamlit страницам роль тонкого UI.

### 2.5 Справочники уже есть, но нет панели управления

Справочники лежат в `data/`, но не управляются через приложение:

- модели и ТТХ;
- цены;
- опции;
- условия оплаты;
- менеджеры;
- clauses договора;
- фундаментные DOCX-приложения;
- шаблоны КП и договора.

Любое изменение требует правки файлов, проверки тестами и участия разработчика.
Это ограничивает эксплуатацию отделом продаж.

### 2.6 Supabase используется как хранилище сделок, но не как системная БД правил

Сейчас Supabase хранит результаты работы: КП и договоры. Он пока не хранит:

- версии прайсов;
- версии правил;
- справочники;
- роли пользователей;
- согласования;
- аудит действий;
- версии шаблонов документов;
- результаты импорта;
- статусы качества данных.

То есть база уже есть, но production-слой управления бизнес-данными ещё не
построен.

### 2.7 Документные шаблоны и приложения не версионируются как бизнес-артефакты

DOCX-шаблоны лежат в `templates/`, строительные задания — в `data/fundament/`.
Это работает, но production требует:

- версии шаблонов;
- дату действия;
- список обязательных переменных;
- проверку незаполненных плейсхолдеров;
- связь КП/договора с версией шаблона;
- журнал обновления шаблонов.

## 3. Target Product Vision

Целевая версия должна остаться простой для менеджера:

1. Менеджер выбирает клиента и конфигурацию.
2. Приложение показывает рекомендованные цены и безопасные диапазоны.
3. Менеджер может обосновать нестандартную цену.
4. Руководитель видит отклонения и согласует их.
5. КП и договор генерируются из актуальных версий прайсов, правил и шаблонов.
6. Вся история изменений сохраняется.

Целевое приложение должно иметь три слоя:

- **Sales UI** — рабочие экраны менеджера: КП, договор, список КП, статусы.
- **Admin UI** — управление прайсами, правилами, справочниками, шаблонами.
- **Business Core** — pricing engine, rules engine, document generation,
  storage layer, audit.

На первом production-этапе это всё ещё может быть Streamlit. Не нужно сразу
переходить на FastAPI/React. Важнее сначала отделить данные и правила от кода,
а уже потом решать вопрос промышленного стека.

## 4. Admin Panel Concept

Админка должна быть отдельным разделом Streamlit, доступным не всем ролям. В
первой версии это может быть третья страница навигации, но реализацию стоит
начинать только после закрытия текущей v2.1-стабилизации.

### 4.1 Управление прайсами

Минимально нужные функции:

- загрузка нового прайса из Excel/CSV/подготовленного JSON;
- валидация структуры файла;
- просмотр импортированных моделей и опций;
- подсветка новых, изменённых и удалённых позиций;
- дата действия прайса;
- статус версии: draft, validated, active, archived;
- выбор активной версии;
- откат к предыдущей версии;
- журнал ошибок импорта;
- хранение исходного файла импорта;
- отчёт "что изменилось относительно активного прайса".

Для первой версии не обязательно строить универсальный импорт любых PDF. Более
практично принять подготовленный Excel/CSV в понятной структуре и сделать
надёжную валидацию.

### 4.2 Управление ценовыми правилами

Нужны разделы:

- классы цен A/B/C и их параметры;
- минимальная цена;
- рекомендованная цена;
- максимальная цена;
- допустимый диапазон;
- правила наценки;
- правила скидки;
- исключения для модели, опции, категории или клиента;
- комментарий при выходе за рекомендованный диапазон;
- порог, после которого нужно согласование руководителя;
- список активных правил;
- дата начала и окончания действия правила.

Важное разделение:

- **минимальная цена** — ниже нельзя без отдельного разрешения;
- **рекомендованная цена** — обычная рабочая цена;
- **максимальная цена** — верхняя планка, но менеджер может поставить выше
  только с комментарием, если бизнес это разрешает;
- **цена "под запрос"** — блокирует генерацию до ручного решения.

### 4.3 Управление справочниками

Справочники стоит выносить постепенно, начиная с тех, которые меняются чаще:

- менеджеры;
- условия оплаты;
- категории опций;
- тексты описаний опций;
- регионы и условия доставки;
- шаблоны формулировок;
- типы фундамента;
- модели и комплектации.

Модели и технические характеристики лучше не давать редактировать свободной
формой на первом этапе. Там высок риск ошибок. Для них достаточно просмотра,
валидации импорта и ограниченного редактирования администратором.

### 4.4 Управление шаблонами документов

Админке нужны:

- загрузка шаблона КП;
- загрузка шаблона договора;
- загрузка шаблона спецификации;
- версии шаблонов;
- дата действия;
- список переменных шаблона;
- проверка обязательных полей;
- тестовая генерация на фикстурной сделке;
- статус active/archived;
- журнал изменений.

Для приложений:

- библиотека строительных заданий;
- контрольные листы;
- будущие приложения ОРИОН;
- человекочитаемые имена;
- тип фундамента, секции, применимость;
- проверка, что файл открывается и может быть склеен.

### 4.5 Управление пользователями и ролями

Роли:

- менеджер;
- руководитель отдела продаж;
- администратор;
- технический специалист;
- просмотр/аудитор.

Права:

- формировать КП;
- формировать договор;
- менять цену в рекомендованном диапазоне;
- выходить за рекомендованный диапазон с комментарием;
- согласовывать нестандартные цены;
- загружать прайсы;
- активировать прайсы;
- менять правила;
- менять шаблоны;
- смотреть журнал действий.

### 4.6 Журнал действий

Журнал должен отвечать на вопросы:

- кто загрузил прайс;
- кто активировал прайс;
- кто изменил правило;
- кто сформировал КП;
- кто вручную изменил цену;
- почему цена вышла за диапазон;
- кто согласовал отклонение;
- когда был сформирован договор;
- на какой версии прайса, правил и шаблонов были созданы документы.

### 4.7 Контроль качества данных

Нужны автоматические проверки:

- пустые обязательные поля;
- цена равна 0 там, где это не "силами Заказчика";
- цена сильно ниже минимума;
- цена сильно выше максимума;
- прайс просрочен;
- нет активной версии прайса;
- нет активной версии шаблона;
- модель есть в `models`, но нет в активном прайсе;
- опция есть в прайсе, но не имеет категории или описания;
- справочник менеджеров пуст;
- договор ссылается на приложение, но файл приложения не выбран.

## 5. Pricing & Rules Architecture

### 5.1 Pricing engine

Нужен отдельный слой, который отвечает не за UI-виджеты, а за бизнес-решение:

- найти активную версию прайса;
- получить базовую цену модели или опции;
- применить класс цены;
- рассчитать min/recommended/max;
- применить исключения;
- вернуть результат с причинами и флагами.

Предлагаемая сущность результата:

- `item_id`;
- `price_list_version_id`;
- `base_price`;
- `min_price`;
- `recommended_price`;
- `max_price`;
- `selected_price`;
- `price_status`: ok, below_recommended, below_min, above_max, on_request;
- `requires_comment`;
- `requires_approval`;
- `applied_rules`;
- `warnings`.

Текущий `src/pricing.py` можно развивать в этом направлении. Не нужно удалять
его сразу. Первый шаг — добавить рядом новый слой, например
`src/pricing_engine.py` или пакет `src/pricing/`, и постепенно переводить
виджеты на него.

### 5.2 Rules engine без переусложнения

На старте не нужен большой enterprise rules engine. Достаточно конфигурируемого
слоя правил:

- правило имеет тип, область действия, параметры, дату действия и приоритет;
- область действия может быть model, option, category, client_type, region;
- правила применяются детерминированно;
- результат объясним: видно, какие правила сработали.

Примеры правил:

- `retail_and_dealer_range`: min = dealer, recommended = retail, max = retail * 1.4;
- `retail_only_range`: min = retail * 0.6, recommended = retail, max = retail * 1.4;
- `manual_range`: min/max из позиции прайса;
- `on_request`: блокировать генерацию до ручной цены;
- `manager_can_exceed_recommended`: разрешить, но требовать комментарий;
- `below_min_requires_approval`: создать заявку на согласование.

### 5.3 Что хранить в snapshot КП

Для production у каждого КП нужно сохранять:

- версию прайса;
- версию набора правил;
- версию шаблона КП;
- исходные цены, рассчитанные min/recommended/max;
- выбранные менеджером цены;
- комментарии по отклонениям;
- статусы согласования.

Это защитит старые КП от пересчёта по новому прайсу.

### 5.4 Тестирование расчётов

Нужны отдельные тесты pricing engine:

- класс A: min/recommended/max;
- класс B;
- класс C;
- UNKNOWN;
- on_request;
- ширина 3.5/4 м;
- выход ниже min;
- выход выше max;
- требование комментария;
- требование согласования;
- сохранение snapshot расчёта.

## 7. User Roles & Permissions

### 7.1 Менеджер

Может:

- создавать КП;
- выбирать модель, опции, оплату;
- менять цену внутри разрешённого диапазона;
- добавлять комментарий к нестандартной цене;
- отправлять отклонение на согласование;
- формировать договор после согласования;
- смотреть свои КП и договоры.

Не может:

- активировать прайс;
- менять правила;
- менять шаблоны;
- согласовывать собственные отклонения.

### 7.2 Руководитель отдела продаж

Может:

- видеть КП менеджеров;
- согласовывать отклонения;
- смотреть маржинальные предупреждения;
- возвращать КП на доработку;
- смотреть журнал изменений по продажам.

Не обязательно должен:

- редактировать справочники;
- загружать шаблоны;
- править технические данные.

### 7.3 Администратор

Может:

- загружать прайсы;
- валидировать и активировать версии;
- управлять справочниками;
- управлять пользователями и ролями;
- менять шаблоны;
- смотреть полный аудит.

### 7.4 Технический специалист

Может:

- проверять технические справочники;
- редактировать технические описания;
- подтверждать новые модели, опции, комплектации;
- проверять приложения и чертежи.

### 7.5 Аудитор / просмотр

Может:

- смотреть КП, договоры, версии прайсов, журнал действий;
- не может менять данные.

## 8. Document Generation Architecture

Текущая генерация документов уже имеет полезные границы, но нуждается в
production-обвязке.

### 8.1 КП

Сейчас КП генерируется в `src/generators/kp_generator.py` из state и `prices`.
Целевое состояние:

- генератор получает не Streamlit state, а нормализованный `ProposalDraft`;
- цены приходят из pricing engine;
- snapshot содержит версии прайса, правил и шаблона;
- генератор не решает, можно ли генерировать КП: это делает validation layer;
- DOCX-байты и метаданные генерации сохраняются как результат.

### 8.2 Договор

Сейчас страница договора много делает сама: загружает КП, извлекает карточку,
рисует форму, редактирует спецификацию, собирает данные и запускает генерацию.

Целевое состояние:

- отдельный `contract_service` готовит `ContractDraft`;
- `from_kp.py` отвечает только за конвертацию КП в договорную модель;
- `payment_line.py` и редактор платежей работают с одной доменной моделью;
- `spec_v2_filler.py` получает готовые данные, а не добирает их из файлов;
- приложения выбираются через библиотеку приложений с версиями;
- результат генерации сохраняет связи с версиями шаблонов.

### 8.3 Шаблоны

Для production нужно:

- хранить версии шаблонов;
- перед активацией проверять переменные;
- на тестовом КП выполнять smoke-генерацию;
- сохранять версию шаблона в КП/договоре;
- иметь быстрый откат.

## 9. Audit, Logging & Versioning

### 9.1 Версии прайсов

Каждый прайс должен иметь:

- версию;
- дату действия;
- источник;
- статус;
- автора загрузки;
- дату активации;
- список изменений относительно предыдущего активного прайса.

КП должно ссылаться на конкретный `price_list_id`.

### 9.2 Версии правил

Набор правил должен версионироваться отдельно от прайса. Это позволит менять
коридоры, согласования и исключения без подмены самого прайса.

КП должно ссылаться на конкретный `pricing_rule_set_id`.

### 9.3 Версии шаблонов

КП, договор и спецификация должны знать:

- какая версия шаблона использовалась;
- какие приложения были включены;
- какие переменные остались незаполненными;
- кто запустил генерацию.

### 9.4 Audit log

Аудит нужен не только для безопасности, но и для управляемости продаж:

- ручная цена;
- изменение количества;
- добавление произвольной позиции;
- выход за диапазон;
- комментарий менеджера;
- решение руководителя;
- смена активного прайса;
- смена активных правил;
- загрузка шаблона.

## 10. Implementation Roadmap

### Этап 1 — минимальная админка без большой переделки

Цель: сделать обновление прайса управляемым, не ломая текущий КП.

Что сделать:

- добавить таблицы `price_lists`, `price_items`, `price_imports`,
  `price_import_errors`;
- оформить SQL-миграции в репозитории;
- сделать страницу админки "Прайсы";
- загрузка подготовленного CSV/XLSX/JSON;
- валидация обязательных колонок;
- сравнение с текущим активным прайсом;
- просмотр imported rows;
- выбор активной версии;
- загрузчик `load_prices()` научить брать активный прайс из БД с fallback на
  `data/prices.json`;
- сохранять `price_list_id` в snapshot КП;
- в админке показать текущие классы цен и коэффициенты как read-only.

Почему это первый этап: он закрывает самый больной эксплуатационный риск, но
не требует переписывать генерацию КП и договора.

### Этап 2 — управление правилами

Цель: вынести ценовые коридоры и исключения из кода.

Что сделать:

- добавить `pricing_rule_sets`, `pricing_rules`, `pricing_exceptions`;
- создать pricing engine рядом с текущим `src/pricing.py`;
- покрыть engine тестами;
- перевести модельные и опционные price widgets на результат engine;
- добавить min/recommended/max;
- добавить комментарий при выходе за recommended;
- добавить статус `requires_approval`;
- сохранять расчётные границы в snapshot КП;
- в админке дать управление диапазонами и исключениями.

### Этап 3 — роли и согласования

Цель: сделать нестандартную цену управляемым процессом.

Что сделать:

- пользователи и роли;
- permissions;
- заявки на согласование;
- статусы КП;
- список "требует согласования";
- решение руководителя;
- audit log для ручных правок;
- блокировка генерации договора, если КП требует согласования и не согласовано.

### Этап 4 — production-качество

Цель: стабилизировать приложение как внутренний рабочий инструмент.

Что сделать:

- миграции БД в репозитории;
- бэкапы Supabase;
- smoke-тест генерации документов на фикстурах;
- мониторинг ошибок генерации;
- закрыть known test gaps;
- привести `src/pages/2_Договор.py` к более тонкому UI через сервисные функции;
- разделить document generation и Streamlit UI;
- добавить журнал генераций;
- описать регламент обновления прайса и шаблонов.

### Этап 5 — продуктовая версия

Цель: подготовить систему к возможному использованию другими компаниями.

Что сделать:

- мультикомпанейность;
- отдельные прайсы и шаблоны на компанию;
- настройка ролей на компанию;
- импорт/экспорт;
- документация администратора;
- документация менеджера;
- API-слой, если Streamlit начнёт мешать;
- возможный переход на FastAPI + отдельный frontend только после доказанного
  упора в ограничения Streamlit.

## 11. MVP-to-Production Priorities

### Сделать в первую очередь

1. Версионирование прайсов и активная версия.
2. Сохранение `price_list_id` в КП.
3. SQL-миграции в репозитории.
4. Базовая страница админки для загрузки и просмотра прайса.
5. Pricing engine с min/recommended/max и тестами.
6. Комментарий менеджера при нестандартной цене.
7. Audit log для изменения цен и активных версий.

### Сделать после стабилизации первого production-контура

1. Полное управление всеми справочниками.
2. Роли и согласования.
3. Версионирование шаблонов.
4. Панель качества данных.
5. История изменений по каждой позиции КП.
6. Расширенная аналитика по менеджерам, скидкам и марже.

### Отложить, чтобы не раздуть MVP

1. FastAPI/React-переписывание.
2. Битрикс-интеграцию.
3. Мультикомпанейность.
4. Универсальный парсер любых PDF-прайсов.
5. Полноценный CRM-модуль.
6. Сложный no-code rules engine.
7. ORM-слой без явной необходимости.

## 12. Risks & Recommendations

### Риск 1: старые КП могут пересчитываться по новым правилам

Рекомендация: сохранять `price_list_id`, `pricing_rule_set_id` и снимок
расчётных границ по каждой позиции. Старый документ должен воспроизводиться по
старым данным.

### Риск 2: админка может превратиться в большой продукт раньше времени

Рекомендация: первая админка должна уметь только загрузить, проверить,
посмотреть и активировать прайс. Управление всеми справочниками отложить.

### Риск 3: ручные правки цен останутся невидимыми

Рекомендация: уже на втором этапе требовать комментарий при выходе за
рекомендованную границу и писать событие в audit log.

### Риск 4: договорный экран станет слишком тяжёлым

Рекомендация: постепенно выносить из `src/pages/2_Договор.py` сервисные функции,
но не начинать большой рефакторинг до закрытия v2.1. Самый безопасный путь —
выносить только новые production-функции в отдельные модули.

### Риск 5: правила будут разъезжаться между КП и договором

Рекомендация: КП должен сохранять нормализованный snapshot, а договор должен
читать именно его. Договор не должен заново угадывать цену, прайс или условия
по тексту.

### Риск 6: нет схемы БД в репозитории

Рекомендация: перед расширением Supabase добавить папку миграций и зафиксировать
текущие таблицы `kps` и `contracts`, затем добавлять новые таблицы только через
миграции.

### Риск 7: слишком жёсткие ценовые границы мешают реальным продажам

Рекомендация: заменить логику "можно/нельзя" на три уровня:

- рекомендованный диапазон;
- допустимое отклонение с комментарием;
- критическое отклонение с согласованием.

### Архитектурная рекомендация

Не переписывать приложение сейчас. Правильный следующий шаг — добавить
управляемую версию прайса и минимальный pricing engine вокруг текущего MVP.
Streamlit остаётся рабочим интерфейсом, JSON остаётся fallback-источником, а
Supabase постепенно становится системой управления бизнес-данными.
