# Спецификация фиксов генерации — КП/договоры/спецификации

Дата: 2026-07-08 (уточнён заходом 1: ловушки написаны, 35 красных; C4→баг, D2+B1/E2 шире, D1 под вопросом)
Источник: построчная сверка генерации с эталонами `docs/contract_templates_v1/*.md`
по 5 сценариям (Ромашка, Агрофирма×3, ТАТПРОФ×2, ВКМ).

## Как читать документ

Каждый фикс: **как сейчас** → **как должно** → **критерий приёмки (ловушка)**.
- «Критерий приёмки» = машинно-проверяемое условие. По нему пишется тест-ловушка,
  которая на текущем коде КРАСНАЯ (баг воспроизведён), после фикса — ЗЕЛЁНАЯ.
- Ловушка проверяет СТРУКТУРУ (есть/нет, один/два, такая формулировка). Смысловую
  корректность подтверждает Антон глазами на финальном review.

## Общие правила сверки (важно для всех фиксов)
- Суммы/цены НЕ сверяются с эталоном — генератор считает из прайса, расхождение ожидаемо.
- НДС 22% — правильно; 20% в старых эталонах — устаревшее, не эталон для НДС.
- Свободные поля (гарантия, марка двутавра, настил, подшив) в эталонах отсутствуют,
  ловушками не проверяются.

# ГРУППА A — крупные (P0). Требуют диагностики причины ДО фикса

## A1 — ОРИОН: состав позиций по эталону (переопределён после диагностики)
**Диагностика опровергла «потерю»:** ПАК ОРИОН доходит до документа. «Ноль ОРИОНа»
в файле ВКМ — вероятно stale-снапшот (КП собран до появления маппинга ОРИОН,
коммиты 2026-05-23/06-04). ДЕЙСТВИЕ АНТОНА: пересобрать ВКМ с нуля (свежий КП,
не загрузка по номеру) и подтвердить, что ПАК появляется. Если да — «потери» нет.

**Реальная задача — расщепить ОРИОН-пакет на позиции ПО ЭТАЛОНУ.**
Сейчас код даёт 1 строку («ПАК ОРИОН Стандарт (оборудование + шеф-монтаж)»),
эталон требует раздельные позиции, число зависит от сценария:

Фундамент + ОРИОН — ТРИ позиции:
- «Программно-аппаратный комплекс «ОРИОН»»
- «Установка опор и кабель-трасс для программно-аппаратного комплекса «ОРИОН»»
- «Монтаж и настройка программно-аппаратного комплекса «ОРИОН»»

Монтаж + ОРИОН (без фундамента) — ДВЕ позиции:
- «Программно-аппаратный комплекс «ОРИОН»»
- «Монтаж ПАК «ОРИОН»»
- (опор НЕТ — нет фундамента)

Правило:
- ПАК ОРИОН — всегда;
- монтаж ОРИОН — всегда, наименование зависит от сценария:
  фундамент → «Монтаж и настройка ПАК «ОРИОН»»; монтаж → «Монтаж ПАК «ОРИОН»»;
- опоры/кабель-трассы — ТОЛЬКО при фундаменте (авто-добавляются, не ручная опция).

**Реализация (решение Антона — расщепить в прайсе):** пакет ОРИОН в data/prices.json
разбить на «оборудование» / «монтаж» / «опоры» так, чтобы генератор выдавал
раздельные позиции по правилу выше. Наименования — по эталону (см. E3b).

**Мёртвый код (убрать при этой работе):** ветка `"orion_install" in key`
(spec_items.py:69-70) и проверка `"orion_install" in items_by_id`
(clauses_context.py:98) — ключ `orion_install` сейчас не производится нигде.
Оживить при расщеплении пакета (появится ключ монтажа ОРИОН).

**Критерий приёмки:**
- фундамент+ОРИОН → 3 позиции ОРИОН (ПАК, опоры, монтаж-и-настройка);
- монтаж+ОРИОН → 2 позиции (ПАК, монтаж), опор нет;
- ОРИОН выкл → ни одной позиции ОРИОН;
- наименования == эталонным.
**Приоритет:** P1 (не P0 — потери нет). Затрагивает прайс → сверить суммы/бандлы.

## D2+B1 — клауза «выезд бригад»: формулировка по признаку стройки + без дублей
**Как сейчас (УТОЧНЕНО заходом 1 — проще):** обе формулировки выезда печатаются
подряд БЕЗУСЛОВНО во всех сценариях с монтажом — «Выезд монтажной бригады…» и
«Выезд строительной и монтажной бригад…» идут друг за другом всегда, независимо
от scope. Фикс: убрать безусловное задвоение + выбрать ОДНУ формулировку по
признаку «подрядчик строит фундамент».
Подкритерий «нет монтажа → нет клаузы» покрыт ловушкой БАГ-1b (supply-флоу,
клауз выезда нет by design) — отдельной фикстуры «фундамент без монтажа» НЕТ
(Антон: фундамент всегда с монтажом, сценарий нереален).
**Как должно (правило из эталонов, однозначное):**
- подрядчик СТРОИТ фундамент → «Выезд строительной и монтажной бригад…»
  (эталоны: фундамент_монтаж, строительство_с_материалом);
- подрядчик фундамент НЕ строит (рама/площадка заказчика/заказчик сам делает
  фундамент) → «Выезд монтажной бригады…»
  (эталоны: рама_монтаж, монтаж, монтаж_ОРИОН, рама_шеф-монтаж);
- нет монтажа/шеф-монтажа → клаузы выезда НЕТ;
- всегда РОВНО ОДНА, без дублей.
**Критерий приёмки:**
- подрядчик строит фундамент → клауза содержит «строительной и монтажной бригад», ×1;
- подрядчик не строит → «монтажной бригады» (без «строительной»), ×1;
- нет монтажа → клаузы выезда нет;
- ни в одном сценарии не двоится.

# ГРУППА C — кавычки и имена сторон (P1)

## C1+C3 — нормализация кавычек имени заказчика к ёлочкам (УТОЧНЕНО: вход ПРЯМЫМИ)
**Как вводит Антон (факт):** прямыми кавычками через Shift+2 — `"Агрофирма "Промышленная"`
(три прямые кавычки при вложенности), НЕ ёлочками. C1 и C3 — ОДИН баг: генератор
не нормализует прямые кавычки; на вложенном имени даёт кашу
(`ООО "Агрофирма «Промышленная"` — внешняя прямая, закрывающая потеряна).
**Как должно:** прямые кавычки нормализуются в ёлочки; вложенность распознаётся
по позиции (первая открывает внешнюю, последняя закрывает внешнюю, средние — внутреннюю).
**Критерий приёмки (вход ПРЯМЫМИ кавычками — реалистичный):**
- ввод `"Ромашка"` → в docx `«Ромашка»`;
- ввод `"Агрофирма "Промышленная"` (три прямые) → `«Агрофирма «Промышленная»»`
  (внешние и внутренние ёлочки, закрывающие на месте, ничего не потеряно);
- прямых кавычек `"` в имени заказчика в docx нет нигде.
**НЕ делать тест с ёлочками на входе** — Антон так не вводит, нереалистичный кейс.
**РЕАЛИЗОВАНО (заход 3):** normalize_quotes в src/contracts/utils.py — специализирован
под ОДНУ (возможно вложенную) сущность в кавычках. ГРАНИЦА (техдолг, НЕ баг): на двух
независимых парах («ООО "ТД "Х" плюс») или тексте после закрывающей — молчаливый брак;
одиночная кавычка теряется. Антон подтвердил: имена всегда одна сущность в кавычках —
граница НЕ задевает реальные данные. Если появится нетиповое имя — доработать алгоритм.

## F1 — умный дефолт оплаты по вехам (РЕШЕНО: умный дефолт + ручная правка)
**Как сейчас:** дефолт 30/40/30 «от общей цены договора», игнорирует scope.
**Как должно:** заполнение оплаты «по умолчанию» СЕЕТ вехи по активным бакетам
(не плоские 30/40/30); менеджер дальше правит вручную в редакторе оплаты.
Правило бакетов (из эталонов):
- бакет ВЕСЫ (+ОРИОН если вкл): предоплата 50% (60% если ОРИОН) → доплата остаток
  по уведомлению об отгрузке; доставка — в доплату за весы;
- бакет ФУНДАМЕНТ (если подрядчик строит): предоплата 50% → доплата 50% по акту;
- бакет МОНТАЖ+ПОВЕРКА: предоплата 50% → доплата 50% по акту монтажа;
- порядок вех: весы → фундамент → монтаж; активны только бакеты под текущий scope.
**Критерий приёмки:**
- фундамент+монтаж → бакеты весы/фундамент/монтаж, не 30/40/30;
- рама+монтаж (без фундамента) → бакеты весы/монтаж, фундаментного нет;
- ОРИОН вкл → предоплата весы+ОРИОН 60%, ОРИОН в бакете весов;
- сумма всех вех = ИТОГО (100%);
- ручная правка засеянных строк не перетирается при перегенерации.
**Оговорки:**
1. Проценты (50/60) ВЫВЕРИТЬ с Антоном до кодинга — агент показывает таблицу
   «бакет → % предоплаты», Антон подтверждает (взяты из эталонов, возможны частные случаи).
2. ОТДЕЛЬНЫЙ ФРОНТ, opus-plan (новый механизм сеялки вех, не правка существующего).
   Делать ПОСЛЕ P0/P1/P2 — затрагивает генерацию сумм оплаты, риск задеть работающее.
3. Связать с известным ограничением payment_lines_editor (bucket/source id).
