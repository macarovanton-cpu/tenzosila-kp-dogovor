# Спецификация фиксов генерации — КП/договоры/спецификации

Дата: 2026-07-08
Источник: построчная сверка генерации с эталонами `docs/contract_templates_v1/*.md`
по 5 сценариям (Ромашка, Агрофирма×3, ТАТПРОФ×2, ВКМ).

## Как читать документ

Каждый фикс: **как сейчас** → **как должно** → **критерий приёмки (ловушка)**.
- «Критерий приёмки» = машинно-проверяемое условие. По нему пишется тест-ловушка,
  которая на текущем коде КРАСНАЯ (баг воспроизведён), после фикса — ЗЕЛЁНАЯ.
- Ловушка проверяет СТРУКТУРУ (есть/нет, один/два, такая формулировка). Смысловую
  корректность подтверждает Антон глазами на финальном review.

## Общие правила сверки (важно для всех фиксов)
- Суммы/цены НЕ сверяются с эталоном — генератор считает из прайса, расхождение ожидаемо.
- НДС 22% — правильно; 20% в старых эталонах — устаревшее, не эталон для НДС.
- Свободные поля (гарантия, марка двутавра, настил, подшив) в эталонах отсутствуют,
  ловушками не проверяются.

# ГРУППА A — крупные (P0). Требуют диагностики причины ДО фикса

## A1 — ОРИОН выпадает из спецификации при включённой опции
**Как сейчас:** ОРИОН включён в UI, но в документе ноль ОРИОНа — нет позиции ПАК,
монтажа ОРИОН, опор; документ идентичен обычному фундамент+монтаж.
**Как должно (по эталонам monтаж_ОРИОН / фундамент_монтаж_ОРИОН):**
- позиция «Программно-аппаратный комплекс «ОРИОН»» присутствует;
- позиция монтажа ОРИОН: «Монтаж ПАК «ОРИОН»» (монтаж-сценарий) либо
  «Монтаж и настройка программно-аппаратного комплекса «ОРИОН»» (фундамент-сценарий);
- для фундамент+ОРИОН — позиция «Установка опор и кабель-трасс для программно-
  аппаратного комплекса «ОРИОН»»;
- ОРИОН фигурирует в сроках и комплекте поставки;
- обязательства заказчика по опорам (из блока «Опора»).
**Критерий приёмки:**
- ОРИОН вкл → есть позиция ПАК «ОРИОН» + позиция монтажа ОРИОН;
- фундамент+ОРИОН вкл → есть позиция опор/кабель-трасс;
- ОРИОН выкл → ни одной из этих позиций/упоминаний нет (не протекает).
**Диагностика (агент, read-only, до фикса):** где теряется ОРИОН —
не доходит до снапшота КП? теряется в build_specification_from_kp_snapshot?
нет в маппинге опций→позиции? Показать корень.
**Оговорка:** в известных ограничениях значится «ОРИОН-приложения не реализованы
как пакет». Диагностика различает: «не реализовано» (фича) vs «реализовано, но
теряется» (баг). Опция в UI есть и включалась → что-то есть, но не доходит.

## БАГ-1a — рама+монтаж даёт клаузы фундамента вместо площадки
**Как сейчас:** рама-сценарий классифицируется как «фундамент силами заказчика»:
- п.6 «Заказчик обязуется изготовить фундамент своими силами…» (ЛИШНЕЕ);
- контрольный лист фундамента (ЛИШНЕЕ);
- подклеено приложение «Строительное задание на фундамент Весов» (ЛИШНЕЕ);
- клауза площадки 30х4 ОТСУТСТВУЕТ.
**Как должно (дословно, эталон рама_монтаж п.6):**
«Заказчик для установки рамы и Весов предоставляет твердую (асфальт, бетон или
дорожные плиты) горизонтальную площадку размером не менее 30х4м. Допустимые
перепады по высоте – не более 50 мм по всей длине площадки. Допустимый уклон
не более 1:500.»
Плюс монтажные клаузы (общие для монтажа): весы в 5м, автокран 16т,
короткобазный автомобиль, подводка 220В (ПУЭ).
НЕ должно быть: клаузы фундамента-заказчиком, контрольного листа, стройзадания.
**Критерий приёмки:**
- рама+монтаж → есть клауза площадки «не менее 30х4м»;
- рама+монтаж → НЕТ клаузы «изготовить фундамент своими силами»;
- рама+монтаж → НЕТ приложения «Строительное задание на фундамент»;
- рама+монтаж → НЕТ контрольного листа фундамента.
**Диагностика (агент):** где scope «рама» классифицируется как «фундамент
заказчиком» — в build_contract_clauses? в определении foundation-типа?
в attachment-резолвере resolve_build_task (недавно правился в раннере)?

## БАГ-1b — выбор флоу: рама без монтажа должна быть поставкой
**Правило (как должно):**
- есть монтаж/поверка (наши работы на объекте) → договор со спецификацией (spec-флоу);
- нет наших работ (продаём весы/раму) → договор ПОСТАВКИ (supply-флоу),
  без ролевых клауз, спецификация = простой перечень товара.
- рама+монтаж → spec; рама без монтажа → supply.
**Критерий приёмки:** рама без монтажа генерит договор поставки, не спецификацию.
**Диагностика (агент, ПЕРВЫМ делом):**
1. флоу spec/supply выбирается вручную или автоматически? (Антон не уверен —
   по заметкам «автовыбор типа договора не работает, ставится вручную».)
2. если авто — по какому признаку;
3. где чинить, чтобы рама-без-монтажа уходила в supply.
**Развилка:** если флоу ставится ВРУЧНУЮ — это не баг генератора, а UX-решение
(нужен автовыбор или подсказка менеджеру). Закрыть по факту диагностики.

# ГРУППА B/D — клаузы и дубли (P1). Причина ясна, чинятся по спецификации

## D2+B1 — клауза «выезд бригад»: формулировка по признаку стройки + без дублей
**Как сейчас:** клауза протекает в сценарий без монтажа (B1) И задваивается
в сценарии с монтажом — идут подряд «Выезд монтажной бригады…» и «Выезд
строительной и монтажной бригад…» (D2).
**Как должно (правило из эталонов, однозначное):**
- подрядчик СТРОИТ фундамент → «Выезд строительной и монтажной бригад…»
  (эталоны: фундамент_монтаж, строительство_с_материалом);
- подрядчик фундамент НЕ строит (рама/площадка заказчика/заказчик сам делает
  фундамент) → «Выезд монтажной бригады…»
  (эталоны: рама_монтаж, монтаж, монтаж_ОРИОН, рама_шеф-монтаж);
- нет монтажа/шеф-монтажа → клаузы выезда НЕТ;
- всегда РОВНО ОДНА, без дублей.
**Критерий приёмки:**
- подрядчик строит фундамент → клауза содержит «строительной и монтажной бригад», ×1;
- подрядчик не строит → «монтажной бригады» (без «строительной»), ×1;
- нет монтажа → клаузы выезда нет;
- ни в одном сценарии не двоится.

## D1 — задвоенная строка Госреестра в ТТХ
**Как сейчас:** строка «Весы… выпускаются… внесён в Госреестр… № 78871-20»
печатается дважды подряд (Ромашка, п.13 показатель 10).
**Как должно:** строка Госреестра выводится один раз.
**Критерий приёмки:** строка с «№ 78871-20» / «внесён в Госреестр» встречается ×1.

## D3 — дубль «именуемые совместно «Стороны»» в преамбуле
**Как сейчас:** «…именуемые совместно «Стороны», именуемые совместно «Стороны»,
заключили…» (Ромашка).
**Как должно (эталон):** «…именуемые совместно «Стороны», заключили…» — один раз.
**Критерий приёмки:** фраза «именуемые совместно «Стороны»» в преамбуле ×1.

# ГРУППА C — кавычки и имена сторон (P1)

## C1+C3 — нормализация кавычек имени заказчика к ёлочкам
**Как сейчас:** `ООО "Ромашка"` (прямые вместо ёлочек) и
`ООО "Агрофирма «Промышленная"` (внешние прямые, закрывающая потеряна).
**Как должно:** внешние кавычки имени заказчика — ВСЕГДА ёлочки, что бы менеджер
ни ввёл; вложенное содержимое сохраняется как есть.
**Критерий приёмки:**
- ввод `"Ромашка"` → в документе `«Ромашка»`;
- ввод `«Ромашка»` → `«Ромашка»` (не сломано);
- ввод `ООО «Агрофирма «Промышленная»»` → ёлочки сохранены, ничего не потеряно;
- прямых кавычек `"` в имени заказчика в документе нет нигде.

## C4 — две формы имени подрядчика по контексту (страховка, не фикс)
**Правило (обе формы правильные):**
- по договору/спецификации → «ООО «ТПК «Тензосила»»;
- в блоках сертификации / свидетельства об утверждении типа (Госреестр) →
  «ООО «Компания «Тензосила»» (на это юрлицо оформлены документы).
**Критерий приёмки:**
- в реквизитах/преамбуле/подписях → «ТПК «Тензосила»;
- в блоке Госреестра → «Компания «Тензосила»;
- формы не «уезжают» в чужой контекст; кавычки-ёлочки корректны.
**Примечание:** сейчас, судя по эталону, используются правильно. Ловушка на C4 —
СТОРОЖ: при починке кавычек C1/C3 не слить обе формы в одну.

**C2 (двойная ёлочка «Тензосила»») — НЕ баг, убрано.** `ООО «ТПК «Тензосила»»`
с двумя закрывающими — корректное закрытие вложенных ёлочек (правило C1).

# ГРУППА E — оформление, нумерация, порядок (P2)

## E1 — двойная точка в адресе объекта
**Как сейчас:** «уч. 7..» — шаблон ставит точку, значение уже с точкой.
**Как должно:** шаблон ставит точку; концевая точка/пробел из значения адреса
срезается → в документе ровно одна точка.
**Критерий приёмки:** ввод адреса с точкой и без → одна концевая точка, не две.

## E2 — пропуск номера «3» (раздел «Сроки»)
**Как сейчас:** нумерация 1, 2.1-2.3, затем сразу 4; блок сроков без номера 3.
**Как должно (эталон):** «3. Срок поставки Весов и выполнения Работ:» —
пронумерован как пункт 3; нумерация сплошная (1,2,3,4…14) без пропусков.
**Критерий приёмки:** есть пункт «3.»; верхнеуровневая нумерация без дыр.

## E3a — порядок позиций как в эталоне
**Как сейчас:** порядок вперемешку (Весы, Монтаж, Поверка, Доставка, Рама, Пандусы).
**Как должно:** оборудование → услуги, как в эталоне:
Весы → Рама → Пандусы → Доставка → Монтаж → Поверка
(ОРИОН-позиции и фундамент — на своих местах согласно эталону сценария).
**Критерий приёмки:** фиксированный порядок; весы первые; услуги после оборудования.

## E3b — наименования позиций по эталону (не каталожные развёрнутые)
**Как сейчас:** «Рама под весы ВЕСТА-С(Ф)/ФЛ(СЛ), 18м», «Комплект пандусов под
весы ВЕСТА-ФЛ/СЛ (L=2,9м)» — каталожные, длиннее эталона.
**Как должно:** наименования == эталонным. Справочник эталонных наименований:

| Тип позиции | Эталонное наименование |
|---|---|
| Весы | Весы автомобильные ВЕСТА-{модель}, max {тоннаж}т, размеры платформы {L}х3м |
| Рама | Рама 18м для весов ВЕСТА |
| Пандусы (СЛ) | Комплект пандусов для весов ВЕСТА-СЛ/ФЛ |
| Пандусы (Ф) | Комплект пандусов для весов ВЕСТА-Ф/С |
| Доставка | Доставка весов до объекта |
| Монтаж | Монтаж автомобильных весов |
| Шеф-монтаж | Шеф-монтаж автомобильных весов |
| Поверка | Поверка автомобильных весов с доставкой эталонов |
| Фундамент | Фундамент железобетонный под весы автомобильные ВЕСТА-{модель} |
| Фундамент пандусный | Фундамент железобетонный пандусный под весы автомобильные ВЕСТА-{модель} |
| Строительство (материал заказчика) | Строительство фундамента силами Подрядчика с предоставлением материала Заказчиком |
| ПАК ОРИОН | Программно-аппаратный комплекс «ОРИОН» |
| Монтаж ОРИОН (монтаж-сцен.) | Монтаж ПАК «ОРИОН» |
| Монтаж ОРИОН (фунд-сцен.) | Монтаж и настройка программно-аппаратного комплекса «ОРИОН» |
| Опоры ОРИОН | Установка опор и кабель-трасс для программно-аппаратного комплекса «ОРИОН» |

**Критерий приёмки:** наименование каждой позиции == эталонному для этого типа
(плейсхолдеры {модель}/{тоннаж}/{L} подставляются).
**Оговорка:** таблица собрана из первых таблиц эталонов; агент при фиксе сверяет
её с data/prices.json (совпадают ли ключи позиций) — если расходится, сообщает,
не угадывает.

# ГРУППА F — продуктовое (НЕ баг)

## F1 — оплата по вехам vs дефолт 30/40/30
**Наблюдение:** генератор по дефолту ставит 30/40/30 «от общей цены договора».
Эталоны используют оплату по вехам (предоплата за весы+фундамент, доплата за
фундамент по акту, доплата за весы по уведомлению об отгрузке, монтаж по акту).
**Статус:** НЕ баг (дефолт не настраивался). Продуктовое решение:
автоматизировать сборку вех по сценарию ИЛИ оставить ручную настройку.
**Отложено** — обсуждается отдельно, вне этого набора фиксов.
